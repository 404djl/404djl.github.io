第 7 节：进程创建与程序加载（fork + exec）

学习目标：深入理解 Unix “fork + exec” 模型的实现，掌握地址空间复制、ELF 程序格式解析、用户栈构建，以及失败时的完整回滚机制。

预计用时：3-4 小时

前置要求：完成第 6 节，理解 struct proc、allocproc()、proc_pagetable() 等进程基础设施

一、理论：fork + exec 模型

1.1 为什么分离 fork 和 exec？

Unix 的进程创建不是”直接创建一个新进程运行指定程序”，而是拆成两步：

fork()：复制当前进程（包含所有状态）
exec()：用新程序替换当前进程的地址空间

这个设计看起来很绕，但它的价值体现在 fork 和 exec 之间可以插入任意操作：

// shell 执行 "ls > output.txt" 的过程：
int pid = fork();
if(pid == 0) {
    // 子进程（fork 之后、exec 之前）
    close(1);                    // 关闭标准输出
    open("output.txt", O_WRONLY|O_CREATE);  // fd=1 现在指向文件
    exec("ls", argv_ls);         // ls 的输出自然流向文件
}
wait(0);

// 如果 "创建进程" 是一个原子操作，重定向就无从实现

fork+exec 模型的能力：

操作 在 fork 和 exec 之间完成 效果
重定向 > / < close() + open() exec 后程序以为自己在操作 stdout/stdin
管道 | close() + dup() exec 后两个程序通过管道通信
后台运行 & 不调用 wait() 父进程继续，子进程独立运行
环境变量 修改全局变量 exec 的新程序继承修改后的环境
文件描述符继承 什么都不做 exec 后的程序继承所有打开的文件

1.2 fork() 的语义

fork() 调用一次，返回两次：

int pid = fork();

if(pid < 0) {
    // fork 失败（进程表满、内存不足）
} else if(pid == 0) {
    // 在子进程中执行（fork 返回 0）
} else {
    // 在父进程中执行（fork 返回子进程的 PID）
}

子进程是父进程的完整拷贝：

  • 相同的地址空间内容（代码、数据、栈、堆）
  • 相同的程序计数器（PC）——两个进程都从 fork() 返回后的下一条指令开始
  • 相同的打开文件描述符（但共享文件表项，引用计数 +1）
  • 不同的 PID，不同的通过 fork() 的返回值
父进程内存：
  [代码][数据][栈][堆]
      ↓ fork()
父进程              子进程
  [代码][数据][栈][堆]    [代码][数据][栈][堆]（物理内存独立拷贝）
  pid = 子PID           pid = 0
  继续执行...            继续执行...

1.3 exec() 的语义

exec() 用来自文件系统的新程序替换当前进程的地址空间：

exec("ls", argv);
// 如果成功：ls 的代码开始执行，当前进程的所有用户内存被替换
// exec 成功时不返回！（返回到的地方已经不存在了）
// 如果失败：exec 返回 -1，当前进程正常继续

被保留的内容：

  • PID（进程 ID 不变，仍是同一个进程）
  • 打开的文件描述符（除非设置了 FD_CLOEXEC，xv6 不支持）
  • 内核栈
  • 进程在内核中的 struct proc 槽位

被替换的内容：

  • 所有用户内存（代码、数据、栈、堆）
  • 程序计数器（跳到新程序的入口点 entry）
  • 用户页表

二、源码精读：kernel/proc.c 中的 fork()

2.1 完整 fork() 代码解析

int
fork(void)
{
  int i, pid;
  struct proc *np;
  struct proc *p = myproc();   // 父进程

  // ① 分配新进程槽位（含 trapframe 和初始页表）
  if((np = allocproc()) == 0){
    return -1;
  }

  // ② 复制父进程的用户地址空间（所有物理页内容）
  if(uvmcopy(p->pagetable, np->pagetable, p->sz) < 0){
    freeproc(np);
    release(&np->lock);
    return -1;
  }
  np->sz = p->sz;

  // ③ 建立父子关系
  np->parent = p;

  // ④ 复制 trapframe（保存的用户寄存器现场）
  *(np->trapframe) = *(p->trapframe);

  // ⑤ 让子进程的 fork() 返回 0（父进程的返回值 pid 在后面设置）
  np->trapframe->a0 = 0;

  // ⑥ 复制打开的文件描述符（引用计数 +1）
  for(i = 0; i < NOFILE; i++)
    if(p->ofile[i])
      np->ofile[i] = filedup(p->ofile[i]);

  // ⑦ 复制当前目录（引用计数 +1）
  np->cwd = idup(p->cwd);

  // ⑧ 复制进程名（调试用）
  safestrcpy(np->name, p->name, sizeof(p->name));

  // ⑨ 记录返回给父进程的值（子进程 PID）
  pid = np->pid;

  // ⑩ 设为可运行，释放锁
  np->state = RUNNABLE;
  release(&np->lock);

  return pid;   // 父进程返回子进程 PID
                // 子进程从 forkret → usertrapret 返回，a0=0
}

2.2 关键步骤深度解析

步骤 ④⑤：为什么复制 trapframe 能让子进程”从 fork() 返回”？

当父进程进入内核（通过 ecall）调用 sys_fork() 时，trampoline.S 已经将父进程的全部 32 个用户寄存器保存到 p->trapframe。

fork() 做了 *(np->trapframe) = *(p->trapframe)——子进程拷贝了父进程进入内核时的完整寄存器快照，包括：

  • epc：父进程执行 ecall 时的 PC（+4 后指向 ecall 的下一条指令）
  • sp：父进程的用户栈指针
  • 所有其他寄存器

然后 np->trapframe->a0 = 0——覆盖系统调用返回值寄存器为 0。

当子进程第一次被调度（通过 forkret → usertrapret → trampoline.S），会从 trapframe 恢复所有寄存器：

  • a0 = 0（fork 在子进程中的返回值）
  • epc 指向 ecall 后的下一条指令（即 fork() 调用处的返回点）
  • sp 和其他寄存器与父进程完全相同

子进程就像刚从 fork() 返回一样——只是返回值是 0。

父进程进入内核（ecall 系统调用）：
  用户寄存器全部存入 p->trapframe
  执行 fork() → 返回 pid（存入 p->trapframe->a0）
  恢复 p->trapframe 到寄存器，返回用户态
  a0 = pid（子进程 PID）

子进程第一次被调度：
  forkret() → usertrapret() → trampoline.S
  从 np->trapframe 恢复寄存器：
    a0 = 0（被 fork() 修改）
    epc = 父进程调用 ecall 时的 PC（fork 的返回处）
    sp = 父进程的用户栈指针
  进入用户态，在 fork() 调用处继续
  a0 = 0（fork 在子进程中返回 0）

步骤 ⑥：文件描述符的”共享”

filedup(p->ofile[i]) 不是复制文件，而是增加文件的引用计数：

fork() 之前：
  父进程 ofile[1] ──→ [struct file: fd=1, pos=100, refcnt=1] ──→ inode

fork() 之后：
  父进程 ofile[1] ──→ [struct file: fd=1, pos=100, refcnt=2]
  子进程 ofile[1] ──┘           ↑
                        父子共享同一个 file 结构体！

这意味着：父子进程如果都向 fd=1 写数据，会推进同一个文件偏移位置。

步骤 ⑦：idup(p->cwd) 与目录引用

idup 增加当前目录 inode 的引用计数，确保即使父进程调用 chdir() 改变自己的工作目录，子进程仍然指向 fork 时的目录。

2.3 fork() 的全部内存操作

fork() 的内存分配（假设父进程 sz = 8KB = 2 页）：

allocproc():
  kalloc()                   → trapframe（4KB）
  kvmcreate() + mappages()   → L2根页表（4KB）
  各级中间页表               → 若干4KB

uvmcopy(parent, child, 2 pages):
  kalloc()                   → 子进程第 0 页（4KB）
  memmove()                  → 复制父进程第 0 页内容
  mappages()                 → 建立子进程页表映射

  kalloc()                   → 子进程第 1 页（4KB）
  memmove()                  → 复制父进程第 1 页内容
  mappages()                 → 建立子进程页表映射

总计：每次 fork 至少分配 (sz/4KB + 4 + 页表页数) 个物理页
父进程 sz 越大，fork 越慢

这正是 Linux 引入 Copy-on-Write（COW）fork 的原因：fork 时不立即复制物理页，只有在父子进程真正写某一页时才复制。MIT 6.S081 的 COW lab 要求学生为 xv6 实现这个优化。

三、源码精读：kernel/exec.c——完整 157 行

exec() 是 Unix 系统最复杂的系统调用之一。xv6 的实现虽然精简，但包含了所有核心要素。

3.1 ELF 文件格式基础

在深入 exec() 源码之前，需要理解 ELF（Executable and Linkable Format）文件格式：

ELF 文件结构：

┌─────────────────────────────────────┐  偏移 0
│         ELF Header（64字节）         │  struct elfhdr
│  magic（4字节）: \x7FELF             │
│  entry（8字节）: 程序入口虚拟地址     │
│  phoff（8字节）: Program Header 偏移 │
│  phnum（2字节）: Program Header 数量 │
│  ...                                │
├─────────────────────────────────────┤
│       Program Header 0              │  struct proghdr
│  type: LOAD（需要加载到内存）         │
│  flags: R/W/X 权限                   │
│  off: 在 ELF 文件中的偏移            │
│  vaddr: 加载到的虚拟地址             │ ← 比如 0x0（代码段）
│  filesz: 文件中的大小                │
│  memsz: 内存中的大小（≥ filesz）     │ ← memsz > filesz 时多余部分清零（BSS）
│  align: 对齐要求                     │
├─────────────────────────────────────┤
│       Program Header 1              │  另一个段（如数据段）
│  ...                                │
├─────────────────────────────────────┤
│                                     │
│     实际的代码和数据                  │ ← 由 off+filesz 描述
│                                     │
└─────────────────────────────────────┘

xv6 编译出的用户程序使用 ELF 格式（file user/_ls 可以验证）。exec() 的核心工作就是解析 ELF，将各个段加载到新进程的地址空间中。

**struct elfhdr 和 struct proghdr**：

// kernel/elf.h
#define ELF_MAGIC 0x464C457FU  // "\x7FELF"

struct elfhdr {
  uint magic;      // 魔数，必须是 ELF_MAGIC
  uchar elf[12];   // ELF 标识（class、data、version 等）
  ushort type;     // 类型（ET_EXEC = 可执行文件）
  ushort machine;  // 目标架构（EM_RISCV = RISC-V）
  uint version;
  uint64 entry;    // 程序入口虚拟地址（main 函数前的 _start）
  uint64 phoff;    // Program Header Table 在文件中的偏移
  uint64 shoff;    // Section Header Table 偏移（exec 不需要）
  uint flags;
  ushort ehsize;   // ELF header 大小
  ushort phentsize;// 每个 Program Header 的大小
  ushort phnum;    // Program Header 数量
  // ...
};

struct proghdr {
  uint32 type;     // 段类型：ELF_PROG_LOAD(1) = 需要加载
  uint32 flags;    // 权限：ELF_PROG_FLAG_EXEC(1), WRITE(2), READ(4)
  uint64 off;      // 段在 ELF 文件中的偏移
  uint64 vaddr;    // 段的目标虚拟地址
  uint64 paddr;    // 物理地址（用于嵌入式，xv6 忽略）
  uint64 filesz;   // 文件中的大小
  uint64 memsz;    // 内存中的大小（memsz > filesz 时，多余部分 = BSS，清零）
  uint64 align;    // 对齐要求（必须是 2 的幂）
};

memsz > filesz 的含义（BSS 段）：

C 程序中全局未初始化变量（int global_arr[1000];）存在 BSS 段。BSS 数据不保存在 ELF 文件中（全是零，保存了浪费空间），但在内存中必须占据相应大小的区域（全部初始化为零）。uvmalloc() 会将分配的页清零（memset(0, PGSIZE)），所以 memsz > filesz 的区域自然就是全零——恰好符合 BSS 语义。

3.2 exec() 完整流程

int
exec(char *path, char **argv)   // path = 程序路径，argv = 参数数组
{
  char *s, *last;
  int i, off;
  uint64 argc, sz = 0, sp, ustack[MAXARG+1], stackbase;
  struct elfhdr elf;
  struct inode *ip;
  struct proghdr ph;
  pagetable_t pagetable = 0, oldpagetable;
  struct proc *p = myproc();

局部变量说明：

  • sz：新地址空间已分配到的虚拟地址（从 0 开始增长）
  • sp：用户栈指针（构建用户栈时使用）
  • ustack[]：临时存储 argv 字符串在用户栈上的地址
  • pagetable：新建的页表（成功时替换旧页表，失败时释放）
  • oldpagetable：原来的页表（成功后释放）

阶段一：读取并校验 ELF 文件

  begin_op();                       // 文件系统日志开始

  if((ip = namei(path)) == 0){      // 在文件系统中查找程序文件
    end_op();
    return -1;
  }
  ilock(ip);

  // 读取 ELF header（64字节）
  if(readi(ip, 0, (uint64)&elf, 0, sizeof(elf)) != sizeof(elf))
    goto bad;
  // 验证魔数：必须是 "\x7FELF"
  if(elf.magic != ELF_MAGIC)
    goto bad;

安全检查：readi(ip, 0, ...) 的第二个参数 0 表示”读到内核地址”（而非用户地址）。elf.magic 验证防止将非 ELF 文件当作程序执行（例如执行一个文本文件会在此 goto bad）。

阶段二：创建新页表并加载各程序段

  // 为新程序创建新用户页表（含 TRAMPOLINE + TRAPFRAME 映射）
  if((pagetable = proc_pagetable(p)) == 0)
    goto bad;

  // 遍历所有 Program Header
  for(i=0, off=elf.phoff; i<elf.phnum; i++, off+=sizeof(ph)){
    // 读取第 i 个 Program Header
    if(readi(ip, 0, (uint64)&ph, off, sizeof(ph)) != sizeof(ph))
      goto bad;
    if(ph.type != ELF_PROG_LOAD)    // 只处理 LOAD 类型
      continue;

    // 安全检查
    if(ph.memsz < ph.filesz)        // 内存大小不能小于文件大小
      goto bad;
    if(ph.vaddr + ph.memsz < ph.vaddr)  // 防止虚拟地址溢出
      goto bad;

    // 在新页表中分配从 sz 到 ph.vaddr+ph.memsz 的虚拟内存
    uint64 sz1;
    if((sz1 = uvmalloc(pagetable, sz, ph.vaddr + ph.memsz)) == 0)
      goto bad;
    sz = sz1;

    if(ph.vaddr % PGSIZE != 0)      // xv6 要求段必须页对齐
      goto bad;

    // 将段数据从文件读取到新页表对应的内存
    if(loadseg(pagetable, ph.vaddr, ip, ph.off, ph.filesz) < 0)
      goto bad;
  }
  iunlockput(ip);   // 解锁并释放 inode 引用
  end_op();         // 文件系统日志结束
  ip = 0;           // 清除，防止 goto bad 重复释放

uvmalloc 的调用逻辑：

假设程序有两个 LOAD 段：

  • 段 0：vaddr=0x0, memsz=0x3000（代码段，12KB）
  • 段 1：vaddr=0x3000, memsz=0x2000（数据段，8KB）
初始：sz = 0

处理段 0：
  uvmalloc(pagetable, 0, 0+0x3000)    → sz = 0x3000
  loadseg(pagetable, 0, ip, off, filesz)  → 从文件读代码到 [0x0, 0x3000)

处理段 1：
  uvmalloc(pagetable, 0x3000, 0x3000+0x2000) → sz = 0x5000
  loadseg(pagetable, 0x3000, ip, off, filesz)  → 从文件读数据到 [0x3000, 0x5000)

阶段三：分配用户栈

  p = myproc();
  uint64 oldsz = p->sz;    // 保存旧进程的大小（用于失败回滚）

  // 在 sz 向上对齐到页边界后，再分配 2 个页
  // 第 1 页：保护页（不设 PTE_U）—— guard page
  // 第 2 页：用户栈
  sz = PGROUNDUP(sz);
  uint64 sz1;
  if((sz1 = uvmalloc(pagetable, sz, sz + 2*PGSIZE)) == 0)
    goto bad;
  sz = sz1;

  uvmclear(pagetable, sz - 2*PGSIZE);  // 清除保护页的 PTE_U 标志
  sp = sz;                              // 用户栈指针 = 栈顶（高地址）
  stackbase = sp - PGSIZE;             // 栈底（保护页之上，栈的最低合法地址）

用户栈的内存布局：

虚拟地址：

  sz（段加载后）：  0x5000
  PGROUNDUP(sz)：  0x5000（已对齐）
  
  分配 2*PGSIZE = 8KB：

  0x7000    ← sp（栈顶，空的，向下增长）
  ├─────────── 用户栈（4KB，PTE_R|PTE_W|PTE_U）
  0x6000    ← stackbase（栈最低合法地址）
  ├─────────── 保护页（4KB，PTE_R|PTE_W，无 PTE_U）
  0x5000

保护页的作用：用户栈如果溢出（访问 stackbase 以下），会碰到没有 PTE_U 的保护页，触发 page fault——内核可以检测并报告栈溢出，而不是静默损坏堆数据。

阶段四：将参数压入用户栈

  // 将 argv 字符串从高地址向下压栈
  for(argc = 0; argv[argc]; argc++) {
    if(argc >= MAXARG)    // MAXARG=32，参数不能太多
      goto bad;
    sp -= strlen(argv[argc]) + 1;   // 字符串长度 + NUL 终止符
    sp -= sp % 16;                  // RISC-V ABI：sp 必须 16 字节对齐
    if(sp < stackbase)              // 检测栈溢出
      goto bad;
    if(copyout(pagetable, sp, argv[argc], strlen(argv[argc]) + 1) < 0)
      goto bad;
    ustack[argc] = sp;              // 记录字符串在用户栈上的地址
  }
  ustack[argc] = 0;    // argv[argc] = NULL（数组终止符）

  // 将 argv 指针数组（ustack）压栈
  sp -= (argc+1) * sizeof(uint64);  // 每个指针 8 字节，最后一个是 NULL
  sp -= sp % 16;
  if(sp < stackbase)
    goto bad;
  if(copyout(pagetable, sp, (char*)ustack, (argc+1)*sizeof(uint64)) < 0)
    goto bad;

  // argc 通过 a0 返回（exec 的返回值）
  // argv 指针数组的地址通过 a1 传递
  p->trapframe->a1 = sp;

用户栈构建完成后的布局：

假设执行 exec("ls", {"ls", "-l", NULL})：

高地址 → 低地址：

  0x6FF0  [NUL]
  0x6FED  "-l\0"（argv[1] 的字符串）
  0x6FE0  "ls\0"（argv[0] 的字符串）
             ↕ 中间对齐填充
  0x6FD0  argv[2] 的指针 = 0（NULL）
  0x6FC8  argv[1] 的指针 = 0x6FED
  0x6FC0  argv[0] 的指针 = 0x6FE0
  
  sp = 0x6FC0     （这是 main(argc, argv) 中 argv 参数的值）
  a0 = argc = 2   （通过 exec 返回值传给 a0）
  a1 = sp = 0x6FC0（直接设置 trapframe->a1）

RISC-V 调用约定：main(int argc, char *argv[]) 的参数通过 a0, a1 传递。

  • a0 = argc：通过 exec() 的返回值传递（系统调用返回值放在 a0）
  • a1 = (char **)sp：通过直接设置 p->trapframe->a1 传递

阶段五：提交，替换旧地址空间

  // 提取程序名（路径的最后一部分）用于调试
  for(last=s=path; *s; s++)
    if(*s == '/')
      last = s+1;
  safestrcpy(p->name, last, sizeof(p->name));

  // ══════ 不可回滚点（Commit）══════
  oldpagetable = p->pagetable;      // 保存旧页表
  p->pagetable = pagetable;         // 切换到新页表
  p->sz = sz;                       // 更新进程大小
  p->trapframe->epc = elf.entry;    // 设置程序入口点（从 entry 开始执行）
  p->trapframe->sp = sp;            // 设置用户栈指针
  proc_freepagetable(oldpagetable, oldsz);  // 释放旧地址空间

  return argc;    // 返回 argc，作为用户 main() 的第一个参数（a0）

Commit 点的设计：

在 p->pagetable = pagetable 这行之前，失败仍可回滚（释放新页表）；之后就无法回滚了（旧页表已经被 proc_freepagetable 释放）。这就是为什么要先建立新页表，最后才切换并释放旧的——“failed exec leaves the process intact” （exec 失败时进程仍然可以继续运行）。

阶段六：错误处理（goto bad）

 bad:
  if(pagetable)
    proc_freepagetable(pagetable, sz);   // 释放新页表
  if(ip){
    iunlockput(ip);                       // 释放文件锁和引用
    end_op();
  }
  return -1;

goto bad 的使用：

exec() 中多次出现 goto bad，这是 C 语言中处理多层失败的经典模式。任何一步出错，都跳到 bad: 标签，统一释放所有已分配的资源，返回 -1。如果没有 goto，需要在每个失败点重复所有清理代码，极其繁琐且容易遗漏。

3.3 loadseg()——将程序段从文件读入内存

static int
loadseg(pagetable_t pagetable, uint64 va, struct inode *ip,
        uint offset, uint sz)
{
  uint i, n;
  uint64 pa;

  if((va % PGSIZE) != 0)
    panic("loadseg: va must be page aligned");

  for(i = 0; i < sz; i += PGSIZE){
    pa = walkaddr(pagetable, va + i);   // 虚拟地址 → 物理地址
    if(pa == 0)
      panic("loadseg: address should exist");   // 页必须已由 uvmalloc 分配
    if(sz - i < PGSIZE)
      n = sz - i;     // 最后一页可能不满
    else
      n = PGSIZE;
    if(readi(ip, 0, (uint64)pa, offset+i, n) != n)  // 从文件读到物理地址
      return -1;
  }
  return 0;
}

关键细节：

  1. walkaddr(pagetable, va+i) 在新页表（不是当前进程页表）中查找物理地址——uvmalloc 已经在新页表中建立了映射，loadseg 需要找到这些物理页的实际地址才能写入
  2. readi(ip, 0, (uint64)pa, ...) 的第二个参数 0 = 直接写到物理地址（内核视角）—— pa 是物理地址，在内核直接映射区可以直接访问
  3. 按页读取（PGSIZE 为单位），最后一页可能不满（filesz 不一定是 PGSIZE 的倍数）

3.4 exec() 的完整内存视图

执行 exec("ls", argv) 之后，进程的用户地址空间变为：

虚拟地址（低 → 高）：

0x0000           text（代码段，PTE_R|PTE_X|PTE_U）
                   ls 的机器指令
 ...
vaddr+filesz     text + BSS
 ...
vaddr+memsz      data（数据段，PTE_R|PTE_W|PTE_U）
                   全局变量、静态变量
 ...
sz（ELF加载后）

PGROUNDUP(sz)    保护页（SZ+PGSIZE，无 PTE_U）
PGROUNDUP(sz)+PGSIZE  用户栈（SZ+2*PGSIZE，PTE_R|PTE_W|PTE_U）
                   ↓（sp 从高地址向低地址增长）
                   [argv[0]指针][argv[1]指针]...[NULL]
                   [argv[n-1]字符串]...[argv[0]字符串]
                   ← sp 初始指向 argv[] 数组

（巨大的空洞）

TRAPFRAME = TRAMPOLINE - PGSIZE（无 PTE_U）
TRAMPOLINE = MAXVA - PGSIZE（无 PTE_U）

四、深入理解：fork + exec 的协作

4.1 shell 如何用 fork + exec 执行命令

user/sh.c 展示了 fork+exec 模型的经典用法：

// shell 主循环（简化）
int main(void) {
  char buf[100];
  while(getcmd(buf, sizeof(buf)) >= 0) {

    if(buf 是 "cd xxx") {
      chdir(buf+3);   // cd 是特例：必须在父进程执行（改变 shell 自身的目录）
      continue;
    }

    if(fork1() == 0)      // fork 一个子进程
      runcmd(parsecmd(buf));  // 子进程执行命令
    wait(0);              // 父进程等待子进程完成
  }
}

void runcmd(struct cmd *cmd) {
  switch(cmd->type) {
  case EXEC:
    exec(cmd->argv[0], cmd->argv);   // 替换子进程为目标程序
    fprintf(2, "exec %s failed\n", cmd->argv[0]);  // 只有 exec 失败才到这里
    break;

  case PIPE:  // "ls | wc"
    pipe(p);
    if(fork1() == 0) {
      close(1); dup(p[1]);   // 左侧：标准输出 → 管道写端
      close(p[0]); close(p[1]);
      runcmd(pcmd->left);    // exec "ls"
    }
    if(fork1() == 0) {
      close(0); dup(p[0]);   // 右侧：标准输入 ← 管道读端
      close(p[0]); close(p[1]);
      runcmd(pcmd->right);   // exec "wc"
    }
    close(p[0]); close(p[1]);
    wait(0); wait(0);        // 等两个子进程完成
    break;
  }
  exit(0);
}

管道 ls | wc 的执行轨迹：

shell (pid=2)
  ├── fork() → pid=3（处理 PIPE）
  │    ├── fork() → pid=4（ls）
  │    │    close(1); dup(p[1])   // stdout → pipe[1]
  │    │    exec("ls")            // ls 的输出写到管道
  │    │    exit(0)
  │    └── fork() → pid=5（wc）
  │         close(0); dup(p[0])   // stdin ← pipe[0]
  │         exec("wc")            // wc 从管道读取 ls 的输出
  │         exit(0)
  └── wait(0); wait(0)            // 等两个子进程

管道的神奇之处：ls 和 wc 本身不知道彼此的存在，也不需要修改。fork 之后修改文件描述符，再 exec 实现了透明的进程间通信。

4.2 exec() 为什么先建新页表再释放旧页表（失败安全）

exec() 的内存管理策略：

策略一（危险）：先释放旧页表，再建立新页表
  ①  free(old_pagetable)
  ②  new_pagetable = allocate_and_load()
  如果 ② 失败 → 进程没有可用的页表 → 进程损坏，只能 panic

策略二（exec 的实际做法）：先建新页表，成功后再释放旧页表
  ①  new_pagetable = allocate_and_load()（在此期间旧页表仍然有效）
  如果 ① 失败 → goto bad → proc_freepagetable(new_pagetable, sz)
               → 旧页表完好，进程继续正常运行，exec 返回 -1
  如果 ① 成功 → p->pagetable = new_pagetable → free(old_pagetable)

这就是”原子替换”思想：直到确认新状态完全就绪，才切换并废弃旧状态。

六、思考题

  1. fork() 中 *(np->trapframe) = *(p->trapframe) 是一次整体拷贝。其中包含 epc 字段，指向父进程调用 ecall 后的下一条指令。子进程恢复执行后，是从哪里开始运行的？为什么不是从进程的最开始？

    子进程从 ecall (系统调用) 指令的下一条指令开始运行——也就是 fork() 调用在用户空间的返回处。epc 被 trampoline.S 保存为 sepc 的值，而 sepc 硬件在执行 ecall 时自动设为 ecall +4（下一条指令）。子进程不需要从程序开头运行，它和父进程处于完全相同的执行位置，只是返回值（a0）不同。

  2. exec() 将参数字符串从 argv（内核地址）压入用户栈（用户地址），使用了 copyout()。为什么不能直接用指针赋值？

    用户栈存在于新创建的用户页表中，而 argv 字符串来自旧的用户地址空间或内核。exec() 在内核中运行，CPU 使用内核页表，直接用虚拟地址访问用户栈会访问到内核页表下的物理地址，而不是新用户页表对应的物理地址。copyout(pagetable, sp, ...) 通过显式查询新页表（walkaddr）找到用户栈对应的物理地址，再通过内核直接映射写入——这才是正确的跨页表内存访问方式。

  3. xv6 的 exec() 不支持 setuid 位（即 exec 之后进程有更高权限）。如果要支持这个特性，需要在哪里修改？需要额外注意哪些安全问题？

    需要在 ELF 头读取后、提交阶段之前，检查文件的 inode 权限位（ip->mode & 0x800），如果 setuid 位置位，将进程的 UID 改为文件所有者的 UID（xv6 没有 UID 当然要先加这个机制）。安全问题：(1) 检查 setuid 后要立即关闭它继承的到可能危险的文件描述符（防止权限提升后泄露敏感文件句柄）；(2) 要防止符号链接攻击（TOCTOU：检查权限和执行之间被替换文件）；(3) exec 的参数（从用户空间读取）需要在切换权限之前就已经读取到内核，防止攻击者在切换后修改。

  4. 为什么 exec 成功时不返回，但失败时返回 -1？从进程调度的角度解释：exec 成功时，返回地址已经不复存在了，程序是如何”不返回”的？

    exec 成功时：p->trapframe->epc 被设置为新程序的入口地址（elf.entry），p->trapframe->sp 被设置为新的用户栈指针，然后函数正常 return（返回内核，通过系统调用返回机制）。当系统调用从内核返回用户态时，trampoline.S 会从 trapframe 恢复寄存器，epc 是新程序的入口——于是 CPU 跳到新程序开始执行，而不是回到调用 exec 的用户代码。”旧”程序的代码已经被新页表替换，物理上就不存在了。exec 失败时，trapframe->epc 没有被修改，系统调用正常返回 -1，控制流回到调用 exec 的地方。

  5. xv6 的 fork 是完整复制（eager copy），而现代操作系统使用 Copy-on-Write（COW）。在如下场景中，这两种方式的页数消耗有多大差异？假设父进程内存为 10MB（2560 页），fork 后子进程立即 exec 一个 100KB（25页）的程序。

    eager copy：fork 时复制 2560 个物理页（10MB），exec 后释放 2560 页再分配约 25+栈 页。消耗峰值：父进程 2560 页 + 子进程 2560 + 几页中间状态 = 约 5120 页额外消耗。COW fork：fork 时不复制任何物理页，只复制页表（标记所有页为只读 COW），消耗仅约几页页表页。exec 时直接放弃所有 COW 标记，分配新的 25+栈 页。消耗峰值：父进程 2560 页 + 子进程页表几页 + 新程序约 30 页 = 约 2590 页。节省约 2530 页（~10MB）。这正是 “fork + exec” 最常用场景（shell 执行命令）下 COW 的巨大价值。

  6. shell 的 cd 命令为什么不通过 fork+exec 来执行，而是直接在父进程（shell 本身）中调用 chdir()？

    因为 chdir() 改变的是当前进程的工作目录（struct proc.cwd）。如果 shell fork 一个子进程执行 exec("cd", ...) 或在子进程中调用 chdir()，工作目录只在子进程中改变；子进程退出后，shell（父进程）的工作目录丝毫不变——用户感受到的 cd 毫无效果。因此 cd 必须由 shell 进程自己调用 chdir()，修改自己的 cwd。user/sh.c 中对此有明确处理：if(buf[0]=='c' && buf[1]=='d') { chdir(buf+3); continue; }

七、本节小结

概念 要点
fork+exec 分离 fork 之间可以插入任意操作（重定向、管道、setuid 等）
fork() 返回 父进程得到子 PID，子进程 a0 被覆盖为 0
trapframe 复制 子进程继承父进程进入内核时的寄存器快照，从同一点恢复执行
文件描述符共享 filedup() 增加引用计数，父子共享同一 struct file（共享偏移）
ELF 格式 file header（入口/段偏移/段数量）+ program headers（各段地址/权限/大小）
exec() 三阶段 ① 读 ELF + 加载段；② 建用户栈 + 压 argv；③ 提交（切换页表）
BSS 处理 memsz > filesz：多余部分由 uvmalloc 的 memset(0) 自动清零
用户栈布局 保护页（无 PTE_U）+ 栈页；argv 字符串从高到低，指针数组在下
exec 失败安全 先建新页表再替换，任何步骤失败均 goto bad 释放新页表，进程完好
loadseg() 按页读文件（readi），写入已映射的物理地址（通过 walkaddr 找到）
argc / a1 传递 argc 由 exec 返回值（a0）传递，argv 直接写入 trapframe->a1
