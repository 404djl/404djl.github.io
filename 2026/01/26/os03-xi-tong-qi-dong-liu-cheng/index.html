第 3 节：系统启动流程

学习目标：追踪 xv6 从 QEMU 上电到第一个用户进程运行的完整路径，理解多核启动协议、特权级切换和内核初始化序列。

预计用时：3-4 小时

前置要求：完成第 2 节，理解 RISC-V 特权级和 CSR 寄存器

一、理论：从上电到用户空间

1.1 启动的全景图

xv6 的启动是一个精心编排的序列，从硬件到软件，从最高特权级到最低特权级：

┌──────────────────────────────────────────────────────────────────┐
│ 阶段 1: 硬件 (QEMU)                                             │
│   QEMU 将 kernel 加载到 0x80000000                               │
│   每个 CPU 核心（hart）从 0x80000000 开始执行                     │
├──────────────────────────────────────────────────────────────────┤
│ 阶段 2: M-mode (entry.S → start.c)                              │
│   每个 hart 设置自己的栈指针                                      │
│   配置 CSR 寄存器、委托中断、初始化时钟                            │
│   通过 mret 切换到 S-mode                                        │
├──────────────────────────────────────────────────────────────────┤
│ 阶段 3: S-mode 初始化 (main.c)                                   │
│   CPU 0：执行完整的初始化序列（17 个 init 函数）                   │
│   其他 CPU：等待 CPU 0 完成，再做最小初始化                        │
├──────────────────────────────────────────────────────────────────┤
│ 阶段 4: 第一个用户进程 (userinit → initcode → init)              │
│   userinit() 创建第一个进程，加载 initcode                        │
│   initcode 执行 exec("/init")                                   │
│   init 进程打开控制台、启动 shell                                 │
├──────────────────────────────────────────────────────────────────┤
│ 阶段 5: 调度循环 (scheduler)                                     │
│   每个 CPU 进入 scheduler() 无限循环                              │
│   在 RUNNABLE 进程间轮转调度                                      │
│   系统正式运行                                                    │
└──────────────────────────────────────────────────────────────────┘

1.2 多核启动协议

xv6 运行在 QEMU 的 RISC-V virt 平台上，默认配置 3 个 CPU 核心。启动时的关键问题：

所有核心同时开始执行

QEMU 使用 -kernel 选项加载内核 ELF，然后让每个 hart 从 0x80000000 开始执行（即 entry.S 的 _entry）。这意味着 3 个 CPU 核心会同时执行相同的代码。

为什么不能所有核心同时初始化？

初始化涉及大量共享数据结构的设置（如进程表、页表、文件表），如果多个核心同时修改这些数据，会产生竞态条件。因此 xv6 采用主从式启动：

CPU 0（主核心）：
  ① 执行完整初始化（17 个 init 函数）
  ② 设置 started = 1（通知其他核心）
  ③ 进入 scheduler()

CPU 1, 2（从核心）：
  ① 自旋等待 started == 1
  ② 仅执行最小初始化（3 个 init 函数）
  ③ 进入 scheduler()

1.3 第一个用户进程的诞生

xv6 的第一个用户进程有两个阶段：

阶段 1：initcode（嵌入内核的微型程序）

  • userinit() 将 initcode[] 数组（52 字节的机器码）复制到新进程的用户空间
  • initcode 的唯一任务：调用 exec("/init", argv)
  • 为什么不直接加载 /init？因为此时文件系统初始化还没有完成（fsinit() 在 forkret() 中调用）

阶段 2：/init 程序（user/init.c）

  • 打开控制台设备（建立 fd 0/1/2）
  • 无限循环：fork() + exec("sh") → shell 退出则重启
userinit()                 initcode              /init          shell
    │                          │                    │              │
    │  创建进程 + 加载 initcode  │                    │              │
    ├─────────────────────────>│                    │              │
    │                          │ exec("/init")      │              │
    │                          ├──────────────────>│              │
    │                          │                    │ open console │
    │                          │                    │ dup(0), dup(0)
    │                          │                    │ fork+exec    │
    │                          │                    ├─────────────>│
    │                          │                    │              │ $

二、源码精读：kernel/kernel.ld（链接器脚本）

在分析代码之前，先理解内核是如何在内存中布局的。链接器脚本控制了这一切。

2.1 逐段解析

OUTPUT_ARCH( "riscv" )        /* 目标架构：RISC-V */
ENTRY( _entry )                /* 程序入口点：_entry（在 entry.S 中） */

SECTIONS
{
  . = 0x80000000;              /* 起始虚拟地址（=物理地址，因为还没开分页） */

  .text : {                    /* 代码段 */
    *(.text .text.*)           /* 所有 .o 文件的代码 */
    . = ALIGN(0x1000);         /* 对齐到页边界 */
    _trampoline = .;           /* 标记 trampoline 代码的起始地址 */
    *(trampsec)                /* trampoline.S 中标记为 trampsec 段的代码 */
    . = ALIGN(0x1000);         /* 对齐到下一个页边界 */
    ASSERT(. - _trampoline == 0x1000, "..."); /* 确保 trampoline 恰好 1 页 */
    PROVIDE(etext = .);        /* 导出符号：代码段结束地址 */
  }

  .rodata : { ... }           /* 只读数据段 */
  .data : { ... }             /* 可读写数据段 */
  .bss : { ... }              /* 未初始化数据段（零初始化） */

  PROVIDE(end = .);            /* 导出符号：内核结束地址 */
}

关键符号：

符号 含义 使用位置
_entry 内核入口点（第一条指令） QEMU 跳转目标
_trampoline trampoline 代码的物理地址 kvminit() 映射用
etext 代码段结束地址 kvminit() 区分代码段和数据段的映射权限
end 内核在内存中的结束地址 kinit() 从这里开始管理空闲物理页

内核在内存中的布局：

0x80000000  ┌──────────────────┐ ← _entry
            │   .text          │    代码段（可读+可执行）
            │   ...            │
            ├──────────────────┤ ← _trampoline（页对齐）
            │   trampoline.S   │    恰好 1 页（4KB）
            ├──────────────────┤ ← etext（页对齐）
            │   .rodata        │    只读数据（可读）
            ├──────────────────┤
            │   .data          │    数据段（可读+可写）
            ├──────────────────┤
            │   .bss           │    未初始化数据（零初始化）
            ├──────────────────┤ ← end
            │                  │
            │   空闲物理页      │    由 kalloc.c 管理
            │                  │
0x88000000  └──────────────────┘ ← PHYSTOP

为什么 trampoline 必须在单独的一页？

trampoline 会被映射到用户页表和内核页表的最高虚拟地址（TRAMPOLINE = MAXVA - PGSIZE）。页表映射以页为单位，所以 trampoline 代码必须占据完整的一页，且不能与其他代码混在一个页中。

三、源码精读：kernel/entry.S（启动入口）

这是整个内核执行的第一条指令。仅 20 行，却建立了 C 语言运行的基础。

3.1 完整代码逐行解析

        # QEMU 将内核加载到 0x80000000
        # 并让每个 CPU 跳转到这里
        # kernel.ld 保证这段代码被放在 0x80000000

.section .text           # 放入 .text 段
_entry:                  # 入口标签（kernel.ld 中 ENTRY(_entry) 指定的）

        # 为 C 代码建立栈
        # stack0 在 start.c 中声明
        # 每个 CPU 有 4096 字节的栈
        # sp = stack0 + (hartid + 1) * 4096

        la sp, stack0           # sp = stack0 的地址
        li a0, 1024*4           # a0 = 4096（栈大小）
        csrr a1, mhartid        # a1 = 当前 CPU 的 hartid（0, 1, 或 2）
        addi a1, a1, 1          # a1 = hartid + 1
        mul a0, a0, a1          # a0 = 4096 * (hartid + 1)
        add sp, sp, a0          # sp = stack0 + 4096 * (hartid + 1)

        # 跳转到 start.c 中的 start() 函数
        call start

spin:                           # start() 不应该返回
        j spin                  # 如果返回了，死循环

3.2 栈指针计算详解

stack0 在 start.c 中定义为：

__attribute__ ((aligned (16))) char stack0[4096 * NCPU];
// = 一个 4096 * 8 = 32768 字节的数组（NCPU=8）
// __attribute__ ((aligned (16))) 保证 16 字节对齐（RISC-V ABI 要求）

三个 CPU 的栈分配：

stack0 (低地址)
  │                                            
  ├────── stack0 + 4096  ← CPU 0 的栈顶 (sp)   
  │       CPU 0 的栈空间（向下增长）              
  ├────── stack0 + 8192  ← CPU 1 的栈顶 (sp)   
  │       CPU 1 的栈空间                         
  ├────── stack0 + 12288 ← CPU 2 的栈顶 (sp)   
  │       CPU 2 的栈空间                         
  ├────── ...                                   
  └────── stack0 + 32768

为什么是 hartid + 1 而不是 hartid？

栈从高地址向低地址增长。CPU 0 的栈空间是 stack0[0..4095]，栈顶是 stack0 + 4096。如果用 hartid * 4096，CPU 0 的 sp = stack0（栈底），就没有可用空间了。

为什么这里可以用 csrr a1, mhartid？

此时 CPU 运行在 M-mode（QEMU 启动后默认的特权级），mhartid 是 M-mode 的 CSR，只有 M-mode 可以访问。

3.3 关键点：此时的 CPU 状态

_entry 执行时，CPU 处于以下状态：

  • 特权级：M-mode
  • 分页：关闭（物理地址 = 虚拟地址）
  • 中断：未配置
  • 其他寄存器：不确定（未初始化）

这就是为什么 _entry 的第一件事是设置 sp——没有栈就不能调用 C 函数。

四、源码精读：kernel/start.c（M-mode 初始化）

entry.S 设好栈后调用 start()。这个函数在 M-mode 执行，完成硬件初始化后切换到 S-mode。

4.1 全局变量

// entry.S 使用的栈空间，每个 CPU 一个 4KB 栈
__attribute__ ((aligned (16))) char stack0[4096 * NCPU];

// 时钟中断的 scratch 区域，每个 CPU 32 个 uint64
uint64 mscratch0[NCPU * 32];

// kernelvec.S 中的 M-mode 时钟中断处理函数
extern void timervec();

4.2 start() 函数详解

每个 CPU 核心都会独立执行这个函数。三个核心几乎同时运行到这里，但由于操作的都是各自的 CSR 寄存器（每个核心有自己的一套 CSR），所以不会冲突。

void start()
{

步骤 ①：配置 mret 的目标特权级

  // 将 MPP 设为 S-mode，mret 执行后进入 S-mode
  unsigned long x = r_mstatus();
  x &= ~MSTATUS_MPP_MASK;   // 清除 MPP 字段（bit 12:11）
  x |= MSTATUS_MPP_S;       // 设置 MPP = 01（S-mode）
  w_mstatus(x);

mstatus.MPP 告诉 mret 指令要跳转到哪个特权级。这里设置为 S-mode，因为 xv6 内核运行在 S-mode。

步骤 ②：配置 mret 的目标地址

  // mepc = main 函数的地址，mret 会跳转到这里
  w_mepc((uint64)main);

mret 的行为：跳转到 mepc 的地址 + 切换到 MPP 指定的特权级。

步骤 ③：关闭分页

  // satp = 0 → 关闭分页
  w_satp(0);

此时还没有创建页表。如果分页已开启但没有有效的页表，任何内存访问都会页错误。

步骤 ④：委托中断和异常

  // 将所有异常和中断委托给 S-mode 处理
  w_medeleg(0xffff);   // Exception DElegation
  w_mideleg(0xffff);   // Interrupt DElegation
  
  // 使能 S-mode 的三类中断
  w_sie(r_sie() | SIE_SEIE | SIE_STIE | SIE_SSIE);

不委托的话，用户态的 ecall（系统调用）会先陷入 M-mode，再转发到 S-mode，增加不必要的延迟。委托后直接到 S-mode。

步骤 ⑤：初始化时钟中断

  timerinit();

详见 4.3 节。

步骤 ⑥：保存 hartid 到 tp 寄存器

  int id = r_mhartid();
  w_tp(id);

mhartid 只能在 M-mode 读取。进入 S-mode 后，内核通过 r_tp() 获取当前 CPU 编号（cpuid() 函数就是这样实现的）。

步骤 ⑦：切换到 S-mode

  asm volatile("mret");
}

mret 执行后：

  1. 特权级从 M-mode 切换到 S-mode（因为 MPP = 01）
  2. PC 跳转到 mepc 的值（main 函数的地址）
  3. mstatus.MIE 被恢复为 mstatus.MPIE 的值

此后 CPU 永远不会回到 M-mode（时钟中断除外）。

4.3 timerinit() 函数详解

时钟中断是操作系统实现抢占式调度的基础。

void timerinit()
{
  int id = r_mhartid();

设置第一次时钟中断的触发时间：

  int interval = 1000000;  // 1,000,000 个时钟周期
  *(uint64*)CLINT_MTIMECMP(id) = *(uint64*)CLINT_MTIME + interval;
  • CLINT_MTIME：单调递增的时钟计数器（所有 CPU 共享）
  • CLINT_MTIMECMP(id)：每个 CPU 的比较寄存器
  • 当 MTIME >= MTIMECMP 时，触发时钟中断
  • 间隔约 1/10 秒（在 QEMU 中）

为 timervec 准备 scratch 数据：

  uint64 *scratch = &mscratch0[32 * id]; // 每个 CPU 有独立的 scratch 区域
  scratch[4] = CLINT_MTIMECMP(id);        // MTIMECMP 寄存器的地址
  scratch[5] = interval;                   // 中断间隔
  w_mscratch((uint64)scratch);             // 存入 mscratch CSR

timervec 是纯汇编代码，不能调用 C 函数，所以提前把需要的数据放在 scratch 中。

设置 M-mode trap 处理函数：

  w_mtvec((uint64)timervec);   // M-mode trap → 跳到 timervec
  w_mstatus(r_mstatus() | MSTATUS_MIE);  // 使能 M-mode 中断
  w_mie(r_mie() | MIE_MTIE);             // 使能 M-mode 时钟中断
}

4.4 timervec：时钟中断的 M-mode 处理

timervec 在 kernelvec.S 中定义（第 93-121 行），是整个系统中唯一在 M-mode 运行的中断处理程序：

timervec:
        # scratch[0..2] 是寄存器保存区
        # scratch[4] = CLINT_MTIMECMP 地址
        # scratch[5] = 中断间隔
        
        csrrw a0, mscratch, a0    # 交换 a0 和 mscratch
        sd a1, 0(a0)              # 保存 a1 到 scratch[0]
        sd a2, 8(a0)              # 保存 a2 到 scratch[1]
        sd a3, 16(a0)             # 保存 a3 到 scratch[2]

        # 设置下一次时钟中断
        ld a1, 32(a0)             # a1 = CLINT_MTIMECMP 地址
        ld a2, 40(a0)             # a2 = interval
        ld a3, 0(a1)              # a3 = 当前 MTIMECMP 值
        add a3, a3, a2            # a3 += interval
        sd a3, 0(a1)              # 写回新的 MTIMECMP

        # 触发 S-mode 软件中断（将时钟中断"转发"给内核）
        li a1, 2                  # bit 1 = SSIP
        csrw sip, a1              # 设置 sip.SSIP

        # 恢复寄存器
        ld a3, 16(a0)
        ld a2, 8(a0)
        ld a1, 0(a0)
        csrrw a0, mscratch, a0    # 恢复 a0

        mret                       # 返回被中断的代码

中断转发机制：

时钟到期 → M-mode timervec 执行
  ① 设置下一次定时器（MTIMECMP += interval）
  ② 写 sip.SSIP = 1（触发 S-mode 软件中断）
  ③ mret 返回

S-mode 检测到 SSIP 中断 → kerneltrap() / usertrap() 处理
  → 调用 yield() 让出 CPU

这是因为 RISC-V 不允许将 M-mode 时钟中断委托给 S-mode，所以必须用这种”M-mode 接收 → 转发为软件中断 → S-mode 处理”的方式。

五、源码精读：kernel/main.c（S-mode 初始化）

start() 的 mret 跳转到 main()，此时 CPU 已经在 S-mode。这是内核初始化的核心。

5.1 完整代码解析

#include "types.h"
#include "param.h"
#include "memlayout.h"
#include "riscv.h"
#include "defs.h"

volatile static int started = 0;   // 多核同步标志

volatile 告诉编译器不要优化对 started 的读取——其他 CPU 可能随时修改它。

5.2 CPU 0 的初始化序列

void main()
{
  if(cpuid() == 0){              // 只有 CPU 0 执行完整初始化

cpuid() 读取 tp 寄存器获取 hartid（在 start.c 中设置）。

阶段 1：控制台和输出（先让 printf 能工作）

    consoleinit();    // 初始化 UART 硬件，注册 console 设备的 read/write
    printfinit();     // 初始化 printf 的锁（pr.lock）
    printf("\n");
    printf("xv6 kernel is booting\n");
    printf("\n");
  • consoleinit()：调用 uartinit() 配置 UART 硬件，将 consoleread / consolewrite 注册到 devsw[CONSOLE]
  • printfinit()：初始化一个自旋锁 pr.lock，使多核打印不会混乱
  • 必须最先初始化，否则后续的 printf 和 panic 无法工作

阶段 2：内存管理

    kinit();          // 初始化物理页分配器
    kvminit();        // 创建内核页表
    kvminithart();    // 开启分页（写 satp 寄存器）
  • kinit()：将 end 到 PHYSTOP 之间的所有物理页加入空闲链表
  • kvminit()：分配一个页作为根页表，建立内核地址空间的映射（UART, PLIC, 内核代码/数据, TRAMPOLINE 等）
  • kvminithart()：将内核页表地址写入 satp，执行 sfence_vma() 刷新 TLB，正式开启分页

从此刻起，所有内存访问都经过页表翻译。 但由于内核页表使用直接映射（虚拟地址 = 物理地址），代码可以无缝继续执行。

阶段 3：进程子系统

    procinit();       // 初始化进程表（为每个进程分配内核栈）

procinit() 做了重要的工作：

void procinit(void) {
  struct proc *p;
  initlock(&pid_lock, "nextpid");
  for(p = proc; p < &proc[NPROC]; p++) {
    initlock(&p->lock, "proc");
    // 为每个可能的进程分配一个内核栈页
    char *pa = kalloc();                    // 分配物理页
    uint64 va = KSTACK((int)(p - proc));    // 计算虚拟地址
    kvmmap(va, (uint64)pa, PGSIZE, PTE_R | PTE_W);  // 映射到内核页表
    p->kstack = va;                         // 记录栈的虚拟地址
  }
  kvminithart();  // 重新加载 satp（因为页表变了）
}

关键设计：

  • 每个进程的内核栈都有独立的虚拟地址（靠近 TRAMPOLINE 之下）
  • 栈之间有 guard page（未映射的页），栈溢出会触发页错误而不是默默覆盖数据
TRAMPOLINE  ┌─────────────────┐
            │   TRAMPOLINE    │
            ├─────────────────┤
            │ Guard Page (×)  │  ← 未映射
            ├─────────────────┤ ← KSTACK(0)
            │ proc[0] 内核栈  │  4KB
            ├─────────────────┤
            │ Guard Page (×)  │
            ├─────────────────┤ ← KSTACK(1)
            │ proc[1] 内核栈  │
            ├─────────────────┤
            │      ...        │

阶段 4：Trap 和中断

    trapinit();       // 初始化 tickslock 锁
    trapinithart();   // 设置 stvec = kernelvec
    plicinit();       // 设置 PLIC 中断优先级
    plicinithart();   // 使能该 CPU 的 UART 和 VIRTIO 中断
  • trapinit()：仅初始化一个锁（tickslock），非常简单
  • trapinithart()：w_stvec((uint64)kernelvec) — 设置 S-mode 的 trap 处理函数。此后这个 CPU 上发生的任何 trap（中断/异常）都会跳到 kernelvec
  • plicinit()：在 PLIC 中设置 UART 和 VIRTIO 的中断优先级为 1（非零 = 使能）
  • plicinithart()：在 PLIC 中使能当前 CPU 接收 UART 和 VIRTIO 中断

阶段 5：文件系统基础结构

    binit();            // 初始化块缓存（buffer cache）双向链表
    iinit();            // 初始化 inode 缓存
    fileinit();         // 初始化全局文件表（ftable）
    virtio_disk_init(); // 初始化 virtio 磁盘驱动

这些函数主要是初始化锁和数据结构。注意 fsinit()（文件系统初始化）不在这里——它在第一个用户进程的 forkret() 中调用，因为 fsinit() 需要读磁盘（可能阻塞），不适合在 main() 中使用。

阶段 6：创建第一个用户进程

    userinit();         // 创建第一个用户进程

详见第六节。

阶段 7：通知其他 CPU

    __sync_synchronize();  // 内存屏障
    started = 1;           // 通知其他 CPU 可以继续了

__sync_synchronize() 是 GCC 内置的内存屏障（memory barrier），确保：

  1. started = 1 的写入不会被编译器/CPU 重排到前面的初始化之前
  2. 前面所有写入的数据对其他 CPU 立刻可见

5.3 其他 CPU 的初始化

  } else {
    while(started == 0)    // 自旋等待 CPU 0 完成初始化
      ;
    __sync_synchronize();  // 内存屏障
    printf("hart %d starting\n", cpuid());
    kvminithart();         // 开启分页（使用 CPU 0 创建的页表）
    trapinithart();        // 设置 stvec = kernelvec
    plicinithart();        // 使能设备中断
  }

从核心只需要三个初始化：

  • kvminithart()：将 satp 设为 kernel_pagetable（所有 CPU 共享同一个内核页表）
  • trapinithart()：设置自己的 stvec
  • plicinithart()：在 PLIC 中使能自己的中断

为什么其他 CPU 不需要 kinit(), procinit() 等？

这些函数初始化的是全局共享的数据结构（空闲链表、进程表等），只需要初始化一次。多个 CPU 通过锁来安全地共享这些数据。

5.4 进入调度循环

  scheduler();   // 永不返回
}

所有 CPU 最终都进入 scheduler() 的无限循环。main() 永远不会返回。

六、源码精读：userinit() — 创建第一个用户进程

6.1 完整代码解析

void userinit(void)
{
  struct proc *p;

  p = allocproc();         // ① 分配一个进程结构
  initproc = p;            // 记录为全局的 init 进程指针

allocproc() 做了以下工作：

  1. 在 proc[NPROC] 数组中找到一个 UNUSED 的槽位
  2. 分配 PID
  3. 分配一个物理页作为 trapframe
  4. 创建空的用户页表（映射了 TRAMPOLINE 和 TRAPFRAME）
  5. 设置 context.ra = forkret，context.sp = kstack + PGSIZE
  // ② 分配一个用户页，复制 initcode 的机器码进去
  uvminit(p->pagetable, initcode, sizeof(initcode));
  p->sz = PGSIZE;           // 进程大小 = 1 页

initcode[] 是硬编码在 proc.c 中的 52 字节机器码（从 user/initcode.S 编译而来）：

uchar initcode[] = {
  0x17, 0x05, 0x00, 0x00, 0x13, 0x05, 0x45, 0x02,
  0x97, 0x05, 0x00, 0x00, 0x93, 0x85, 0x35, 0x02,
  0x93, 0x08, 0x70, 0x00, 0x73, 0x00, 0x00, 0x00,
  // ... 共 52 字节
};

为什么不直接从磁盘加载 /init？

此时文件系统还没有初始化！fsinit() 在第一个进程被调度运行后才会调用。所以只能把一小段启动代码直接嵌入内核。

  // ③ 设置 trapframe，准备"返回"用户态
  p->trapframe->epc = 0;      // 用户程序从地址 0 开始执行
  p->trapframe->sp = PGSIZE;  // 用户栈在页的顶部

epc = 0 意味着 sret 后 CPU 会跳到虚拟地址 0，这正是 uvminit() 放置 initcode 的地方。

  // ④ 设置进程名和当前目录
  safestrcpy(p->name, "initcode", sizeof(p->name));
  p->cwd = namei("/");        // 当前目录 = 根目录

  // ⑤ 设置进程状态为 RUNNABLE
  p->state = RUNNABLE;

  release(&p->lock);
}

进程创建完成！但它还没有运行——它只是被标记为 RUNNABLE，等待 scheduler() 调度。

6.2 initcode 做了什么

user/initcode.S 的源码非常简单：

# 在用户空间运行的初始程序
# 执行 exec("/init", argv)

.globl start
start:
        la a0, init         # a0 = "/init" 字符串的地址
        la a1, argv         # a1 = argv 数组的地址
        li a7, SYS_exec     # a7 = 7（exec 的系统调用号）
        ecall               # 系统调用！

# exec 如果成功不会返回，如果失败则循环 exit
exit:
        li a7, SYS_exit     # a7 = 2（exit 的系统调用号）
        ecall
        jal exit

# 数据
init:
  .string "/init\0"         # 程序路径

.p2align 2
argv:
  .long init                # argv[0] = "/init"
  .long 0                   # argv[1] = NULL（终止符）

initcode 的唯一目的就是执行 exec("/init", argv)。exec() 会用 /init 程序的代码替换当前地址空间，所以 initcode 执行后就”消失”了。

6.3 第一次被调度：forkret()

当 scheduler() 第一次选中 initcode 进程时，会 swtch 到该进程的 context。由于 allocproc() 设置了 context.ra = forkret，所以第一次”调度”实际上是跳到 forkret()：

void forkret(void)
{
  static int first = 1;

  // 释放 scheduler 持有的进程锁
  release(&myproc()->lock);

  if (first) {
    first = 0;
    fsinit(ROOTDEV);    // ← 文件系统初始化！在这里完成
  }

  usertrapret();         // 返回用户空间
}

关键洞察：

  • fsinit(ROOTDEV) 在这里调用，因为它需要读磁盘（bread()），而读磁盘可能需要 sleep()，sleep() 需要一个进程上下文。main() 中没有进程上下文，所以不能在 main() 中调用
  • first 是 static 变量，确保 fsinit() 只被调用一次
  • usertrapret() 最终会 sret 到用户态，PC 跳转到 trapframe->epc（= 0），开始执行 initcode

6.4 从内核到用户态的第一次跳转

完整路径：

scheduler()
  ↓ swtch(&c->context, &p->context)
forkret()
  ↓ usertrapret()
    ↓ 设置 trapframe 中的内核信息
    ↓ w_stvec(uservec) — 切换到用户态 trap 处理
    ↓ w_satp(用户页表)
    ↓ 跳到 trampoline.S 中的 userret
      ↓ 恢复用户寄存器
      ↓ sret
用户态地址 0x0 → initcode 开始执行
  ↓ ecall (exec("/init"))
    ↓ 进入内核，执行 sys_exec()
    ↓ 加载 /init 程序
    ↓ sret
/init 程序开始执行
  ↓ open("console") → fd 0
  ↓ dup(0) → fd 1
  ↓ dup(0) → fd 2
  ↓ fork() + exec("sh")
shell 启动，显示 "$" 提示符

七、源码精读：scheduler() — 调度循环

7.1 代码解析

void scheduler(void)
{
  struct proc *p;
  struct cpu *c = mycpu();     // 获取当前 CPU 结构
  
  c->proc = 0;                // 当前没有运行进程
  for(;;){
    intr_on();                 // 开中断（避免死锁）
    
    int found = 0;
    for(p = proc; p < &proc[NPROC]; p++) {
      acquire(&p->lock);
      if(p->state == RUNNABLE) {
        // 找到一个可运行的进程
        p->state = RUNNING;        // 标记为运行中
        c->proc = p;               // 记录当前 CPU 运行的进程
        swtch(&c->context, &p->context);  // 切换到该进程

        // 进程让出 CPU 后回到这里
        c->proc = 0;
        found = 1;
      }
      release(&p->lock);
    }
    if(found == 0) {
      intr_on();
      asm volatile("wfi");     // 没有可运行进程，等待中断
    }
  }
}

7.2 调度器的工作方式

scheduler() 无限循环:
┌─────────────────────────────────────────────────────┐
│ ① 遍历 proc[0..63]，找 state == RUNNABLE 的进程     │
│ ② 找到了：                                          │
│    p->state = RUNNING                               │
│    swtch(&c->context, &p->context)                  │
│    ─── 现在 CPU 在执行进程 p 的代码 ───               │
│    ─── 进程 p 调用 yield()/exit()/sleep() ───        │
│    ─── swtch 回到这里 ───                            │
│    c->proc = 0                                      │
│    继续遍历                                          │
│ ③ 没找到（所有进程都在等待）：                        │
│    wfi（wait for interrupt，低功耗等待中断唤醒）     │
└─────────────────────────────────────────────────────┘

swtch 的本质：保存当前的 callee-saved 寄存器（ra, sp, s0-s11）到 c->context，然后从 p->context 恢复这些寄存器。由于恢复了 ra 和 sp，”返回”时实际上跳到了另一段代码（进程 p 之前让出 CPU 的位置）。

7.3 启动时的第一次调度

启动时 scheduler 第一次循环：

proc[0] = initcode 进程 (RUNNABLE)
proc[1..63] = UNUSED

scheduler:
  找到 proc[0]，state = RUNNABLE
  proc[0].state = RUNNING
  swtch(&c->context, &proc[0].context)
    ↓
  proc[0].context.ra = forkret  ← allocproc() 设置的
  proc[0].context.sp = kstack + PGSIZE
    ↓
  跳到 forkret()
    ↓
  fsinit(ROOTDEV)  ← 初始化文件系统
  usertrapret()    ← 返回用户态

十、思考题

  1. entry.S 中的所有 CPU 核心同时开始执行。它们调用 start() 时是否会发生竞争？

    不会。start() 中操作的都是每个 CPU 私有的 CSR 寄存器和私有的栈，没有共享数据的写入（全局变量 mscratch0 的写入位置按 hartid 分开）。所以多个核心同时执行 start() 是安全的。

  2. 如果把 main.c 中的 __sync_synchronize() 去掉会怎样？

    在弱内存序架构上，CPU 0 可能先把 started = 1 写入缓存，但之前的初始化数据还没有刷新到内存。其他 CPU 看到 started == 1 后开始运行，但可能读到未完成初始化的数据，导致不确定的崩溃。内存屏障确保所有在屏障之前的写入对其他 CPU 可见。

  3. 为什么 fsinit() 不能在 main() 中调用？

    fsinit() 需要读磁盘超级块（调用 bread()）。bread() 向 virtio 磁盘发送请求后会调用 sleep() 等待磁盘完成。但 main() 不在任何进程的上下文中（myproc() 返回 NULL），sleep() 需要一个进程结构来保存状态。所以必须在第一个进程被调度后（forkret 中）才能安全调用。

  4. scheduler() 中为什么要在循环开始时调用 intr_on()？

    进程在被调度前通过 acquire(&p->lock) 关闭了中断。当 swtch 返回到 scheduler 时，中断仍然是关的（因为还持有锁）。释放锁后中断恢复。但如果没有 RUNNABLE 进程，scheduler 会一直遍历，在 acquire/release 中反复开关中断。循环开头的 intr_on() 确保在寻找下一个进程时中断始终打开，这样设备中断（如磁盘完成）可以唤醒睡眠的进程。

  5. initcode 为什么是机器码硬编码在 C 数组中，而不是从文件系统加载？

    这是一个”鸡和蛋”的问题：加载文件需要文件系统 → 初始化文件系统需要磁盘 I/O → 磁盘 I/O 需要 sleep() → sleep() 需要进程上下文 → 进程需要代码来运行 → 代码在文件系统中。用硬编码的 initcode 打破了这个循环依赖。

  6. RISC-V 的 wfi 指令有什么作用？scheduler() 中为什么要用它？

    wfi（Wait For Interrupt）让 CPU 进入低功耗等待状态，直到下一个中断到来。当没有 RUNNABLE 进程时，CPU 空转循环会浪费电力和产生热量。wfi 让 CPU “休眠”到下一个中断（如时钟中断或设备中断）才醒来，减少资源浪费。

概念 要点
