OS11-Trap机制（内核态）与中断处理

更新日期:   2026-03-28

第 11 节：Trap 机制（内核态）与中断处理

学习目标：理解内核态 trap 的处理路径（与用户态的异同）；掌握 PLIC 中断控制器的工作原理；追踪时钟中断从 M-mode 到 S-mode 的转发过程；深入理解 UART 键盘输入中断的完整处理链路。

预计用时：3-4 小时

前置要求：完成第 9 节（用户态 Trap）和第 10 节（系统调用），理解 usertrap()、trapframe、stvec、sepc、scause 等概念

一、理论：内核态 Trap 与用户态 Trap 的比较

1.1 两种 Trap 入口的根本区别

回顾第 9 节：用户程序触发 trap（ecall、缺页异常、中断）时，硬件保存最少的上下文（sepc、scause、sstatus），然后跳转到 stvec 所指向的处理入口。

关键区别在于 stvec 指向的地址：

场景 stvec 指向 页表 流程
CPU 在用户态运行时 TRAMPOLINE 中的 uservec 用户页表 需要换页表，用 sscratch 交换 a0，保存完整 trapframe
CPU 在内核态运行时 kernelvec（内核直接地址） 内核页表（已是） 无需换页表，直接在当前内核栈上压栈保存寄存器

内核态 trap 更简单的原因：

  1. 无需切换页表：CPU 已经在内核页表下运行
  2. 无需 sscratch 技巧：不需要借助 sscratch 临时保存寄存器就能访问内核数据结构
  3. 无需跳转到 trampoline：kernelvec 是普通内核代码地址，可以直接使用

1.2 内核态 Trap 的设置时机

stvec 在以下时机被设置为 kernelvec：

CPU 上电 → start() → main() → trapinithart()
                                    ↓
                            w_stvec((uint64)kernelvec)
                            ←── 此后内核运行期间，stvec 始终指向 kernelvec

当 usertrap() 被调用时（即刚从用户态进入内核），第一件事就是把 stvec 切换回 kernelvec：

// kernel/trap.c 的 usertrap() 开头
void usertrap(void) {
  // 立即把 stvec 从 uservec 换回 kernelvec
  // 因为我们已经切换到内核页表，usertrap 本身处于内核态
  w_stvec((uint64)kernelvec);
  // ...
}

为什么 usertrap() 开头要做这个切换？

uservec 是用户页表中的 trampoline 页，只有用户态初次进入内核时才需要它。一旦我们在 usertrap() 里运行，就已经切换到了内核页表——如果这时再次发生 trap（比如内核代码触发了中断），就不应该再跳回 trampoline，而应该跳到 kernelvec。

1.3 内核态 Trap 的两种来源

内核在执行时可能触发两类 trap：

① 外设中断（External Interrupt）：

  • UART 有新字符输入（用户按下键盘）
  • 磁盘 I/O 完成（VirtIO 磁盘操作完成）
  • 时钟中断（通过软件中断转发，见 1.4 节）

② 内核异常（Exception）：

  • 极少发生（正常情况下内核代码不应触发缺页异常或非法指令）
  • 如果发生，kerneltrap() 会调用 panic()，打印错误信息并死机

xv6 的当前实现不支持内核态缺页异常处理（现代 Linux 内核支持，用于实现 copy_on_write 到内核缓冲区等功能）。

1.4 时钟中断的双级转发机制

时钟中断是调度器的心跳——每隔固定时间（xv6 中约 1/10 秒）触发一次，强制当前运行的进程让出 CPU。

RISC-V 的时钟中断有一个特殊之处：原始时钟中断只在 M-mode 发生（通过 CLINT 硬件），不能直接在 S-mode 处理。xv6 用双级转发解决：

CLINT 硬件产生 M-mode 时钟中断
  │
  ▼
kernelvec.S 中的 timervec（M-mode 向量）
  │ 1. 重新设置下一次时钟中断的时间（CLINT_MTIMECMP += interval）
  │ 2. 向 S-mode 发送"软件中断"信号（写 sip.SSIP = 1）
  │ 3. mret 返回被中断的 M-mode 代码（实际上 xv6 不在 M-mode 运行用户代码）
  ▼
S-mode 中的 CPU 感受到 SSIP（Supervisor Software Interrupt Pending）
  │
  ▼
kernelvec → kerneltrap() → devintr()
  │ scause == 0x8000000000000001（软件中断）
  │ → 调用 clockintr()，递增 ticks，wakeup(&ticks)
  │ → 清除 sip.SSIP（w_sip(r_sip() & ~2)）
  │ → 返回 2（表示"这是时钟中断"）
  ▼
kerneltrap() 收到 which_dev == 2 → yield()
  ▼
进程调度（可能切换到另一个进程）

为什么时钟中断要在 M-mode 处理后转发到 S-mode？

RISC-V 规范规定 CLINT（Core Local Interrupt Controller，核内中断控制器）的定时器中断只发到 M-mode。xv6 在 start.c 的 timerinit() 中设置了 M-mode 时钟中断，timervec 则将其转换为 S-mode 软件中断，使内核（S-mode）能感知到时钟的到来。这是 RISC-V 特权级架构的设计决策——M-mode 充当”安全监视器”角色，控制何时以及如何向 S-mode 暴露时钟事件。

二、源码精读：kernel/kernelvec.S——内核态 Trap 向量

2.1 kernelvec——内核态中断/异常入口

# kernel/kernelvec.S（节选）

.globl kerneltrap
.globl kernelvec
.align 4          # 4 字节对齐（stvec 的低 2 位用于模式，必须对齐）
kernelvec:
        # 在当前内核栈上开辟 256 字节的保存空间
        # 与 uservec 不同，这里无需切换页表，也无需 sscratch 技巧
        addi sp, sp, -256

        # 保存所有 32 个通用寄存器（caller-saved + callee-saved 全部保存）
        # 因为 kerneltrap() 是一个普通 C 函数调用，会遵守调用约定破坏 caller-saved
        # 所以 kernelvec 必须保存所有寄存器，而不仅仅是 callee-saved
        sd ra,  0(sp)
        sd sp,  8(sp)    # 保存的是当前栈指针（已减了 256）
        sd gp,  16(sp)
        sd tp,  24(sp)   # 注意：恢复时跳过 tp（见后）
        sd t0,  32(sp)
        # ... 保存所有 31 个寄存器，共 256 = 32 * 8 字节
        sd t6,  240(sp)

        # 调用 C 语言的 trap 处理函数
        call kerneltrap

        # kerneltrap() 返回后，恢复所有寄存器
        ld ra,  0(sp)
        ld sp,  8(sp)
        ld gp,  16(sp)
        # ！！不恢复 tp（tp = thread pointer，存放当前 hart ID）
        # 注释：// not this, in case we moved CPUs: ld tp, 24(sp)
        # 原因：yield() 可能切换 CPU，恢复旧的 tp 值会导致 cpuid() 返回错误
        ld t0,  32(sp)
        # ... 恢复其余寄存器
        ld t6,  240(sp)

        addi sp, sp, 256

        # 返回被中断的内核代码
        sret

与 uservec 的关键对比：

方面 uservec kernelvec
页表切换 必须（用户→内核页表） 不需要（已是内核页表）
sscratch 用来临时换 a0 指向 trapframe 不需要
保存目标 trapframe（进程的 trapframe 结构） 当前内核栈（直接 addi sp, sp, -256）
恢复 tp 从 trapframe 的 kernel_hartid 字段恢复 **不恢复 tp**（防止 CPU 迁移问题）
后续跳转 跳入 usertrap() 调用 kerneltrap()

为什么不恢复 tp？

tp 寄存器存放当前 hart（CPU）的 ID，cpuid() 函数直接读取 tp返回当前 CPU 编号。kerneltrap() 可能调用 yield()，而 yield() 会切换到调度器，进程可能被迁移到另一个 CPU 上恢复执行。如果此时恢复 tp 为中断前的旧 CPU ID，cpuid() 就会返回错误的 CPU 编号，导致严重的并发 bug（如使用错误的每 CPU 数据）。

2.2 timervec——M-mode 时钟中断处理

# kernel/kernelvec.S（后半段）

.globl timervec
.align 4
timervec:
        # start.c 设置的 mscratch 指向的内存布局：
        # scratch[0,8,16] : 3 个寄存器保存槽
        # scratch[32]     : CLINT_MTIMECMP 寄存器的地址
        # scratch[40]     : 期望的中断间隔（cycle 数）

        # 用 mscratch 交换 a0，a0 现在指向 scratch 数组
        csrrw a0, mscratch, a0

        # 临时保存 a1, a2, a3
        sd a1, 0(a0)
        sd a2, 8(a0)
        sd a3, 16(a0)

        # 设置下一次时钟中断时间：MTIMECMP += interval
        ld a1, 32(a0)     # a1 = CLINT_MTIMECMP 地址
        ld a2, 40(a0)     # a2 = interval（约 100 万 cycle ≈ 0.1 秒）
        ld a3, 0(a1)      # a3 = 当前 MTIMECMP 值
        add a3, a3, a2    # a3 += interval（下一次中断时间）
        sd a3, 0(a1)      # 写回 MTIMECMP

        # 向 S-mode 注入软件中断信号
        li a1, 2          # 2 = SSIP（Supervisor Software Interrupt Pending）位
        csrw sip, a1      # 设置 sip.SSIP = 1，触发 S-mode 软件中断

        # 恢复 a1, a2, a3
        ld a3, 16(a0)
        ld a2, 8(a0)
        ld a1, 0(a0)
        csrrw a0, mscratch, a0  # 恢复 a0

        # M-mode 中断返回（回到被中断的 M-mode 代码，实际是 S-mode 代码）
        mret

csrw sip, a1 的作用：

sip（Supervisor Interrupt Pending）寄存器的 bit 1 是 SSIP（Supervisor Software Interrupt Pending）。当 M-mode 设置 sip.SSIP = 1 后，如果 S-mode 的 sstatus.SIE（全局中断使能）和 sie.SSIE（软件中断使能）均为 1，CPU 在 mret 返回 S-mode 后会立即感知到待处理的软件中断，然后跳转到 stvec（即 kernelvec）处理。

**start.c 中的 timerinit()**：

// kernel/start.c
void timerinit() {
  int id = r_mhartid();
  int interval = 1000000;   // ~0.1 秒（QEMU 约 10MHz 等效）
  
  // 初始化下一次中断时间
  *(uint64*)CLINT_MTIMECMP(id) = *(uint64*)CLINT_MTIME + interval;

  // 设置 scratch 数组（供 timervec 使用）
  uint64 *scratch = &mscratch0[32 * id];
  scratch[4] = CLINT_MTIMECMP(id);   // scratch[32] in bytes = scratch[4] as uint64
  scratch[5] = interval;              // scratch[40] in bytes = scratch[5] as uint64
  w_mscratch((uint64)scratch);

  // 设置 M-mode trap 向量为 timervec
  w_mtvec((uint64)timervec);
  
  // 开启 M-mode 全局中断和时钟中断
  w_mstatus(r_mstatus() | MSTATUS_MIE);
  w_mie(r_mie() | MIE_MTIE);
}

三、源码精读：kernel/trap.c——内核态 Trap 处理

3.1 trapinithart()——每 CPU 的初始化

// 在 trapinithart() 中设置内核态 trap 向量
void
trapinithart(void)
{
  w_stvec((uint64)kernelvec);
  // 把 stvec 设置为 kernelvec 的物理地址
  // 这是 S-mode 中断/异常向量（直接模式，stvec 低 2 位 = 0b00）
}

trapinithart() 在 main() 的每个 CPU 初始化路径中都有调用（CPU 0 和其他 CPU 都调用），确保每个核心的 stvec 都正确指向 kernelvec。

3.2 kerneltrap()——内核态 Trap 的 C 处理函数

// kernel/trap.c

void
kerneltrap()
{
  int which_dev = 0;

  // ① 保存当前关键 CSR 的值（因为 yield() 后可能换了 CPU，这些值会改变）
  uint64 sepc    = r_sepc();
  uint64 sstatus = r_sstatus();
  uint64 scause  = r_scause();

  // ② 合法性检验：kerneltrap 只处理来自 S-mode 的 trap
  if((sstatus & SSTATUS_SPP) == 0)
    panic("kerneltrap: not from supervisor mode");

  // 进入 kerneltrap 时中断应该关闭（避免嵌套 trap 复杂化处理）
  if(intr_get() != 0)
    panic("kerneltrap: interrupts enabled");

  // ③ 调用 devintr() 处理外设中断
  if((which_dev = devintr()) == 0){
    // devintr 返回 0 表示无法识别的 trap（异常）
    printf("scause %p\n", scause);
    printf("sepc=%p stval=%p\n", r_sepc(), r_stval());
    panic("kerneltrap");   // 内核异常 → panic（正常内核不应触发）
  }

  // ④ 若为时钟中断（devintr 返回 2）且当前有运行中的进程，则 yield
  if(which_dev == 2 && myproc() != 0 && myproc()->state == RUNNING)
    yield();

  // ⑤ 恢复在 ① 中保存的 CSR 值
  // 原因：yield() 会切换进程，sret 后需要返回到正确的 sepc 和 sstatus
  // 如果不恢复，yield() 后的 sepc/sstatus 可能变成另一个进程的值
  w_sepc(sepc);
  w_sstatus(sstatus);
}

为什么要在 yield() 前后保存/恢复 sepc 和 sstatus？

yield() 调用 sched()，sched() 调用 swtch() 切换到调度器上下文，进而可能切换到别的进程。别的进程运行时可能也会触发 trap，修改 sepc 和 sstatus。当控制权通过调度器再次返回到当前进程时，kernelvec.S 的 sret 指令会使用 sepc 和 sstatus 来恢复被中断的内核代码——如果这两个值被破坏，内核就会跳到错误地址，导致崩溃。

3.3 clockintr()——时钟 Tick 计数

// kernel/trap.c

void
clockintr()
{
  acquire(&tickslock);
  ticks++;                  // 递增全局 tick 计数（系统启动以来的时钟次数）
  wakeup(&ticks);           // 唤醒所有在 ticks 上睡眠的进程（如 sys_sleep()）
  release(&tickslock);
}

ticks 是一个全局变量，tickslock 是保护它的自旋锁。每次时钟中断都会调用 clockintr()：

  • **递增 ticks**：系统时钟的刻度（sys_uptime() 返回这个值）
  • **wakeup(&ticks)**：通知所有等待 sleep N ticks 的进程重新检查条件（第 10 节 sys_sleep() 中已分析）

3.4 devintr()——设备中断识别与分发

// kernel/trap.c

// 返回值：
//   2  = 时钟中断（软件中断转发的）
//   1  = 外设中断（PLIC：UART、VirtIO 等）
//   0  = 无法识别（可能是异常）
int
devintr()
{
  uint64 scause = r_scause();

  // ——————————————— 情形 1：S-mode 外设中断（通过 PLIC）———————————————
  // scause 最高位 = 1（中断类型），低 8 位 = 9（S-mode 外设中断代码）
  if((scause & 0x8000000000000000L) && (scause & 0xff) == 9) {

    // 向 PLIC 查询是哪个设备产生了中断
    int irq = plic_claim();

    if(irq == UART0_IRQ) {
      uartintr();           // UART 输入中断：读字符，送入 console 缓冲
    } else if(irq == VIRTIO0_IRQ) {
      virtio_disk_intr();   // VirtIO 磁盘中断：磁盘 I/O 完成，唤醒等待的进程
    } else if(irq) {
      printf("unexpected interrupt irq=%d\n", irq);
    }

    // 通知 PLIC 中断已处理（允许该设备再次中断）
    if(irq)
      plic_complete(irq);

    return 1;   // 返回 1 表示"外设中断，已处理"

  // ——————————————— 情形 2：S-mode 软件中断（由 timervec 注入）———————————————
  } else if(scause == 0x8000000000000001L) {
    // 最高位 = 1（中断）+ 低位 = 1（软件中断编号）

    if(cpuid() == 0) {
      clockintr();   // 只让 CPU 0 递增 ticks，避免多核重复计数
    }

    // 清除 sip.SSIP 位，否则 CPU 会反复处理这个"待处理中断"
    w_sip(r_sip() & ~2);

    return 2;   // 返回 2 表示"时钟中断"

  } else {
    return 0;   // 无法识别
  }
}

scause 的编码规则（RISC-V 规范）：

scause 寄存器（64 位）
┌────┬────────────────────────────────┐
│ 63 │            低 63 位            │
└────┴────────────────────────────────┘
  │
  ├── 0 = 异常（exception）：低位 = 异常代码
  │     0: 指令地址对齐错误
  │     2: 非法指令
  │     8: 用户态 ecall
  │     13: 加载页错误（Load Page Fault）
  │     15: 存储页错误（Store Page Fault）
  │
  └── 1 = 中断（interrupt）：低位 = 中断代码
        1: S-mode 软件中断（SSIP）      ← timervec 注入
        5: S-mode 时钟中断              （xv6 不用）
        9: S-mode 外设中断（SEIP）      ← PLIC 产生

四、源码精读：kernel/plic.c——平台级中断控制器

4.1 PLIC 是什么？

PLIC（Platform-Level Interrupt Controller，平台级中断控制器）是 RISC-V 系统中协调外设中断的硬件模块。外设（UART、磁盘、网卡等）通过中断线连接到 PLIC，PLIC 负责：

  1. 仲裁（Arbitration）：多个外设同时中断时，按优先级选择一个发给 CPU
  2. 路由（Routing）：决定把中断发给哪个 CPU 的哪个特权级
  3. 确认协议（Claim/Complete）：CPU 认领中断（claim）→ 处理 → 完成通知（complete）

xv6 的 PLIC 物理地址从 0x0C000000 开始（QEMU virt 平台）。

QEMU virt 平台上的中断设备：

      UART0（IRQ 10）  ←── 用户键盘输入
              │
      VIRTIO0（IRQ 1） ←── 磁盘操作
              │
           PLIC
     0x0C000000
              │
         ┌────┴────┐
     CPU hart 0  CPU hart 1 ...（每个 hart 有独立的 PLIC 接口）

4.2 PLIC 的内存映射寄存器

kernel/memlayout.h 中定义了 PLIC 的寄存器地址：

#define PLIC           0x0c000000L
#define PLIC_PRIORITY  (PLIC + 0x0)       // 每个 IRQ 的优先级（4 字节/IRQ）
#define PLIC_PENDING   (PLIC + 0x1000)    // 待处理中断位图

// 每个 hart 的 S-mode 相关寄存器（offset 按 hart 编号计算）
#define PLIC_SENABLE(hart)   (PLIC + 0x2080 + (hart)*0x100)   // 使能位图
#define PLIC_SPRIORITY(hart) (PLIC + 0x201000 + (hart)*0x2000) // 优先级阈值
#define PLIC_SCLAIM(hart)    (PLIC + 0x201004 + (hart)*0x2000) // 认领/完成

PLIC 工作流程：

外设产生中断
    │
    ▼
PLIC 检查该 IRQ 的优先级 > PLIC_SPRIORITY（hart）的阈值？
并且 PLIC_SENABLE(hart) 中该 IRQ 的使能位 = 1？
    │
    ├── 否 → 中断被屏蔽
    │
    └── 是 → 向该 hart 发送外设中断信号（SEIP）
                  │
                  ▼
              CPU 感知 SEIP → 跳转到 stvec（kernelvec）
                  │
                  ▼
              kerneltrap() → devintr() → plic_claim()
                  │ 读取 PLIC_SCLAIM(hart) → 获得 IRQ 号
                  │ 处理对应设备
                  ▼
              plic_complete(irq)
                  │ 写 PLIC_SCLAIM(hart) = irq → 通知 PLIC 完成
                  ▼
              PLIC 允许该设备再次发送中断

4.3 plicinit()——全局 PLIC 初始化

// kernel/plic.c

void
plicinit(void)
{
  // 设置 UART0（IRQ 10）的优先级为 1（非零即可，0 表示禁用）
  *(uint32*)(PLIC + UART0_IRQ*4) = 1;

  // 设置 VIRTIO0（IRQ 1）的优先级为 1
  *(uint32*)(PLIC + VIRTIO0_IRQ*4) = 1;
}

PLIC_PRIORITY 寄存器组是一个数组，下标为 IRQ 号，每项 4 字节。设置优先级 > 0 才能使对应 IRQ 生效（0 = 完全禁用该中断源）。plicinit() 只由 CPU 0 调用一次，完成全局配置。

4.4 plicinithart()——每 CPU 的 PLIC 初始化

// kernel/plic.c

void
plicinithart(void)
{
  int hart = cpuid();

  // 使能此 hart 的 S-mode 下 UART0 和 VIRTIO0 中断
  // 写入一个 32 位位图，IRQ 号对应的位置 1 = 使能
  *(uint32*)PLIC_SENABLE(hart) = (1 << UART0_IRQ) | (1 << VIRTIO0_IRQ);
  //                              (1 << 10)       | (1 << 1)

  // 设置此 hart 的 S-mode 优先级阈值为 0（接受所有优先级 > 0 的中断）
  *(uint32*)PLIC_SPRIORITY(hart) = 0;
}

plicinithart() 在每个 CPU 上都调用（main() 中 plicinithart() 在所有 CPU 的初始化路径上），使得多核系统中的每个 CPU 都能接收 UART 和磁盘中断（由 PLIC 仲裁分配给某一个 CPU 处理）。

4.5 plic_claim() 和 plic_complete()

// 向 PLIC 查询应处理哪个中断，返回 IRQ 号（0 表示无中断）
int
plic_claim(void)
{
  int hart = cpuid();
  int irq = *(uint32*)PLIC_SCLAIM(hart);  // 读取 CLAIM 寄存器 → 获得 IRQ 号
  return irq;
}

// 告知 PLIC 中断处理完成（写 COMPLETE 寄存器，与 CLAIM 共用同一地址）
void
plic_complete(int irq)
{
  int hart = cpuid();
  *(uint32*)PLIC_SCLAIM(hart) = irq;  // 写入 IRQ 号 = COMPLETE 操作
}

PLIC_SCLAIM 读写语义不同：

  • 读取 PLIC_SCLAIM(hart)：CLAIM 操作，PLIC 返回当前最高优先级的待处理 IRQ（同时内部标记为”已认领”，不会发给其他 CPU）
  • 写入 PLIC_SCLAIM(hart) = irq：COMPLETE 操作，通知 PLIC 该 IRQ 已处理完毕，可以再次触发

这个设计防止同一中断被多个 CPU 重复处理：一旦 CPU A 认领（read CLAIM）了 IRQ 10，PLIC 就不会把 IRQ 10 再发给 CPU B，直到 CPU A 完成处理（write COMPLETE）。

五、源码精读：UART 中断完整处理链路

5.1 中断产生：用户按下键盘

  1. 用户按下一个键（例如 l）
  2. QEMU 模拟 UART（16550A 芯片）：字符存入 RHR（Receive Holding Register）寄存器
  3. UART 硬件通过中断线通知 PLIC：UART0_IRQ（IRQ 10）有中断待处理
  4. PLIC 检查 hart 0 的使能和优先级，决定向 hart 0 发送 S-mode 外设中断（SEIP = 1）

5.2 CPU 感知中断：kernelvec

CPU 执行内核代码（如 scheduler()）时，感知到 SEIP = 1
    │
    ▼
硬件压栈（自动）：sepc = 被中断地址，scause = 0x8000000000000009（外设中断）
sstatus.SPP = 1（来自 S-mode），sstatus.SIE = 0（中断被自动关闭）
    │
    ▼
跳转到 stvec（= kernelvec）

5.5 uartintr()——UART 中断处理函数

// kernel/uart.c
void
uartintr(void)
{
  // 循环读取所有已到达的字符（UART 可能缓冲了多个字符）
  while(1) {
    int c = uartgetc();   // 读 UART 的 RHR 寄存器
    if(c == -1)
      break;              // 没有更多字符了
    consoleintr(c);       // 将字符送入 console 输入缓冲
  }

  // 如果发送缓冲区有数据，趁机发送（复用中断，TX 也顺带处理）
  acquire(&uart_tx_lock);
  uartstart();
  release(&uart_tx_lock);
}

**uartgetc()**：

int
uartgetc(void)
{
  if(ReadReg(LSR) & 0x01) {  // LSR.RX_READY 位检查
    return ReadReg(RHR);     // 读取 RHR（接收保持寄存器）= 收到的字符
  } else {
    return -1;
  }
}

5.6 consoleintr()——字符进入 Console 缓冲

// kernel/console.c（简化版逻辑）
void
consoleintr(int c)
{
  acquire(&cons.lock);
  
  switch(c) {
  case C('P'):    // Ctrl+P：打印进程列表
    procdump();
    break;
  case C('U'):    // Ctrl+U：删除整行
    // 退格处理...
    break;
  case '\n':      // 回车：一行输入完成，唤醒等待读取的进程
  default:
    if(c != 0 && cons.e - cons.r < INPUT_BUF) {
      c = (c == '\r') ? '\n' : c;
      cons.buf[cons.e++ % INPUT_BUF] = c;  // 字符入队
      // ...
    }
    break;
  }
  
  // 如果收到换行符，唤醒在 consoleread() 上睡眠的用户进程
  if(c == '\n' || ...)
    wakeup(&cons.r);
  
  release(&cons.lock);
}

// 回到 devintr()：
plic_complete(irq);  // 告知 PLIC：IRQ 10 处理完成，可再次触发

八、思考题

  1. kernelvec 为什么要保存所有 32 个寄存器，而 swtch.S（第 8 节）只保存 14 个 callee-saved 寄存器？

    swtch() 是一个普通 C 函数调用，调用者（sched()）按 C 调用约定负责在调用前保存 caller-saved 寄存器；swtch() 只需保存 callee-saved（ra, sp, s0-s11）即可。kernelvec 是硬件 trap 入口，硬件不帮你保存任何通用寄存器（只保存 sepc、scause、sstatus 等 CSR），因此软件必须保存全部 32 个寄存器，否则 kerneltrap() 这个 C 函数的执行会破坏 caller-saved 寄存器，trap 返回后被中断的内核代码会发现寄存器值被改变，导致错误。

  2. devintr() 只让 CPU 0 执行 clockintr()，其他 CPU 收到软件中断时跳过 clockintr()，但仍然 yield。为什么这样设计？

    如果每个 CPU 都执行 clockintr()，ticks++ 会被 NCPU 倍速执行（即使有锁也只是串行化，每次时钟实际增加了 NCPU 个 tick），导致 sys_sleep() 等依赖 ticks 的逻辑时间跑快。只让 CPU 0 递增 ticks 保证时钟精度。但**所有 CPU 都执行 yield()**，这是正确的——每个 CPU 上的当前进程都应因时钟中断而让出（否则某个 CPU 上运行的进程可以无限不被抢占）。

  3. 为什么 kerneltrap() 的注释要求进入时中断必须是关闭的（intr_get() != 0 → panic）？

    如果允许内核 trap 处理期间嵌套发生另一个 trap（中断重入），kernelvec 会用同一个内核栈保存第二次 trap 的寄存器——但第一次 trap 的栈帧还在，会发生栈布局混乱。更严重的是，如果 kerneltrap() 正在处理某个持有锁的路径，重入的 trap 如果也要获取同一把锁就会死锁。RISC-V 硬件在 trap 时自动将 sstatus.SIE 清零（关中断），xv6 不手动重开，因此 kerneltrap() 始终在中断关闭的状态下运行，避免了上述问题。

  4. plic_claim() 读 PLIC_SCLAIM(hart) 得到 IRQ 号后，如果对应中断还未处理完成，PLIC 会不会把同一个 IRQ 再发给另一个 CPU？

    不会。PLIC 的 Claim 操作具有原子性——一旦某个 hart 通过读取 CLAIM 寄存器”认领”了一个 IRQ，PLIC 就会内部标记该 IRQ”已被认领”，不会再把它分发给其他 hart，直到该 hart 写 COMPLETE 为止。这就是 claim/complete 两步协议存在的意义：保证每个中断只被一个 CPU 处理一次。

  5. 如果 UART 同时有输入中断（收到字符）和输出中断（发送完成，可继续发送），uartintr() 如何同时处理两者？

    uartintr() 的设计很巧妙：先用 while 循环调用 uartgetc() 处理所有待处理的输入字符，再调用 uartstart() 处理输出缓冲中待发送的字符。UART 硬件在中断时，可能同时设置了 RX（接收就绪）和 TX（发送空闲）两个中断标志，uartintr() 的这种写法在一次中断处理中同时处理了两类事件——“一次中断，批量处理”，减少了中断处理的开销。

九、本节小结

概念 要点
stvec 的值 用户态时 → uservec（trampoline）；内核态时 → kernelvec
kernelvec vs uservec 无需换页表；保存到内核栈（而非 trapframe）；不用 sscratch
tp 不恢复 yield 可能迁移 CPU，恢复旧 tp 会导致 cpuid() 错误
时钟中断路径 CLINT → M-mode timervec → sip.SSIP = 1 → S-mode kernelvec → kerneltrap → devintr → clockintr → yield
devintr() 返回值 2 = 时钟中断；1 = 外设中断；0 = 未识别（→ panic）
PLIC 工作原理 外设 → 发 IRQ → PLIC 仲裁 → 发 SEIP → CPU claim → 处理 → complete
plic_claim() / plic_complete() 同一寄存器地址，读 = claim，写 = complete；防止重复处理
clockintr() 只在 CPU 0 执行（防止多倍计 tick）；所有 CPU 都 yield
UART 中断路径 键盘 → UART → PLIC → kernelvec → kerneltrap → devintr → uartintr → consoleintr → 字符入缓冲 → wakeup
kerneltrap() 的 sepc/sstatus 保存 yield 后可能切换 CPU，必须恢复原 sepc/sstatus 以便 sret 返回正确地址
