第 6 节：进程数据结构与生命周期

学习目标：深入理解 xv6 进程的表示方式、状态转换机制，掌握进程从创建到销毁的完整资源管理流程。

预计用时：3-4 小时

前置要求：完成第 5 节，理解虚拟内存与页表（pagetable_t、trapframe、KSTACK）

一、理论：进程是什么？

1.1 进程 = 地址空间 + 执行状态 + 内核资源

Unix 哲学对进程的三重定义：

┌─────────────────────────────────────────────────────────┐
│                       进程                               │
│                                                         │
│  ① 地址空间          ② 执行状态          ③ 内核资源     │
│  ──────────          ──────────          ──────────     │
│  用户页表            CPU 寄存器           打开的文件      │
│  代码 / 数据         程序计数器（pc）      当前目录        │
│  栈 / 堆             栈指针（sp）          信号（xv6未实现）│
│  TRAPFRAME           trap 上下文          ...            │
│  TRAMPOLINE          内核栈               ...            │
└─────────────────────────────────────────────────────────┘

隔离性：每个进程认为自己独占整台机器——自己的地址空间（虚拟内存），自己的 CPU（时间片），自己的文件描述符表。

并发性：多个进程”同时”运行，依靠调度器在它们之间分时切换 CPU（或在多核上真正并行）。

1.2 五种进程状态

enum procstate { UNUSED, SLEEPING, RUNNABLE, RUNNING, ZOMBIE };

各状态详解：

状态 含义 CPU 是否使用 内存是否占用
UNUSED 进程表的空槽位 否 否
RUNNABLE 准备好运行，等待调度器选中 否（等待） 是
RUNNING 正在 CPU 上执行 是 是
SLEEPING 等待事件（I/O 完成、管道数据等） 否（挂起） 是
ZOMBIE 已调用 exit()，保留退出状态等待父进程 否 部分（struct proc 未释放）

ZOMBIE 状态存在的原因：exit() 后内核需要保留进程的退出状态码（p->xstate）和 PID，直到父进程调用 wait() 来读取。父进程用 wait() 确认子进程已终止时，才将 struct proc 标记为 UNUSED。如果没有 ZOMBIE，父进程就无法获取子进程的退出状态。

1.3 进程表：全局数组 proc[NPROC]

// kernel/param.h
#define NPROC 64   // 系统最多同时存在 64 个进程

// kernel/proc.c
struct proc proc[NPROC];  // 进程表，静态分配

设计特点：

  • 静态数组：在编译时确定大小，无需动态分配进程表本身
  • 线性扫描：allocproc() 通过遍历数组找空槽位，O(NPROC) = O(64)
  • 直接索引：proc[i] 直接得到第 i 个进程的数据
  • 每个槽位有独立的锁：p->lock 保护进程状态，允许多核并发操作不同进程

为什么上限只有 64？xv6 是教学操作系统，64 足够演示概念。Linux 的默认上限是 32768（通过 sysctl kernel.pid_max 可调）。

二、源码精读：kernel/proc.h——完整 106 行

proc.h 定义了进程管理的所有核心数据结构。

2.1 struct context——内核上下文切换的保存现场

// Saved registers for kernel context switches.
struct context {
  uint64 ra;   // 返回地址（Return Address）
  uint64 sp;   // 栈指针（Stack Pointer）

  // callee-saved 寄存器
  uint64 s0;
  uint64 s1;
  uint64 s2;
  uint64 s3;
  uint64 s4;
  uint64 s5;
  uint64 s6;
  uint64 s7;
  uint64 s8;
  uint64 s9;
  uint64 s10;
  uint64 s11;
};

struct context 只保存 callee-saved 寄存器（ra, sp, s0-s11），共 14 个。

为什么只需要保存这 14 个？

RISC-V ABI 规定：

  • Callee-saved（s0-s11, sp, ra）：被调用函数负责保存和恢复。即函数返回时，这些寄存器的值与调用时相同。
  • Caller-saved（a0-a7, t0-t6）：调用者负责保存。函数可以随意修改它们。

上下文切换发生在 swtch() 汇编函数调用时：

进程 A 调用 swtch() → swtch 是一个普通函数调用
→ 编译器保证在 swtch 调用前保存好 caller-saved 寄存器（放在 A 的内核栈上）
→ swtch 内部只需保存/恢复 callee-saved 寄存器
→ 切换到进程 B 时，B 的 callee-saved 寄存器从 B 的 context 恢复
→ B 从 swtch 返回，B 的内核栈上原有的 caller-saved 寄存器自动可用

struct context 存在两个地方：

  • struct proc.context：每个进程的内核执行上下文
  • struct cpu.context：调度器的上下文（每个 CPU 一个）

每次进程通过 sched() 让出 CPU 时，swtch(&p->context, &mycpu()->context) 将进程上下文保存到 p->context，切换到调度器的上下文。

与 struct trapframe 的区别：

struct context struct trapframe
保存时机 内核→调度器的切换（swtch 调用） 用户态进入内核（ecall/中断）
保存内容 callee-saved（14个） 全部 32 个用户寄存器
用途 在内核线程间切换 从内核返回用户态时恢复
存储位置 struct proc 内部字段 独立的物理页（TRAPFRAME）

2.2 struct cpu——每个 CPU 核心的状态

// Per-CPU state.
struct cpu {
  struct proc *proc;    // 当前在此 CPU 上运行的进程（或 NULL）
  struct context context; // 调度器的内核上下文（swtch() 到这里进入 scheduler）
  int noff;             // push_off() 调用的嵌套深度（关中断的层数）
  int intena;           // push_off() 之前中断是否开启
};

extern struct cpu cpus[NCPU];  // 每个 CPU 一个，NCPU=8

noff 和 intena 的作用：

xv6 用 push_off()/pop_off() 来管理中断使能——每次 acquire() 自旋锁时调用 push_off()（关中断），release() 时调用 pop_off()（可能恢复中断）。

由于锁可以嵌套（锁 A 内部再获取锁 B），noff 记录嵌套深度：

  • push_off()：noff++
  • pop_off()：noff--，只有当 noff==0 且原来中断开启时才真正重新开中断

为什么关中断才能获取锁？ 已在第 4 节详细解释——持有锁期间不能被中断，防止中断处理程序也去获取同一把锁（死锁）。

2.3 struct trapframe——保存用户态的完整寄存器现场

// per-process data for the trap handling code in trampoline.S.
// sits in a page by itself just under the trampoline page in the user page table.
// the sscratch register points here.
struct trapframe {
  /*   0 */ uint64 kernel_satp;   // 内核页表（进入内核后使用）
  /*   8 */ uint64 kernel_sp;     // 进程的内核栈顶
  /*  16 */ uint64 kernel_trap;   // usertrap() 的地址
  /*  24 */ uint64 epc;           // 保存的用户程序计数器（回到用户态从这里继续）
  /*  32 */ uint64 kernel_hartid; // 保存的内核 tp 寄存器（hart ID）
  //  以下是全部 32 个 RISC-V 通用寄存器
  /*  40 */ uint64 ra;
  /*  48 */ uint64 sp;
  /*  56 */ uint64 gp;
  /*  64 */ uint64 tp;
  /*  72 */ uint64 t0;
  /*  80 */ uint64 t1;
  /*  88 */ uint64 t2;
  /*  96 */ uint64 s0;
  /* 104 */ uint64 s1;
  /* 112 */ uint64 a0;   // 系统调用的第 1 个参数 / 返回值
  /* 120 */ uint64 a1;
  /* ... */
  /* 168 */ uint64 a7;   // 系统调用号
  /* 176 */ uint64 s2;
  /* ... */
  /* 280 */ uint64 t6;
};

前 5 个字段（内核信息）的特殊意义：

这 5 个字段不是用户寄存器，而是 trampoline.S 需要的内核引导信息：

字段 填充时机 用途
kernel_satp usertrapret() trap 进入时切换到内核页表
kernel_sp usertrapret() 进入内核后使用进程的内核栈
kernel_trap usertrapret() 跳转到 usertrap() 处理 trap
epc trampoline.S（从 sepc 读取） 保存用户 PC，返回时恢复
kernel_hartid usertrapret() 保存 tp 寄存器（内核用 tp 存 hart ID）

为什么 trapframe 需要独占一整个物理页（4KB）？

  • struct trapframe 只有 288 字节（5个内核字段 + 32个寄存器 × 8字节）
  • 但它独占一页（映射在用户页表的 TRAPFRAME 地址）
  • 原因：trampoline.S 进入内核时，CPU 还在用户页表，必须通过虚拟地址 TRAPFRAME 访问它
  • 如果与其他数据共享一页，用户可能通过访问同一页的其他字节来破坏 trapframe
  • 独占一页 = 明确的访问控制边界（PTE_R|PTE_W，无 PTE_U）

2.4 enum procstate 和 struct proc——进程的完整定义

enum procstate { UNUSED, SLEEPING, RUNNABLE, RUNNING, ZOMBIE };

// Per-process state
struct proc {
  struct spinlock lock;

  // 持有 p->lock 时才能访问以下字段：
  enum procstate state;        // 进程状态
  struct proc *parent;         // 父进程指针
  void *chan;                  // 非零时：正在等待的事件（睡眠通道）
  int killed;                  // 非零时：进程被标记为待杀死
  int xstate;                  // 退出状态码（返回给 wait()）
  int pid;                     // 进程 ID

  // 私有字段（无需持有 p->lock）：
  uint64 kstack;               // 进程内核栈的虚拟地址（KSTACK(i)）
  uint64 sz;                   // 用户内存大小（字节）
  pagetable_t pagetable;       // 用户页表
  struct trapframe *trapframe; // 用于 trampoline.S 的数据页（物理地址）
  struct context context;      // 内核上下文（swtch() 切换到这里）
  struct file *ofile[NOFILE];  // 打开的文件（最多 NOFILE=16 个）
  struct inode *cwd;           // 当前目录（inode 指针）
  char name[16];               // 进程名（调试用）
};

字段分组分析：

struct proc 的内存布局（概念示意）：

┌──────────────────────────────────────────────────────┐
│ 同步原语                                              │
│   lock（40字节）                                      │
├──────────────────────────────────────────────────────┤
│ 需要 p->lock 保护的字段（多 CPU 可读写）               │
│   state（4），parent（8），chan（8），killed（4）       │
│   xstate（4），pid（4）                               │
├──────────────────────────────────────────────────────┤
│ 进程私有字段（只有本进程访问，无需锁）                  │
│   kstack（8）—— 内核栈虚拟地址                        │
│   sz（8）—— 用户内存大小                              │
│   pagetable（8）—— 用户页表指针                       │
│   trapframe（8）—— trapframe 物理地址                 │
│   context（112字节）—— 内核上下文                     │
│   ofile[16]（128字节）—— 16个文件指针                 │
│   cwd（8）—— 当前目录 inode                          │
│   name[16]（16字节）—— 进程名                         │
└──────────────────────────────────────────────────────┘

p->lock 的保护范围

注释明确指出：state, parent, chan, killed, xstate, pid 这六个字段需要持有 p->lock 才能读写。为什么？

  • state：调度器和进程都会读写（scheduler() 改 RUNNING，yield() 改 RUNNABLE，sleep() 改 SLEEPING）
  • parent：reparent() 在 exit() 中修改，调度器和 wait() 可能读取
  • chan：sleep() 写入，wakeup() 读取
  • pid：allocpid() 写入，多处读取

而 kstack, sz, pagetable 等只有进程自身访问，不会产生竞争，无需锁。

与进程相关的内存资源总结：

资源 位置 大小 由谁管理
struct proc 本身 静态数组 proc[64] ~360 字节 内核静态分配
内核栈 KSTACK(i)（虚拟地址），物理页动态分配 4KB procinit() 分配，永不释放
trapframe 页 物理页，映射到用户页表 TRAPFRAME 4KB allocproc() / freeproc()
用户页表 物理页（L2/L1/L0 各一页） 最少 3×4KB proc_pagetable() / proc_freepagetable()
用户内存页 物理页，映射到用户页表 0~sz sz（可变） uvmalloc() / uvmdealloc()

三、源码精读：kernel/proc.c 的初始化部分

3.1 全局变量

struct cpu cpus[NCPU];    // 8 个 CPU 的状态
struct proc proc[NPROC];  // 64 个进程的进程表（静态分配）
struct proc *initproc;    // 指向第一个用户进程（/init）的全局指针

int nextpid = 1;          // 下一个分配的 PID（从 1 开始）
struct spinlock pid_lock; // 保护 nextpid 的自旋锁

nextpid 从 1 开始：PID 0 通常保留（类 Unix 系统惯例）。在 xv6 中，进程 PID 单调递增，不复用——即使进程死亡，其 PID 也不会分配给新进程（只要 nextpid 不溢出）。

3.2 procinit()——进程表初始化

void
procinit(void)
{
  struct proc *p;
  
  initlock(&pid_lock, "nextpid");           // 初始化 PID 分配锁
  
  for(p = proc; p < &proc[NPROC]; p++) {
    initlock(&p->lock, "proc");             // 初始化每个进程的锁
    
    // 为每个进程预分配一个内核栈物理页
    char *pa = kalloc();
    if(pa == 0)
      panic("kalloc");
    
    uint64 va = KSTACK((int)(p - proc));    // 计算该进程内核栈的虚拟地址
    kvmmap(va, (uint64)pa, PGSIZE, PTE_R | PTE_W);  // 映射到内核页表
    p->kstack = va;                         // 记录内核栈虚拟地址
  }
  
  kvminithart();    // 重新加载内核页表（因为添加了新映射）
}

内核栈的设计：

虚拟地址空间（高地址区域）：

TRAMPOLINE（MAXVA - PGSIZE）
    ├─ [4KB] trampoline 代码
    ├─ [4KB] 进程 0 的保护页（无效PTE，不映射）
    ├─ [4KB] 进程 0 的内核栈  ← KSTACK(0) = TRAMPOLINE - 2*PGSIZE
    ├─ [4KB] 进程 1 的保护页
    ├─ [4KB] 进程 1 的内核栈  ← KSTACK(1) = TRAMPOLINE - 4*PGSIZE
    ├─ ...
    ├─ [4KB] 进程 63 的保护页
    └─ [4KB] 进程 63 的内核栈 ← KSTACK(63) = TRAMPOLINE - 128*PGSIZE

宏 KSTACK(p) 的计算：

#define KSTACK(p) (TRAMPOLINE - ((p)+1) * 2*PGSIZE)
// KSTACK(0) = TRAMPOLINE - 2*4096 = TRAMPOLINE - 8192
// KSTACK(1) = TRAMPOLINE - 4*4096 = TRAMPOLINE - 16384
// ...

两个 PGSIZE 间距的原因：进程 N 的内核栈和进程 N+1 的内核栈之间有 1 页间隔（保护页），这个保护页没有映射（PTE 无效）。如果内核栈溢出（向低地址越界），下一次内存访问会命中无效 PTE，触发 page fault，内核可以检测到栈溢出，而不是静默损坏其他数据。

为什么内核栈在 procinit() 就分配，不在 allocproc() 时分配？

内核栈是永久分配的——一旦分配就不释放，即使进程死亡（struct proc 变回 UNUSED）。这简化了实现：不需要在 freeproc() 中释放内核栈，也不需要在 allocproc() 时重新分配。64 个内核栈共占 64 × 4KB = 256KB，这是可以接受的代价。

kvminithart() 为什么要在循环后调用？

kvmmap() 只是向内核页表添加新的映射，但 TLB 中的旧缓存没有失效。kvminithart() 会写入 satp 并执行 sfence_vma()，使新增的内核栈映射对当前 CPU 生效。

（注意：此时其他 CPU 还没有调用 kvminithart()，但 procinit() 在 CPU 0 启动时调用，其他 CPU 还在等待，不会访问这些地址。）

3.3 cpuid() / mycpu() / myproc()

// 获取当前 hart（CPU核心）的编号
// 必须在中断禁用时调用（防止进程在读取 tp 和使用返回值之间迁移到另一核）
int
cpuid()
{
  int id = r_tp();   // 读取 tp 寄存器（内核用它存 hart ID）
  return id;
}

// 返回当前 CPU 的 struct cpu*（必须在中断禁用时调用）
struct cpu*
mycpu(void) {
  int id = cpuid();
  struct cpu *c = &cpus[id];
  return c;
}

// 返回当前进程的 struct proc*（可以在任何时候调用）
struct proc*
myproc(void) {
  push_off();            // 禁用中断（防止读取期间 CPU 切换）
  struct cpu *c = mycpu();
  struct proc *p = c->proc;
  pop_off();             // 恢复中断
  return p;
}

为什么 mycpu() 要求中断禁用？

设想这个序列：

  1. 进程在 CPU 0 上调用 mycpu()
  2. 读取 tp = 0（CPU 0 的 hart ID）
  3. 时钟中断：调度器把进程迁移到 CPU 1
  4. 进程恢复，使用刚才读取的 ID 0，访问 cpus[0]
  5. 但进程现在在 CPU 1 上！ cpus[0].proc 是 CPU 0 当前运行的进程，不是当前进程

push_off()/pop_off() 的配对使用：

  • push_off() 关中断，保证从读取 tp 到使用返回值这段代码不会被中断
  • pop_off() 恢复中断状态
  • 即使不需要保护共享数据，也需要关中断防止”CPU 漂移”

tp 寄存器存 hart ID 是何时设置的？

在 kernel/start.c 的 start() 函数中：

// keep each CPU's hartid in its tp register, for cpuid().
int id = r_mhartid();
w_tp(id);

在 M-mode 阶段，每个核心将自己的 hart ID 写入 tp，之后一直保持。

3.4 allocpid()——分配新 PID

int
allocpid() {
  int pid;
  
  acquire(&pid_lock);    // 加锁保护 nextpid
  pid = nextpid;
  nextpid = nextpid + 1;
  release(&pid_lock);
  
  return pid;
}

为什么 nextpid 需要锁？多个 CPU 可能同时调用 allocpid()（例如同时 fork）。如果不加锁，两个 CPU 可能读到相同的 nextpid，分配出相同的 PID——这会破坏进程唯一标识的基本保证。

3.5 allocproc()——分配并初始化一个新进程

// 在进程表中找一个 UNUSED 槽位，初始化运行所需的状态
// 返回时持有 p->lock
// 失败返回 0
static struct proc*
allocproc(void)
{
  struct proc *p;

  // ① 扫描进程表，找 UNUSED 槽位
  for(p = proc; p < &proc[NPROC]; p++) {
    acquire(&p->lock);
    if(p->state == UNUSED) {
      goto found;
    } else {
      release(&p->lock);
    }
  }
  return 0;  // 进程表满了

found:
  // ② 分配 PID
  p->pid = allocpid();

  // ③ 分配 trapframe 页（一个物理页专用于保存用户寄存器）
  if((p->trapframe = (struct trapframe *)kalloc()) == 0){
    release(&p->lock);
    return 0;
  }

  // ④ 创建用户页表（含 TRAMPOLINE 和 TRAPFRAME 的映射）
  p->pagetable = proc_pagetable(p);
  if(p->pagetable == 0){
    freeproc(p);       // 失败时回滚（释放 trapframe）
    release(&p->lock);
    return 0;
  }

  // ⑤ 设置内核上下文：新进程第一次被调度时从 forkret() 开始执行
  memset(&p->context, 0, sizeof(p->context));
  p->context.ra = (uint64)forkret;      // 返回地址 = forkret
  p->context.sp = p->kstack + PGSIZE;   // 栈指针 = 内核栈顶

  return p;  // 返回时 p->lock 仍被持有（调用者负责 release）
}

allocproc() 的执行流程：

进程表扫描（加锁检查每个 proc）
    │
    ▼ 找到 UNUSED 槽位，持有其锁
    │
    ├─ allocpid() → 分配唯一 PID
    │
    ├─ kalloc() → 分配 trapframe 物理页（4KB）
    │
    ├─ proc_pagetable() → 创建用户页表
    │     ├─ uvmcreate() → L2 根页表
    │     ├─ mappages(TRAMPOLINE, trampoline物理页, PTE_R|PTE_X)
    │     └─ mappages(TRAPFRAME, trapframe物理地址, PTE_R|PTE_W)
    │
    └─ 设置 context.ra = forkret, context.sp = 内核栈顶
       （新进程第一次被 swtch 切换到时，将从 forkret 开始执行）

forkret 的作用：

allocproc() 将 context.ra 设为 forkret 的地址。当调度器第一次通过 swtch 切换到这个新进程时，swtch 会执行 ret 指令，跳转到 ra 地址，也就是 forkret：

void
forkret(void)
{
  static int first = 1;
  release(&myproc()->lock);   // 释放仍被持有的 p->lock（从 scheduler 传入）

  if (first) {
    first = 0;
    fsinit(ROOTDEV);          // 第一次执行时初始化文件系统
  }

  usertrapret();              // 返回用户态
}

usertrapret() 是从内核返回用户态的标准路径（第 9 节详细讲解）。forkret 的作用就是给新进程一个”假装从 trap 返回”的入口。

**context.sp = p->kstack + PGSIZE**：

内核栈从 p->kstack 开始，大小为 PGSIZE（4KB）。栈向下增长，所以栈顶在 kstack + PGSIZE（高地址）。设置 sp 是因为 swtch 的 ret 指令返回到 forkret 后，forkret 是普通的 C 函数，需要一个有效的内核栈。

3.6 proc_pagetable()——为进程创建初始用户页表

pagetable_t
proc_pagetable(struct proc *p)
{
  pagetable_t pagetable;

  // ① 创建空用户页表
  pagetable = uvmcreate();
  if(pagetable == 0)
    return 0;

  // ② 映射 TRAMPOLINE（trap 入口/出口代码）
  //    虚拟地址 MAXVA-PGSIZE → 物理地址 trampoline 代码所在页
  //    权限：PTE_R|PTE_X（可读可执行），无 PTE_U（用户态不能直接访问）
  if(mappages(pagetable, TRAMPOLINE, PGSIZE,
              (uint64)trampoline, PTE_R | PTE_X) < 0){
    uvmfree(pagetable, 0);
    return 0;
  }

  // ③ 映射 TRAPFRAME（保存用户寄存器的页）
  //    虚拟地址 MAXVA-2*PGSIZE → p->trapframe 的物理地址
  //    权限：PTE_R|PTE_W（可读可写），无 PTE_U（用户态不能直接访问）
  if(mappages(pagetable, TRAPFRAME, PGSIZE,
              (uint64)(p->trapframe), PTE_R | PTE_W) < 0){
    uvmunmap(pagetable, TRAMPOLINE, 1, 0);
    uvmfree(pagetable, 0);
    return 0;
  }

  return pagetable;
}

新用户页表建立后的初始状态：

用户虚拟地址空间（新进程，尚未 exec）：

MAXVA         ──────────────────────
TRAMPOLINE    [PTE_R|PTE_X]      ← trampoline 代码（trap 入口出口）
TRAPFRAME     [PTE_R|PTE_W]      ← 用户寄存器保存区（sscratch 指向这里）
（以下全部未映射，exec/uvmalloc 之后才会有内容）
0x0           ──────────────────────

TRAMPOLINE 映射的关键特性：

  • 在所有用户页表中，TRAMPOLINE 都映射到同一个物理页（trampoline.S 编译链接后的代码页）
  • 在内核页表中，TRAMPOLINE 也映射到同一物理页
  • 这样在 trap 时切换 satp 时，PC 指向的 trampoline 代码在两个页表中都有效映射，切换不会导致 page fault

3.7 proc_freepagetable()——释放进程页表

void
proc_freepagetable(pagetable_t pagetable, uint64 sz)
{
  uvmunmap(pagetable, TRAMPOLINE, 1, 0);  // 解除 TRAMPOLINE 映射（do_free=0：不释放物理页）
  uvmunmap(pagetable, TRAPFRAME, 1, 0);   // 解除 TRAPFRAME 映射（do_free=0：不释放物理页）
  uvmfree(pagetable, sz);                  // 释放用户数据页 + 页表结构
}

为什么 TRAMPOLINE 和 TRAPFRAME 的解除映射用 do_free=0？

  • TRAMPOLINE：物理页是内核代码的一部分（trampoline.S 编译后的代码），多个进程共享同一个物理页，不能释放！
  • TRAPFRAME：物理页由 allocproc() 中的 kalloc() 分配，但 freeproc() 会单独通过 kfree(p->trapframe) 释放它。如果这里 do_free=1，会导致 kfree 被调用两次（double-free bug）。

所以这两个 uvmunmap 只是清除页表中的 PTE（解除虚拟→物理的映射），不释放背后的物理内存。

3.8 freeproc()——释放进程的所有资源

static void
freeproc(struct proc *p)
{
  if(p->trapframe)
    kfree((void*)p->trapframe);   // 释放 trapframe 物理页
  p->trapframe = 0;

  if(p->pagetable)
    proc_freepagetable(p->pagetable, p->sz);  // 释放页表和用户内存
  p->pagetable = 0;
  p->sz = 0;

  // 清零所有字段，使 struct proc 回到干净状态
  p->pid = 0;
  p->parent = 0;
  p->name[0] = 0;
  p->chan = 0;
  p->killed = 0;
  p->xstate = 0;
  p->state = UNUSED;    // 最后才设置为 UNUSED（重要！）
}

注意：p->state = UNUSED 必须是最后一步。如果提前设置，其他 CPU 可能在资源还未清理完毕时就把这个槽位的 proc 分配出去——这是经典的并发 bug。

freeproc 不释放内核栈：如前所述，内核栈是永久分配的，不在 freeproc 中释放。

四、第一个进程：userinit() 和 initcode

4.1 内嵌的 initcode

// user/initcode.S 编译后的 51 字节机器码，直接内嵌在内核中
uchar initcode[] = {
  0x17, 0x05, 0x00, 0x00, 0x13, 0x05, 0x45, 0x02,  // auipc a0, 0; addi a0, a0, 0x44
  0x97, 0x05, 0x00, 0x00, 0x93, 0x85, 0x35, 0x02,  // auipc a1, 0; addi a1, a1, 0x35
  0x93, 0x08, 0x70, 0x00, 0x73, 0x00, 0x00, 0x00,  // li a7, 7(SYS_exec); ecall
  0x93, 0x08, 0x20, 0x00, 0x73, 0x00, 0x00, 0x00,  // li a7, 2(SYS_exit); ecall
  0xef, 0xf0, 0x9f, 0xff,                           // jal ra, -8（无限循环）
  0x2f, 0x69, 0x6e, 0x69, 0x74, 0x00,               // "/init\0"（字符串数据）
  0x00, 0x24, 0x00, 0x00, 0x00, 0x00,
  0x00, 0x00, 0x00, 0x00
};

这 51 字节对应 user/initcode.S，实际完成的工作是：

# initcode.S（简化版）
.global start
start:
    la a0, init       # a0 = "/init" 字符串的地址
    la a1, argv       # a1 = argv 数组的地址（只有一个 NULL 元素）
    li a7, SYS_exec   # a7 = exec 系统调用号（7）
    ecall             # 执行 exec("/init", {NULL})
    # 如果 exec 失败，执行 exit(0)
    li a7, SYS_exit
    ecall
init:
    .string "/init"
argv:
    .long 0

为什么要把 initcode 编译后的字节内嵌在内核中？

这是一个”先有鸡还是先有蛋”的问题：

  • 要运行用户程序，需要文件系统
  • 要挂载文件系统，需要文件系统初始化代码（fsinit()）
  • fsinit() 只能在进程上下文中运行（因为它需要调用 sleep()）
  • 所以必须先创建第一个进程，才能在它的上下文中初始化文件系统

initcode 是那个”鸡”：它绕过文件系统，直接从内核数据段加载到进程内存，然后调用 exec("/init") 来启动真正的 /init 程序（从文件系统读取）。

4.2 userinit()——创建并启动第一个进程

void
userinit(void)
{
  struct proc *p;

  // ① 分配进程槽位、trapframe、初始用户页表
  p = allocproc();
  initproc = p;          // 记录全局指针

  // ② 将 initcode 加载到虚拟地址 0
  uvminit(p->pagetable, initcode, sizeof(initcode));
  p->sz = PGSIZE;        // 用户内存大小 = 1 页

  // ③ 设置第一次"返回"到用户态的现场
  p->trapframe->epc = 0;      // 用户 PC = 0（initcode 从地址 0 开始执行）
  p->trapframe->sp = PGSIZE;  // 用户栈指针 = 页顶（栈向下增长，从 0x1000 开始）

  // ④ 设置进程名和当前目录
  safestrcpy(p->name, "initcode", sizeof(p->name));
  p->cwd = namei("/");   // 当前目录 = 根目录

  // ⑤ 标记为可运行
  p->state = RUNNABLE;

  release(&p->lock);     // allocproc 持有的锁，在这里释放
}

执行链：

boot
  └─ main() （CPU 0）
       └─ userinit()
            └─ allocproc() → p = proc[0]（PID=1）
            └─ uvminit() → 加载 initcode 到虚拟地址 0
            └─ p->state = RUNNABLE
  └─ scheduler()
       └─ 找到 proc[0]（RUNNABLE）
       └─ swtch(&c->context, &p->context)
       └─ → forkret() → usertrapret() → trampoline.S
       └─ → 进入用户模式，PC=0，执行 initcode

initcode 执行：
  └─ ecall exec "/init" → exec() 替换进程内存
  └─ 运行 user/init.c

init.c 执行：
  └─ open("console", O_RDWR) → fd 0
  └─ dup(0) → fd 1 (stdout)
  └─ dup(0) → fd 2 (stderr)
  └─ fork() + exec("sh") → 启动 shell
  └─ 无限循环 wait() → 回收孤儿进程

五、进程的退出与等待：exit() 和 wait()

5.1 exit()——进程主动退出

void
exit(int status)
{
  struct proc *p = myproc();

  if(p == initproc)
    panic("init exiting");    // init 不能退出！

  // ① 关闭所有打开的文件
  for(int fd = 0; fd < NOFILE; fd++){
    if(p->ofile[fd]){
      fileclose(p->ofile[fd]);
      p->ofile[fd] = 0;
    }
  }

  // ② 释放当前工作目录的引用
  begin_op();
  iput(p->cwd);
  end_op();
  p->cwd = 0;

  // ③ 唤醒 init（可能有孤儿进程需要处理）
  acquire(&initproc->lock);
  wakeup1(initproc);
  release(&initproc->lock);

  // ④ 加锁顺序：先父进程，再自己（prevent 死锁）
  acquire(&p->lock);
  struct proc *original_parent = p->parent;
  release(&p->lock);

  acquire(&original_parent->lock);  // 父进程锁
  acquire(&p->lock);                // 自己的锁

  // ⑤ 将子进程托管给 init（如果自己有子进程）
  reparent(p);

  // ⑥ 唤醒正在 wait() 的父进程
  wakeup1(original_parent);

  // ⑦ 保存退出状态，转为 ZOMBIE
  p->xstate = status;
  p->state = ZOMBIE;

  release(&original_parent->lock);

  // ⑧ 永久让出 CPU（不再返回）
  sched();
  panic("zombie exit");
}

exit() 的资源释放顺序：

exit(status):
  ├─ 关闭所有文件（fileclose × NOFILE）       ← 文件描述符
  ├─ iput(p->cwd)                             ← 当前目录引用计数
  ├─ reparent(p)                              ← 子进程转交 init
  ├─ wakeup1(parent)                          ← 唤醒等待的父进程
  ├─ p->state = ZOMBIE                        ← 变为僵尸（等待父进程回收）
  └─ sched()                                  ← 让出 CPU，永不返回

注意：以下资源在 ZOMBIE 阶段仍然保留，等待 freeproc() 回收：
  - struct proc 本身（状态、退出码 xstate、PID）
  - 内核栈（永久保留）
  - trapframe（由 freeproc 释放）
  - 用户页表和用户内存（由 freeproc → proc_freepagetable 释放）

为什么 exit() 需要同时持有父进程锁和自己的锁？

关键操作是：

  1. reparent(p)：修改 p 的所有子进程的 parent 指针
  2. wakeup1(original_parent)：修改父进程的 state
  3. p->state = ZOMBIE：修改自己的状态

如果先修改子进程的 parent（1），父进程此时调用 wait() 查找 ZOMBIE 子进程，可能看到不一致的状态。持有两个锁确保这三个操作是原子的。

加锁顺序为什么必须是”先父后子”？

这是 xv6 的全局锁顺序规则（parent-then-child rule）：

  • wait() 中：先持有 p->lock（自己），然后获取子进程 np->lock
  • exit() 中：先获取 original_parent->lock，然后获取 p->lock
  • 如果倒序，可能导致死锁（进程 A 等 B，B 等 A）

5.2 wait()——等待子进程退出

int
wait(uint64 addr)  // addr = 用户空间中存放退出状态的地址（可以为 0）
{
  struct proc *np;
  int havekids, pid;
  struct proc *p = myproc();

  acquire(&p->lock);   // 持有自己的锁（全程），防止丢失唤醒

  for(;;){
    // ① 扫描进程表，找 ZOMBIE 子进程
    havekids = 0;
    for(np = proc; np < &proc[NPROC]; np++){
      if(np->parent == p){                  // 是我的子进程？
        acquire(&np->lock);
        havekids = 1;
        if(np->state == ZOMBIE){
          // 找到一个已退出的子进程
          pid = np->pid;
          if(addr != 0 && copyout(p->pagetable, addr,
                                  (char *)&np->xstate, sizeof(np->xstate)) < 0) {
            release(&np->lock);
            release(&p->lock);
            return -1;                      // 无法将退出状态写回用户空间
          }
          freeproc(np);                     // 回收子进程所有资源
          release(&np->lock);
          release(&p->lock);
          return pid;                       // 返回子进程 PID
        }
        release(&np->lock);
      }
    }

    // ② 没有活的子进程 → 直接返回
    if(!havekids || p->killed){
      release(&p->lock);
      return -1;
    }

    // ③ 有子进程但都还活着 → 睡眠等待
    sleep(p, &p->lock);   // 以 p 为 chan 睡眠，直到某个子进程调用 exit() 唤醒
  }
}

wait() 与 exit() 的配合：

父进程 wait()                               子进程 exit()
──────────────                              ──────────────

acquire(&p->lock)
for(;;) {
  扫描进程表...
  没有 ZOMBIE 子进程
  sleep(p, &p->lock)  ←─── 睡眠 ─┐
      释放 p->lock               │
      ...等待...                  │
                                  │  acquire(&parent->lock)
                                  │  acquire(&p->lock)
                                  │  p->state = ZOMBIE
                                  └─ wakeup1(parent)
      重新获取 p->lock            │
      从 sleep 返回               │
  扫描进程表...                   │  release(&parent->lock)
  找到 ZOMBIE 子进程 ←────────────┘
  freeproc(np)        // 回收资源
  return np->pid
}

sleep(p, &p->lock) 的 chan 为什么是 p（即父进程自身的地址）？

sleep(chan, lk) 使进程在通道 chan 上等待，wakeup(chan) 唤醒所有等在这个通道上的进程。选择 p（父进程 struct 地址）作为通道，是因为只有当这个父进程的子进程退出时才需要唤醒这个父进程——用父进程地址作通道，确保唤醒的精准性。

六、生命周期全景：从 fork() 到 exit() 的完整资源流动

fork() 调用：
  allocproc()
    ├─ kalloc()             → trapframe（4KB）
    └─ proc_pagetable()
         ├─ kalloc()        → L2 根页表（4KB）
         ├─ kalloc()        → L1 页表（按需，walk创建）
         ├─ kalloc()        → L0 页表（按需，walk创建）
         └─ mappages(TRAMPOLINE, TRAPFRAME)

  uvmcopy(parent, child, sz)
    └─ 对父进程每一页：
         ├─ kalloc()        → 子进程对应物理页（sz/4096 个）
         └─ mappages()      → 建立子进程页表映射

  设置 ofile[] 引用计数++
  设置 cwd 引用计数++
  子进程 state = RUNNABLE

  ──────────────────── 子进程运行期间 ──────────────────────

exit(status) 调用：
  fileclose(ofile[]) × N   → 关闭打开的文件（引用计数--）
  iput(cwd)                → 目录引用计数--
  wakeup1(parent)          → 唤醒 wait() 中的父进程
  state = ZOMBIE           → 等待父进程回收

  ──────────────────── 父进程 wait() ─────────────────────

freeproc(child) 调用：
  kfree(trapframe)         → 释放 trapframe（4KB）
  proc_freepagetable()
    ├─ uvmunmap(TRAMPOLINE, do_free=0)  → 仅解除映射
    ├─ uvmunmap(TRAPFRAME, do_free=0)   → 仅解除映射
    └─ uvmfree(pagetable, sz)
         ├─ uvmunmap(0, npages, do_free=1) → 释放所有用户页（sz/4096 个物理页）
         └─ freewalk()                     → 释放页表结构（L2/L1/L0 页）
  state = UNUSED

实验 4：追踪 init 进程的行为

// user/init.c 关键逻辑（简化）
int main(void) {
  // 1. 打开控制台作为 fd 0（stdin）
  if(open("console", O_RDWR) < 0){
    mknod("console", CONSOLE, 0);  // 若不存在，先创建设备文件
    open("console", O_RDWR);
  }
  dup(0);  // fd 1 = stdout
  dup(0);  // fd 2 = stderr

  for(;;){
    printf("init: starting sh\n");
    int pid = fork();
    if(pid == 0) {
      exec("sh", argv);   // 子进程：运行 shell
      exit(1);
    }
    for(;;){
      int wpid = wait(0); // 父进程：等待所有子进程
      if(wpid == pid)     // 如果 shell 退出了，重启它
        break;
    }
  }
}

思考：

  2. 如果一个进程的父进程先退出（orphan），它的父进程会变成谁？
  3. dup(0) 为什么能把 fd 0 复制到 fd 1？

实验 6：实现系统调用 getppid()

给 xv6 添加一个新系统调用，返回当前进程的父进程 PID：

步骤 1：在 kernel/sysproc.c 中添加：

uint64
sys_getppid(void)
{
  struct proc *p = myproc();
  // 注意：读取 parent 需要持有 p->lock
  acquire(&p->lock);
  int ppid = p->parent ? p->parent->pid : 0;
  release(&p->lock);
  return ppid;
}

步骤 2：在 kernel/syscall.h 中添加系统调用号：

#define SYS_getppid 23   // 在最后一个号码后添加

步骤 3：在 kernel/syscall.c 中注册：

extern uint64 sys_getppid(void);
// 在 syscalls 数组中添加：
[SYS_getppid] sys_getppid,

步骤 4：在 user/usys.pl 中添加：

entry("getppid");

步骤 5：在 user/user.h 中声明：

int getppid(void);

步骤 6：写测试程序 user/ppid.c：

#include "kernel/types.h"
#include "user/user.h"
int main(){
  printf("我的 PID=%d，父进程 PID=%d\n", getpid(), getppid());
  return 0;
}

八、思考题

  1. struct proc 有 struct context context 字段，同时也保存了 struct trapframe *trapframe 指针。为什么一个用 struct 内嵌，一个用指针？

    context 用内嵌：它很小（112 字节），直接放在 struct proc 中访问高效，swtch() 直接操作 p->context 的地址即可。trapframe 用指针：它需要独占一个物理页（4KB），并且需要在用户页表的 TRAPFRAME 地址处映射。如果内嵌在 struct proc 中，就无法单独映射到特定虚拟地址。分离设计使 trampoline.S 可以通过固定虚拟地址 TRAPFRAME 访问它。

  2. 进程状态机中，RUNNING 状态的进程可以直接跳到 SLEEPING 吗（不经过 RUNNABLE）？

    可以，也是最常见的路径。进程调用 sleep() 时，直接从 RUNNING 变为 SLEEPING（p->state = SLEEPING; sched()），不经过 RUNNABLE。RUNNABLE 是进程等待被调度器选中时的状态；一旦进程主动挂起等待 I/O，没有必要先变成 RUNNABLE 再睡眠。

  3. 为什么 allocproc() 不立即将进程状态设为 RUNNABLE，而是保留调用者（userinit 或 fork）来设置？

    allocproc() 返回时，进程尚未完全初始化（还没有用户内存、系统调用参数等）。如果 allocproc() 内部就设置 RUNNABLE，调度器可能在初始化完成前就调度它，导致运行一个不完整的进程。调用者（fork()/userinit()）在所有初始化完成后才设置 RUNNABLE，保证进程第一次运行时处于完全就绪状态。

  4. exit() 为什么先关闭文件再设置 ZOMBIE，而不是反过来？

    如果先设置 ZOMBIE，父进程可能立即调用 wait() 并执行 freeproc()，释放页表和 trapframe。此时 exit() 后续的 fileclose() 操作会访问已释放的内存——use-after-free bug。先完成所有清理工作再设置 ZOMBIE，确保 ZOMBIE 是一个稳定的最终状态，此后只剩 freeproc() 的最后回收工作（释放 trapframe 和页表），不会有其他代码再访问这个进程的资源。

  5. procinit() 为所有 64 个进程的内核栈都分配了物理页（64 KB），即使大多数进程槽位是 UNUSED。这是不是内存浪费？你能想到更节省的设计吗？

    这是一种空间换时间的权衡：永久预分配避免了每次 allocproc()/freeproc() 时的动态分配/释放开销，也避免了内核栈的碎片化问题。更节省的设计是按需分配（在 allocproc() 中分配内核栈，在 freeproc() 中释放）。但这要求 freeproc() 也要解除内核页表中的 KSTACK 映射，并刷新 TLB，增加了实现复杂性。Linux 内核实际上是按需分配内核栈的（fork() 时用 alloc_thread_stack_node()）。

  6. reparent() 把孤儿进程的父进程改为 initproc，但代码注释中说”we should wake up init here, but that would require initproc->lock”，然后在 exit() 提前唤醒了 init。这里的死锁是怎么产生的？为什么提前唤醒是安全的？

    死锁场景：exit() 同时持有 original_parent->lock 和 p->lock。如果在 reparent() 中调用 wakeup(initproc)，而 initproc (init 进程) 也在 wait() 中持有自己的锁并试图获取某个子进程的锁，就可能形成循环等待。提前唤醒（在获取任何子进程锁之前）是安全的：即使 init 被唤醒后扫描进程表，发现没有 ZOMBIE 子进程，它只会再次睡眠。这是 xv6 中”宁可虚假唤醒，也不死锁“的设计哲学——sleep/wakeup 机制本就允许虚假唤醒（被唤醒后重新检查条件）。

九、本节小结

概念 要点
进程定义 地址空间 + 执行状态 + 内核资源
五种状态 UNUSED→RUNNABLE→RUNNING→SLEEPING→ZOMBIE→UNUSED
进程表 proc[NPROC=64]，静态数组，线性扫描找空槽
struct context 14 个 callee-saved 寄存器，用于内核线程切换
struct cpu 每 CPU 一个：当前进程、调度器上下文、中断嵌套深度
struct trapframe 32 个用户寄存器 + 5 个内核引导字段，独占一物理页
struct proc 进程的完整状态；lock 字段保护 state/parent/chan/pid 等
procinit() 为所有 64 个进程预分配内核栈（永久映射到内核页表）
allocproc() 找 UNUSED 槽 → 分 PID → 分 trapframe → 建页表 → 设 forkret
freeproc() 释放 trapframe → 释放页表 + 用户内存 → 清零 → UNUSED
proc_pagetable() 创建用户页表，映射 TRAMPOLINE + TRAPFRAME（无 PTE_U）
userinit() 创建 PID=1 的第一个进程，加载内嵌的 initcode
exit() 关文件→放目录→托孤→唤醒父→ZOMBIE→sched（永不返回）
wait() 扫描 ZOMBIE 子进程 → freeproc 回收 → 睡眠等待（无子时返回）
ZOMBIE 作用 保留退出状态码，等待父进程 wait() 读取后才真正释放
