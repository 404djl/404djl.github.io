第 8 节：进程调度与上下文切换

学习目标：理解 xv6 如何在多个进程之间共享 CPU——包括 42 行汇编完成的上下文切换、调度器循环、主动让出与时钟中断驱动的抢占，以及 sleep/wakeup 机制。

预计用时：3-4 小时

前置要求：完成第 6、7 节，理解 struct proc、struct context、trapframe 的作用

一、理论：调度的核心问题

1.1 为什么需要调度？

操作系统运行多个进程，但 CPU 是有限的（xv6 最多 NCPU=8 个核）。当进程数 > CPU 数时，操作系统必须在进程之间分时复用 CPU——每个进程运行一段时间，让出 CPU，再等待再次被分配。

调度器要解决的问题：

  1. 何时切换（定时、主动让出、等待 I/O）
  2. 切换到谁（xv6 用最简单的轮询：找第一个 RUNNABLE 进程）
  3. 如何切换（保存/恢复 CPU 状态，即上下文切换）
  4. 切换的安全性（不能在持有多把锁时切换、不能在中断开启时切换）

1.2 协作式 vs 抢占式

策略 触发方式 风险 xv6 实现
协作式（cooperative） 进程主动调用 yield() 或阻塞 I/O 恶意/死循环进程独占 CPU yield()
抢占式（preemptive） 计时器中断强制打断 切换开销，需要保存更多状态 时钟中断 → yield()

xv6 两者结合：

  • 进程主动调用 sleep() 时协作式让出
  • 时钟中断每隔固定时间强制触发 yield()（抢占）

1.3 上下文切换的”两跳”设计

xv6 中，进程之间的切换不是直接切换，而是必须经过调度器线程（scheduler thread）：

进程 A（内核线程）
   │
   │ sched()
   │  └─ swtch(&p->context, &cpu->context)   ← 第一跳：进程 → 调度器
   ▼
scheduler()（在 cpu->context 对应的内核栈上运行）
   │
   │ swtch(&cpu->context, &nextproc->context) ← 第二跳：调度器 → 下一进程
   ▼
进程 B（内核线程，从 sched() 中的 swtch 返回）

为什么要经过调度器线程？

假设进程 A 想直接切换到进程 B，需要同时持有 A->lock 和 B->lock（修改两个进程的状态）。但 xv6 的锁规范要求同时最多持有一把进程锁——持有多把进程锁时容易发生死锁（例如：A 等 B，B 等 A）。

通过调度器线程中转：

  • 进程 A 持有 A->lock → 切换到调度器
  • 调度器释放 A->lock → 选择 B → 持有 B->lock → 切换到 B
  • 进程 B 释放 B->lock → 运行

每次切换只持有一把进程锁，避免了死锁。

1.4 调度上下文 vs Trap 上下文

xv6 有两套寄存器保存机制，用途不同：

机制 触发时机 保存什么 保存到哪 汇编文件
Trap 上下文（trapframe） 用户态进入内核（ecall/中断/异常） 全部 32 个用户寄存器 proc->trapframe trampoline.S
调度上下文（context） 内核线程切换（swtch） 14 个 callee-saved 寄存器 proc->context 或 cpu->context swtch.S

Trap 上下文是保存用户态现场（从用户态切换到内核态）；调度上下文是保存内核线程现场（在多个内核线程之间切换）。

二、源码精读：kernel/swtch.S（42 行）

2.1 完整汇编代码解析

# kernel/swtch.S
# void swtch(struct context *old, struct context *new);
# 
# 将当前寄存器保存到 old，然后从 new 加载寄存器。

.globl swtch
swtch:
        # ── 保存当前线程的上下文到 old（a0 指针） ──
        sd ra,   0(a0)    # 返回地址（swtch 返回时跳到这里）
        sd sp,   8(a0)    # 栈指针

        sd s9,  88(a0)
        sd s10, 96(a0)
        sd s11,104(a0)

        # ── 加载新线程的上下文（a1 指针） ──
        ld ra,   0(a1)
        ld sp,   8(a1)
        ld s0,  16(a1)
        ld s1,  24(a1)
        ld s2,  32(a1)

        ld s10, 96(a1)
        ld s11,104(a1)
        
        ret     # 跳转到新线程的 ra（即之前保存的返回地址）

2.2 为什么只保存 14 个寄存器，不保存全部 32 个？

RISC-V 调用约定将寄存器分为两类：

类别 寄存器 约定 谁负责保存
caller-saved ra, t0-t6, a0-a7 调用者在调用前保存，被调用者可以随意修改 让调用者（sched()）自己搞定
callee-saved sp, s0-s11 被调用者负责保存/恢复，调用者可以假设调用后值不变 swtch 必须保存

swtch 是一个普通的 C 函数调用（从 sched() 或 scheduler() 中 call 进来）。编译器已经生成了保存 caller-saved 寄存器的代码——在 sched() 调用 swtch() 之前，编译器自动将 t0-t6、a0-a7 等压栈（或者直接不使用它们）。

swtch 只需要额外保存 callee-saved 寄存器（s0-s11, ra, sp），因为：

  • sp：切换后需要切换到新线程的栈
  • ra：ret 指令跳转到哪里（即 swtch 的返回地址）
  • s0-s11：C 函数约定被调用者必须保存，swtch 作为被调用者负责

ra 的神奇用途：swtch 保存的不只是普通的返回地址——它是线程下次被”恢复”时的执行起点。当调度器 swtch 到进程时，ret 指令跳到进程的 ra（之前 sched() 调用 swtch 时的返回地址），进程就”从 swtch 返回到 sched() 中”继续执行了。

2.3 struct context 与 swtch 的对应关系

// kernel/proc.h
struct context {
  uint64 ra;   // 偏移  0 → sd ra,   0(a0)
  uint64 sp;   // 偏移  8 → sd sp,   8(a0)
  uint64 s0;   // 偏移 16 → sd s0,  16(a0)
  uint64 s1;   // 偏移 24
  uint64 s2;   // 偏移 32
  uint64 s3;   // 偏移 40
  uint64 s4;   // 偏移 48
  uint64 s5;   // 偏移 56
  uint64 s6;   // 偏移 64
  uint64 s7;   // 偏移 72
  uint64 s8;   // 偏移 80
  uint64 s9;   // 偏移 88
  uint64 s10;  // 偏移 96
  uint64 s11;  // 偏移104
};

struct context 中字段的顺序和偏移量与 swtch.S 中 sd 指令的偏移量完全一一对应——这是刻意设计的，保证汇编可以直接用 a0 加偏移访问每个字段。

2.4 swtch 调用前后的栈变化

调用 swtch 前（进程 A 的内核栈）：
  ...
  [sched() 的栈帧]
    [sched() 调用 swtch 前压栈的 caller-saved 寄存器]
  ← sp（进程 A 的内核态栈指针）

执行 swtch：
  ① sd sp, 8(a0)  → 将当前 sp 存入 A->context.sp
  ② sd ra, 0(a0)  → 将 swtch 的返回地址（即 sched() 内 call swtch 后的下一指令）存入 A->context.ra
  
  ③ ld sp, 8(a1)  → 恢复 B->context.sp（切换到进程 B 的内核栈！）
  ④ ld ra, 0(a1)  → 恢复 B->context.ra（B 上次保存的返回地址）
  ⑤ ret           → 跳到 B->context.ra（进程 B 的 sched() 返回后继续执行）

调用 swtch 后（进程 B 的内核栈）：
  ...
  [sched() 的栈帧（B 进入 sched() 时留下的）]
  ← sp（进程 B 的内核栈指针，来自 B->context.sp）

ret 之后发生了什么：ret = jalr ra，跳到 ra 中存储的地址。对于进程 B 来说，ra = B 上一次调用 swtch 时的返回地址，也就是 sched() 函数中 swtch(...) 调用的下一行。进程 B 就从上次挂起的地方继续执行。

三、源码精读：kernel/proc.c 调度相关函数

3.1 scheduler()——调度器主循环

// kernel/proc.c（约第 449 行起）

// 每个 CPU 的调度器。main() 初始化完成后调用 scheduler()，永不返回。
// 循环：选择一个 RUNNABLE 进程，swtch 切换到它；进程再通过 swtch 回来。
void
scheduler(void)
{
  struct proc *p;
  struct cpu *c = mycpu();
  
  c->proc = 0;          // 初始状态：没有进程在运行
  for(;;){
    // 确保设备可以中断（避免死锁）
    // 如果某个进程持有锁并睡眠，需要中断来唤醒它
    intr_on();
    
    int found = 0;
    for(p = proc; p < &proc[NPROC]; p++) {      // 轮询所有进程槽
      acquire(&p->lock);
      if(p->state == RUNNABLE) {
        // 找到一个可运行的进程
        p->state = RUNNING;
        c->proc = p;
        
        // ── 上下文切换：调度器 → 进程 ──
        swtch(&c->context, &p->context);
        // ── 从这里恢复：进程让出 CPU 后回到此处 ──
        
        c->proc = 0;    // 清除"当前进程"（回到调度器状态）
        found = 1;
      }
      release(&p->lock);
    }
    if(found == 0) {
      // 没有 RUNNABLE 进程：开中断，执行 WFI 等待中断唤醒某进程
      intr_on();
      asm volatile("wfi");   // Wait For Interrupt（省电指令）
    }
  }
}

关键设计细节：

① intr_on() 在循环开头：调度器在选进程之前先开启中断。这避免了死锁场景：如果所有进程都在等待设备中断（如磁盘 I/O），调度器需要能响应设备中断来唤醒这些进程，如果中断关闭，等待永远无法结束。

② 谁释放 p->lock？：acquire(&p->lock) 在 scheduler 中，但对应的 release(&p->lock) 不在 scheduler 中——切换到进程后，进程在 sched() 返回后或 forkret() 中释放自己的锁。这是 xv6 中最重要的锁协议之一：进程在进入 sched() 之前必须持有 p->lock，在从 sched() 返回后释放。

③ WFI（Wait For Interrupt）：当没有 RUNNABLE 进程时（所有进程都在睡眠或是 ZOMBIE），CPU 执行 wfi 指令暂停，等到下一个中断（时钟中断、设备 I/O 完成）到来时恢复——节省电能，避免空转。

④ xv6 的调度算法：最简单的轮询（Round-Robin 简化版）——从数组头遍历到尾，选第一个 RUNNABLE 的进程。没有优先级，没有公平性保证。现实中的调度器（Linux CFS、BSD ULE）复杂得多。

3.2 sched()——进程端的切换入口

// 切换到调度器。调用前必须且只持有 p->lock，
// 并且已经修改了 p->state（不能是 RUNNING）。
void
sched(void)
{
  int intena;
  struct proc *p = myproc();

  // 安全检查：必须持有 p->lock
  if(!holding(&p->lock))
    panic("sched p->lock");

  // 安全检查：只能持有一把锁（p->lock），不能持有其他锁
  // noff > 1 说明还有其他锁（或者 push_off() 嵌套）
  if(mycpu()->noff != 1)
    panic("sched locks");

  // 安全检查：调用者必须已经修改了 p->state（不能还是 RUNNING）
  if(p->state == RUNNING)
    panic("sched running");

  // 安全检查：中断必须是关闭的（acquire() 会关中断）
  if(intr_get())
    panic("sched interruptible");

  // 保存"中断是否被启用"的状态（属于线程，不是 CPU）
  intena = mycpu()->intena;
  
  // ── 上下文切换：进程 → 调度器 ──
  swtch(&p->context, &mycpu()->context);
  // ── 从这里恢复：调度器再次选中此进程后，从这里继续 ──
  
  mycpu()->intena = intena;    // 恢复中断状态
}

noff != 1 的含义：noff 是 “push_off 的嵌套深度”（每次 acquire() 调用 push_off()，release() 调用 pop_off()）。noff == 1 说明当前只持有一把锁（就是 p->lock）。如果 noff > 1，说明还持有其他锁——此时切换会导致其他等待那把锁的进程永远无法获取（死锁）。

intena 的保存与恢复：intena 记录”进入内核（push_off）之前，中断是否被启用”。这个属性属于线程（进程），而不是 CPU——进程 A 切换到调度器再切换到进程 B 时，调度器不应该改变进程 B 的 intena。所以 sched() 在切换前保存、切换后恢复 intena。

3.3 yield()——主动让出 CPU

// 放弃 CPU 控制权，进入下一轮调度。
void
yield(void)
{
  struct proc *p = myproc();
  acquire(&p->lock);   // 获取进程锁（sched() 要求持有）
  p->state = RUNNABLE; // 修改状态：我还可以运行，只是让出 CPU
  sched();             // 切换到调度器
  release(&p->lock);   // 从调度器回来后，释放锁
}

yield() 的 6 行代码体现了调度协议的精髓：

  1. acquire(&p->lock) — 宣告”我要修改自己的状态”
  2. p->state = RUNNABLE — 修改状态（仍可运行，下次调度选到我还能跑）
  3. sched() — 把 CPU 交还给调度器
  4. release(&p->lock) — 调度器选中我回来后，释放锁（和 scheduler 中的 acquire 配对）

3.4 forkret()——新进程第一次被调度

新创建的进程（通过 fork()）初始化的 context.ra 指向 forkret，而不是 sched() 内部。这是因为新进程没有经历过 sched()，只能提供一个”伪返回地址”：

void
forkret(void)
{
  static int first = 1;

  // 调度器调用 swtch 到达这里时，仍然持有 p->lock
  // 必须释放它（否则 acquire 后的 release 没有对应的 acquire）
  release(&myproc()->lock);

  if (first) {
    // 文件系统初始化（fsinit）必须在进程上下文中运行
    // （因为它会调用 sleep），不能在 main() 中运行
    first = 0;
    fsinit(ROOTDEV);
  }

  usertrapret();  // 返回用户态（trapframe 中已有初始寄存器值）
}

**为什么 first 是 static**：xv6 中有多个进程会经历 forkret，但 fsinit 只能执行一次（第一个进程，即 init 进程）。static 保证 first 变量只有一份，第一次调用后设为 0，后续进程的 forkret 直接跳过 fsinit。

3.5 sleep() 和 wakeup()——等待与唤醒

sleep/wakeup 是 xv6 的条件变量机制，用于进程等待某个事件发生（如 I/O 完成、管道有数据、子进程退出等）。

// 原子地释放锁 lk，并在 chan 上睡眠。被唤醒时重新获取 lk。
void
sleep(void *chan, struct spinlock *lk)
{
  struct proc *p = myproc();
  
  // 必须先获取 p->lock，然后才能释放 lk
  // 这样可以保证：在"检查条件"和"进入睡眠"之间，
  // 不会有人在 chan 上 wakeup 而我们却错过
  if(lk != &p->lock){
    acquire(&p->lock);   // 获取进程锁
    release(lk);         // 释放调用者的锁
  }

  // 进入睡眠
  p->chan = chan;         // 记录等待的"频道"（事件标识符）
  p->state = SLEEPING;   // 修改状态

  sched();               // 让出 CPU

  // 被唤醒后，从这里继续
  p->chan = 0;

  if(lk != &p->lock){
    release(&p->lock);
    acquire(lk);         // 重新获取原来的锁，让调用者以为 sleep 只是"暂时等了一下"
  }
}

// 唤醒所有在 chan 上睡眠的进程。
// 调用时不能持有任何 p->lock。
void
wakeup(void *chan)
{
  struct proc *p;

  for(p = proc; p < &proc[NPROC]; p++) {
    acquire(&p->lock);
    if(p->state == SLEEPING && p->chan == chan) {
      p->state = RUNNABLE;   // 唤醒：SLEEPING → RUNNABLE
    }
    release(&p->lock);
  }
}

chan（频道/等待条件）：chan 是一个 void * 指针，作为事件的唯一标识符。惯例是使用相关数据结构的地址：

  • sleep(p, &p->lock) → 等待进程 p（wait() 用于等待子进程）
  • sleep(&b, &bcache.lock) → 等待磁盘缓冲区 b 就绪
  • sleep(&ticks, &tickslock) → 等待时钟滴答（sys_sleep 用）

sleep() 的锁协议——避免”丢失唤醒”（lost wakeup）：

假设没有 p->lock 的保护：

进程 A（消费者）：             进程 B（生产者）：
if(buf_empty()) {              buf_write(data);
  ← 被中断！                   wakeup(&buf);（没人在睡眠，唤醒无效）
  sleep(&buf, &lk);（永远睡）

p->lock 阻止了这种竞争：wakeup() 需要 acquire(&p->lock) 才能将 A 设为 RUNNABLE，而 A 在持有 p->lock 期间设置 p->state = SLEEPING，两者互斥。A 要么在 wakeup 之前进入睡眠（B 能看到 SLEEPING 并唤醒），要么 wakeup 先完成（A 进入睡眠后发现条件已满足，立刻被重新调度）。

四、时钟中断驱动的抢占式调度

4.1 完整的抢占路径

xv6 使用 RISC-V 的机器模式（M-mode）时钟中断来驱动抢占，路径如下：

CLINT 硬件到期
  └─→ M-mode 时钟中断（CPU 硬件触发）
        └─→ timervec（kernel/kernelvec.S，M-mode 中运行）
              ├─ 计划下次中断（修改 MTIMECMP += interval）
              ├─ 设置 S-mode 软件中断位（csrw sip, 2）
              └─ mret（返回）
                  └─→ S-mode 软件中断（CPU 立即处理）
                        ├─ 如果在用户态：trampoline.S → usertrap()
                        │    └─ devintr() 返回 2（时钟中断）
                        │    └─ if(which_dev == 2) yield()
                        └─ 如果在内核态：kernelvec.S → kerneltrap()
                             └─ if(which_dev == 2 && RUNNING) yield()

4.2 timervec（M-mode 时钟处理）

# kernel/kernelvec.S（约 90 行起）
timervec:
    # start.c 已经设置好 mscratch 指向的内存区域：
    # scratch[0,8,16]   : 寄存器暂存区
    # scratch[32]       : CLINT_MTIMECMP 地址（用于设置下次中断时间）
    # scratch[40]       : 中断间隔

    csrrw a0, mscratch, a0   # 将 scratch 区地址载入 a0（同时保存 a0 到 mscratch）
    sd a1, 0(a0)             # 保存 a1, a2, a3（临时保存，timervec 不能修改任何寄存器）
    sd a2, 8(a0)
    sd a3, 16(a0)

    # 计划下次时钟中断（MTIMECMP += interval）
    ld a1, 32(a0)    # CLINT_MTIMECMP 地址
    ld a2, 40(a0)    # 中断间隔（约 100ms）
    ld a3, 0(a1)     # 读取当前 MTIMECMP 值
    add a3, a3, a2   # MTIMECMP += interval
    sd a3, 0(a1)     # 写回 MTIMECMP

    # 向 S-mode 发送软件中断（设置 sip 的 SSIP 位）
    li a1, 2
    csrw sip, a1    # S-mode 软件中断 pending

    # 恢复寄存器，返回
    ld a3, 16(a0)
    ld a2, 8(a0)
    ld a1, 0(a0)
    csrrw a0, mscratch, a0
    mret            # 返回被中断的地方（可能是用户态或内核态）

M-mode → S-mode 的中断转发：xv6 在 start.c 中设置时钟中断委托——M-mode 的时钟中断不转发到 S-mode（RISC-V 不支持直接转发时钟中断到 S-mode），而是由 timervec 通过设置 sip 的 SSIP 位（Supervisor Software Interrupt Pending）来触发一个 S-mode 软件中断，再由 S-mode 统一处理。

4.3 clockintr() 与 ticks

S-mode 的软件中断被 devintr() 识别为 which_dev == 2（时钟中断），调用 clockintr()：

// kernel/trap.c
void
clockintr()
{
  acquire(&tickslock);
  ticks++;              // 全局 tick 计数器 +1
  wakeup(&ticks);       // 唤醒所有调用 sys_sleep 等待时间的进程
  release(&tickslock);
}

ticks 是 xv6 的全局时钟计数，单位是”tick”（约 10ms/tick，取决于 CLINT 的中断间隔设置）。sys_sleep(n) 通过 sleep(&ticks, ...) 等待 ticks 增加 n 次来实现定时睡眠。

4.4 完整的 yield() 触发时序

用户态进程 A 运行...
  ↓（时钟中断）
trampoline.S/uservec：
  保存 A 的 32 个用户寄存器到 trapframe
  切换到内核页表
  切换到 A 的内核栈
  跳到 usertrap()

usertrap()：
  devintr() 返回 2（时钟中断）
  if(which_dev == 2) yield()

yield()：
  acquire(&A->lock)
  A->state = RUNNABLE
  sched()
    swtch(&A->context, &cpu->context)
    ── 切换到调度器 ──

scheduler()：
  swtch 返回，A->context 已保存
  release(&A->lock)
  ... 扫描，找到下一个 RUNNABLE 进程 B ...
  B->state = RUNNING
  swtch(&cpu->context, &B->context)
  ── 切换到进程 B ──

进程 B 的 sched() 接着运行：
  ... 从 yield() 或 sleep() 中的 sched() 返回 ...
  usertrapret()
    trampoline.S/userret：恢复 B 的用户寄存器，sret 返回用户态
用户态进程 B 运行...

五、kernelvec.S 与内核态中断处理

5.1 内核态中断为什么更简单？

Trap 在内核态发生时（进程正在内核中运行），处理比用户态 trap 简单：

  • 不需要切换页表（已经在内核页表）
  • 不需要切换栈（已经在内核栈）
  • 直接在当前栈上保存寄存器，调用处理函数

但内核态 trap 有一个特殊要求：必须保存所有 caller-saved 寄存器（t0-t6, a0-a7, ra），因为中断随时可能在任何内核代码执行时发生，被中断的代码可能正在使用这些寄存器。

5.2 kernelvec 的完整流程

# kernel/kernelvec.S
kernelvec:
    addi sp, sp, -256       # 在当前内核栈上腾出 256 字节

    # 保存所有 32 个通用寄存器（除了 tp，因为 tp 指向 hartid，切换 CPU 后可能变化）
    sd ra, 0(sp)
    sd sp, 8(sp)
    sd gp, 16(sp)
    sd tp, 24(sp)           # tp 保存了但恢复时跳过（见 ld tp 注释）
    sd t0, 32(sp)
    sd t1, 40(sp)
    # ... 全部 32 个寄存器 ...

    call kerneltrap          # 调用 C 函数处理中断

    # 恢复寄存器
    ld ra, 0(sp)
    ld sp, 8(sp)             # 恢复栈指针（回到中断前的位置）
    # 注意：不恢复 tp！（见下方注释）
    # ld tp, 24(sp)          # 跳过，因为 kerneltrap() 内部可能切换了 CPU
    ld t0, 32(sp)
    # ... 恢复其余寄存器 ...

    addi sp, sp, 256
    sret                     # 返回被中断的内核代码

**为什么不恢复 tp**：tp（thread pointer）在 xv6 中存储 CPU 的 hartid（通过 r_tp() 获取）。如果 kerneltrap() 内部调用了 yield()，当前代码可能在另一个 CPU 上恢复——此时 tp 已经被正确地指向新 CPU 的 hartid，不能用保存的旧值覆盖。

5.3 kerneltrap() 中的 sepc 保存

void
kerneltrap()
{
  uint64 sepc = r_sepc();       // 被中断的内核代码的 PC
  uint64 sstatus = r_sstatus(); // 保存 sstatus 状态
  uint64 scause = r_scause();

  if((which_dev = devintr()) == 0)
    panic("kerneltrap");

  // 如果是时钟中断，强制当前进程让出 CPU
  if(which_dev == 2 && myproc() != 0 && myproc()->state == RUNNING)
    yield();

  // yield() 可能触发更多 trap（如时钟中断），导致 sepc 被修改
  // 所以在 yield() 之后必须恢复 sepc 和 sstatus
  w_sepc(sepc);
  w_sstatus(sstatus);
}

yield() 后恢复 sepc 的原因：yield() 会经历 sched() → swtch() → scheduler() 的切换，在这个过程中（以及进程下次被调度并回到 kerneltrap() 的 yield 调用点之后），其他中断可能已经发生并修改了 sepc。函数结束时必须恢复 sepc，才能让 sret（在 kernelvec.S 中）正确返回到被中断的内核代码。

六、完整的上下文切换状态机

6.1 进程状态与切换触发

进程状态转换图（调度相关部分）：

  RUNNABLE ──────────────────────────────────────→ RUNNING
     ↑      scheduler() 选中，swtch() 切换          │
     │                                              │
     │ yield()（时钟中断/主动让出）                 │ sleep(chan, lk)
     │ RUNNING → RUNNABLE → sched()                │ RUNNING → SLEEPING → sched()
     │                                              ↓
     └─────────────────────────────────────── SLEEPING
                     wakeup(chan)
              SLEEPING → RUNNABLE

6.2 多核调度（NCPU > 1）

xv6 支持多 CPU，每个 CPU 运行独立的 scheduler() 循环：

CPU 0                               CPU 1
scheduler loop:                     scheduler loop:
  for p in proc[]:                    for p in proc[]:
    acquire(&p->lock)                   acquire(&p->lock)
    if RUNNABLE:                        if RUNNABLE:
      RUNNING + swtch                     RUNNING + swtch
    release(&p->lock)                   release(&p->lock)

两个 CPU 可以同时运行两个不同的进程。p->lock 保证同一个进程不会被两个 CPU 同时选中（state = RUNNING 在有锁的情况下修改，另一个 CPU 进来看到不是 RUNNABLE 就跳过）。

6.3 锁规则总结

xv6 调度代码的核心锁规则（违反会触发 panic）：

规则 原因
调用 sched() 前必须持有 p->lock sched() 内的 swtch 依赖 p->lock 跨越进程/调度器边界
调用 sched() 前 noff 必须为 1 持有多把锁切换会造成死锁
调用 sched() 前中断必须关闭 acquire() 已经关中断，确保此点
p->state 必须在调用 sched() 前改为非 RUNNING 调度器需要看到正确的状态
wakeup() 调用时不能持有目标进程的 p->lock wakeup 内部会 acquire(&p->lock)

八、思考题

  1. 为什么 sched() 要检查 mycpu()->noff != 1 而不是 noff != 0？能否在 noff == 0 时（中断开启、无锁时）调用 sched()？

    noff == 0 意味着中断是开启的（没有持有任何锁）。但 sched() 后面紧跟 swtch()，swtch 由汇编实现，期间没有对锁的操作。如果中断开启且无锁，时钟中断可能在 swtch 的任意指令之间到来，触发再次调度，导致调度器状态混乱。acquire(&p->lock)（yield() 的第一步）保证了 sched() 被调用时 noff == 1、中断是关闭的。

  2. scheduler() 每次都从 proc[0] 开始轮询，所有 CPU 都这样做。这会导致什么问题？xv6 中有没有缓解措施？

    在进程数量少时，靠近数组末尾的进程会被”饥饿”——每次调度都先检查前面的进程，后面的进程只有前面所有 RUNNABLE 进程都运行一次后才轮到。此外，多核情况下，多个 CPU 都对同一把锁（proc[0]->lock、proc[1]->lock…）竞争，产生锁竞争。xv6 没有缓解措施（它是教学系统，追求简单），现实 OS 会用 per-CPU 运行队列（减少锁竞争）和优先级/公平性算法（防止饥饿）。

  3. sleep() 的参数有两个：chan 和 lk。为什么需要 lk？能否去掉 lk 参数，让调用者自己持有 p->lock 再调用 sleep(chan, &p->lock)？

    lk 的作用是保护”检查条件”与”进入睡眠”之间的原子性。调用模式是：

    acquire(&lk);                    // 获取条件保护锁
while(条件不满足)
sleep(chan, &lk);              // 释放 lk，睡眠，醒后重新获取 lk
// 此处条件已满足，处理数据...
release(&lk);

    如果让调用者自己先 acquire(&p->lock) 再调用，那调用者在 acquire(&p->lock) 和 acquire(&lk) 之间就同时持有两把锁，违反”最多持有一把进程锁”的规则。sleep(chan, lk) 内部原子地”交换”：在释放 lk 之前先获取 p->lock，确保 wakeup 无法在检查条件和进入睡眠之间插入。

  4. wakeup(chan) 遍历整个 proc[] 数组寻找匹配的睡眠进程。在 NPROC=64 的 xv6 中这还好，但如果进程数量达到 100 万呢？你会如何优化？

    可以为每个 chan 维护一个等待队列（linked list of sleeping processes），直接遍历该队列而非全部进程。Linux 使用 wait_queue_head_t，wakeup() 只遍历等待在该队列上的进程——时间复杂度从 O(NPROC) 降到 O(等待者数量)。xv6 省略了这个优化因为 NPROC=64，而且教学目的更重要。

  5. 一个进程调用 exit() 后，最终变成 ZOMBIE 状态，等待父进程的 wait() 来清理。如果父进程先 exit() 了（成为孤儿进程），谁来 wait() 它？

    exit() 内部调用 reparent(p)，将所有子进程的 parent 指针改为 initproc（PID=1 的 init 进程）。user/init.c 中，init 进程运行一个无限循环，不断调用 wait(0) 收割 ZOMBIE 子进程——这就是 init 作为”收割孤儿”的首要职责之一。如果没有 init 的 wait() 循环，孤儿进程的 ZOMBIE 状态会永远持续，其 struct proc 槽位永远不会被释放，最终导致进程表溢出（再也无法 fork() 新进程）。

  6. scheduler() 的 intr_on() 在循环开始执行。若当时没有 RUNNABLE 进程，执行 wfi。如果时钟中断到来，CPU 从 wfi 醒来，devintr() 返回 2（时钟中断），此时 myproc() 返回什么？kerneltrap() 中的 if(which_dev == 2 && myproc() != 0 && myproc()->state == RUNNING) 这个条件是否会执行 yield()？

    调度器运行时 cpu->proc == 0（c->proc = 0 在 scheduler 初始化时设置，每次 swtch 回来后也清零），所以 myproc() 返回 NULL。kerneltrap() 中的条件 myproc() != 0 为假，不会执行 yield()——这是正确的，调度器本身不应该被 yield，否则它会陷入无限递归。时钟中断只让 clockintr() 更新 ticks 并唤醒等待定时器的进程，然后 CPU 回到 scheduler() 的轮询循环，再次寻找 RUNNABLE 进程。

九、本节小结

概念 要点
协作式让出 yield() → sched() → swtch() → scheduler
抢占式调度 时钟中断 → timervec → S-mode 软件中断 → yield()
swtch() 仅保存/恢复 14 个 callee-saved 寄存器（ra, sp, s0-s11）
ra 的作用 保存线程下次被恢复时的执行起点（而非真正的”返回地址”）
调度器线程 每个 CPU 独立运行，cpu->context 是调度器的内核栈
两跳设计 进程→调度器→进程，避免同时持有多把进程锁
sched() 的前置条件 持有 p->lock、noff==1、中断关闭、状态非 RUNNING
sleep(chan, lk) 原子地”交换”：持有 p->lock 后释放 lk，防止丢失唤醒
wakeup(chan) 遍历 proc[] 将 SLEEPING && chan==chan 的进程设为 RUNNABLE
clockintr() 每 tick 更新全局 ticks，唤醒等待时间的进程
wfi 无 RUNNABLE 进程时节省电能，等待中断唤醒
多核调度 每个 CPU 独立轮询 proc[]，p->lock 防止同一进程被多个 CPU 选中
