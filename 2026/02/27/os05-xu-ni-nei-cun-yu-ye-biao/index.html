第 5 节：虚拟内存与页表

学习目标：深入理解 RISC-V Sv39 三级页表机制，掌握 xv6 内核地址空间和用户地址空间的设计，能够独立阅读并理解 vm.c 中所有 442 行代码。

预计用时：4-5 小时

前置要求：完成第 4 节，理解物理页分配机制（kalloc()/kfree()）

一、理论：虚拟内存的核心问题

1.1 为什么需要虚拟内存？

没有虚拟内存，操作系统会面临三个根本性问题：

问题 1：隔离性

没有虚拟内存时：
  进程 A 的代码在物理地址 0x80000000
  进程 B 的代码在物理地址 0x80010000
  进程 A 可以直接读写进程 B 的内存！→ 安全漏洞

问题 2：灵活性

没有虚拟内存时：
  每个进程必须知道自己在物理内存的哪个位置
  编译器无法假设程序加载到固定地址（0x0）
  进程之间的内存必须连续，无法碎片化利用

问题 3：空间

没有虚拟内存时：
  进程的内存大小受限于物理 RAM
  无法使用 swap（磁盘扩展内存）

虚拟内存的解决方案：每个进程看到的是一个假想的、独立的地址空间（虚拟地址空间）。CPU 在访问内存时，硬件自动将虚拟地址翻译为物理地址。这个翻译由页表完成。

1.2 RISC-V Sv39：三级页表

xv6 使用 RISC-V 的 Sv39 分页方案：

  • 39 位虚拟地址：最大虚拟地址空间 = 2³⁹ = 512 GB（如此充裕以至于 xv6 只用了极小一部分）
  • 4KB 页：12 位页内偏移（2¹² = 4096）
  • 三级页表：每级 9 位索引
64 位虚拟地址的结构（只有低 39 位有效）：
┌──────────────┬──────────┬──────────┬──────────┬──────────────┐
│   保留（高位）  │  VPN[2]  │  VPN[1]  │  VPN[0]  │   页内偏移    │
│    63..39    │  38..30  │  29..21  │  20..12  │    11..0     │
│   25 bits    │  9 bits  │  9 bits  │  9 bits  │   12 bits    │
└──────────────┴──────────┴──────────┴──────────┴──────────────┘
              第2级索引      第1级索引      第0级索引    字节偏移
              （L2 VPN）    （L1 VPN）    （L0 VPN）

代码中的宏：PX(2, va)    PX(1, va)    PX(0, va)

地址翻译过程（硬件自动完成）：

给定虚拟地址 va：

  satp 寄存器
  ↓
  [L2 页表页] → 通过 PX(2, va) 找到 PTE₂
  ↓ PTE₂ 中的 PPN（物理页号）
  [L1 页表页] → 通过 PX(1, va) 找到 PTE₁
  ↓ PTE₁ 中的 PPN
  [L0 页表页] → 通过 PX(0, va) 找到 PTE₀
  ↓ PTE₀ 中的 PPN
  物理页起始地址 + 页内偏移 = **物理地址**

直观图示：

虚拟地址：0x0000003fffffd000（TRAMPOLINE 的例子）
  VPN[2] = 0xFF = 511
  VPN[1] = 0x1FF = 511
  VPN[0] = 0x1FD = 509
  offset = 0x000

satp → [L2 页表，512个PTE] → PTE[511] → PPN
                                              ↓
                               [L1 页表，512个PTE] → PTE[511] → PPN
                                                                    ↓
                                              [L0 页表，512个PTE] → PTE[509] → PPN
                                                                                   ↓
                                                                        物理地址 (PPN << 12) + 0x000

1.3 页表项（PTE）的结构

每个 PTE 是一个 64 位的整数：

PTE（64位）：
┌──────────────────────────────────┬────────────┬──────────────────┐
│             保留（高位）           │  PPN（物理页号） │    标志位（低10位） │
│              63..54              │   53..10   │      9..0        │
│              10 bits             │  44 bits   │     10 bits      │
└──────────────────────────────────┴────────────┴──────────────────┘

标志位（低10位）：
  bit 0: V（Valid）       — 此 PTE 是否有效
  bit 1: R（Readable）    — 是否可读
  bit 2: W（Writable）    — 是否可写
  bit 3: X（Executable）  — 是否可执行
  bit 4: U（User）        — 用户态是否可访问（0=仅内核可访问）
  bit 5: G（Global）      — 全局映射（xv6 不使用）
  bit 6: A（Accessed）    — 访问位（xv6 不使用）
  bit 7: D（Dirty）       — 修改位（xv6 不使用）
  bit 8: RSW（Reserved）  — 软件自用
  bit 9: RSW

判断 PTE 类型的规则（RISC-V 规范）：

PTE 类型 R/W/X 标志 含义
非叶节点（中间页表） R=W=X=0 指向下一级页表
叶节点（实际映射） R/W/X 至少一个为 1 映射到物理页

这就是为什么 freewalk() 中用 (pte & (PTE_R|PTE_W|PTE_X)) == 0 来判断是否是指向下一级页表的 PTE。

1.4 地址转换宏详解

kernel/riscv.h 中定义了页表操作的核心宏：

#define PGSIZE 4096              // 每页 4096 字节
#define PGSHIFT 12               // 页内偏移占 12 位

// 向上/向下对齐到页边界
#define PGROUNDUP(sz)  (((sz)+PGSIZE-1) & ~(PGSIZE-1))
#define PGROUNDDOWN(a) (((a)) & ~(PGSIZE-1))

// PTE 标志位
#define PTE_V (1L << 0)  // Valid
#define PTE_R (1L << 1)  // Read
#define PTE_W (1L << 2)  // Write
#define PTE_X (1L << 3)  // Execute
#define PTE_U (1L << 4)  // User

// 物理地址 → PTE 中的 PPN 字段
// 物理地址右移 12 位（去掉页内偏移）再左移 10 位（给标志位腾位置）
#define PA2PTE(pa) ((((uint64)pa) >> 12) << 10)

// PTE 中的 PPN 字段 → 物理地址
// PTE 右移 10 位（跳过标志位）再左移 12 位（还原页内偏移为0）
#define PTE2PA(pte) (((pte) >> 10) << 12)

// 提取 PTE 的低 10 位标志位
#define PTE_FLAGS(pte) ((pte) & 0x3FF)

// 从虚拟地址提取第 level 级的页表索引（VPN[level]）
#define PXMASK 0x1FF                        // 9 位掩码
#define PXSHIFT(level) (PGSHIFT+(9*(level))) // level=0: 12, level=1: 21, level=2: 30
#define PX(level, va) ((((uint64)(va)) >> PXSHIFT(level)) & PXMASK)

// Sv39 最大虚拟地址（比实际允许的最大值小 1 位，避免符号扩展问题）
#define MAXVA (1L << (9 + 9 + 9 + 12 - 1))  // = 2^38 = 256 GB

PA2PTE 和 PTE2PA 的计算示例：

设物理地址 pa = 0x80026000（某个物理页的起始地址）

PA2PTE(0x80026000):
  pa >> 12 = 0x80026000 >> 12 = 0x80026   // 物理页号 PPN
  0x80026 << 10 = 0x20009800             // PPN 移到 PTE 的 bit[53:10] 位置

PTE2PA(0x20009800 | PTE_V):             // PTE 的值（有 Valid 位）
  pte >> 10 = 0x20009800 >> 10 = 0x80026 // 提取 PPN
  0x80026 << 12 = 0x80026000             // 还原物理地址 ✓

1.5 satp 寄存器

satp（Supervisor Address Translation and Protection）寄存器控制分页：

satp（64位）：
┌──────┬──────────────────────┬───────────────────────────────────┐
│ MODE │        ASID          │              PPN                  │
│ 63-60│       59-44          │              43-0                 │
│ 4bit │       16bit          │              44bit                │
└──────┴──────────────────────┴───────────────────────────────────┘

MODE = 8 (Sv39) 时启用三级分页
PPN = 根页表（L2 页表）所在物理页的页号

xv6 中的宏：

#define SATP_SV39 (8L << 60)  // MODE=8 表示 Sv39
#define MAKE_SATP(pagetable) (SATP_SV39 | (((uint64)pagetable) >> 12))
// pagetable >> 12 就是根页表的物理页号 PPN

切换页表 = 写入 satp + 刷新 TLB：

void kvminithart() {
  w_satp(MAKE_SATP(kernel_pagetable));  // 切换到内核页表
  sfence_vma();                          // 刷新 TLB（使 satp 更改生效）
}

1.6 内核地址空间设计

xv6 内核使用直接映射（Identity Mapping）：绝大多数内核虚拟地址 = 物理地址。

内核虚拟地址空间（从低到高）：

0x0000000000000000
       │
       │ （未映射，访问会触发 page fault）
       │
0x0000000002000000  CLINT（0x2000000）
       │  大小 0x10000，R/W
0x000000000C000000  PLIC（0xC000000）
       │  大小 0x400000，R/W
0x0000000010000000  UART0（0x10000000）
       │  大小 0x1000，R/W
0x0000000010001000  VIRTIO0（0x10001000）
       │  大小 0x1000，R/W
       │
       │ （未映射）
       │
0x0000000080000000  KERNBASE（内核代码开始）
       │  内核 text（R/X）：KERNBASE → etext
       │  内核 data + 物理 RAM（R/W）：etext → PHYSTOP
0x0000000088000000  PHYSTOP（物理内存结束）
       │
       │ （未映射）
       │
       │ （很长一段未使用的虚拟地址空间）
       │
0x003fffffff000000  每个进程的内核栈（KSTACK(p)）
       │  KSTACK(p) = TRAMPOLINE - (p+1)*2*PGSIZE
       │  进程 63: ...
       │  保护页（无映射）
       │  进程 62 的内核栈（R/W）
       │  保护页（无映射）
       │  进程 0 的内核栈（R/W）
       │  保护页（无映射）
0x003ffffffe000000  （TRAMPOLINE 下方）
       │
0x003ffffffffffff000  TRAMPOLINE（最高一页，R/X）
       │  虚拟地址 = MAXVA - PGSIZE
       │  物理地址 = trampoline.S 代码的实际物理地址
       │  （在内核页表和用户页表中相同虚拟地址都映射到同一物理页）
0x0040000000000000  MAXVA（边界，不可访问）

重要特性：

  1. 直接映射区域（KERNBASE ~ PHYSTOP）：虚拟地址 = 物理地址，内核访问物理内存无需转换
  2. TRAMPOLINE：映射到最高虚拟地址，是用户态↔内核态切换的”跳板”代码，在用户页表和内核页表中都存在
  3. 内核栈：每个进程在内核地址空间中有一个专属的内核栈，两侧有保护页（无效 PTE），防止栈溢出蔓延

1.7 用户地址空间设计

用户进程的虚拟地址空间（从低到高）：

0x0000000000000000  text（代码段，R/X/U）
       │
       │  original data, BSS（R/W/U）
       │
       │  stack（固定大小，R/W/U）
       │  ← 保护页（无效 PTE，检测栈溢出）
       │
       │  heap（堆，R/W/U，随 sbrk() 增长）
       │  ...
       │
0x003fffffff000000  （空洞）
       │
       │  TRAPFRAME（R/W，不含 U 标志）
       │  = TRAMPOLINE - PGSIZE
       │  保存 trap 时的 32 个寄存器
       │
0x003ffffffffffff000  TRAMPOLINE（R/X，不含 U 标志）
       │  = MAXVA - PGSIZE
       │  与内核页表中相同虚拟地址映射到同一物理页
0x0040000000000000  MAXVA

关键设计问题：TRAMPOLINE 和 TRAPFRAME 没有 PTE_U 标志——用户程序无法直接访问它们，但它们存在于用户页表中，供内核（在用户页表的上下文中）访问。

二、源码精读：kernel/vm.c——完整 442 行（三个部分）

vm.c 是 xv6 中最大的单文件，承担三类职责：

功能分区 函数 说明
页表操作原语 walk(), walkaddr(), mappages(), uvmunmap() 增删改查页表项
内核地址空间 kvminit(), kvminithart(), kvmmap(), kvmpa() 建立和管理内核页表
用户地址空间 uvmcreate(), uvminit(), uvmalloc(), uvmdealloc(), uvmcopy(), uvmclear(), uvmfree(), freewalk() 用户进程内存的分配、释放、复制
内核↔用户数据拷贝 copyout(), copyin(), copyinstr() 跨地址空间的安全数据传输

2.1 全局变量和外部符号

kernel_pagetable 是内核的根页表（L2 页表）所在物理页的地址。它是 pagetable_t，即 uint64*——指向一个 512 个 PTE 的数组。

etext 由链接脚本 kernel.ld 定义，标记内核代码和只读数据的结束位置。etext 之前的内核内存用 PTE_R|PTE_X 映射（可读可执行），etext 之后用 PTE_R|PTE_W 映射（可读可写）。

第一部分：页表操作原语

2.2 walk()——三级页表遍历（最核心函数）

// 在页表 pagetable 中，找到虚拟地址 va 对应的 L0 级 PTE 的地址
// 如果 alloc!=0，则在需要时分配中间级页表页
// 返回 PTE 的指针，失败返回 0
pte_t *
walk(pagetable_t pagetable, uint64 va, int alloc)
{
  if(va >= MAXVA)
    panic("walk");

  for(int level = 2; level > 0; level--) {
    pte_t *pte = &pagetable[PX(level, va)];  // 取第 level 级的 PTE 指针
    if(*pte & PTE_V) {
      pagetable = (pagetable_t)PTE2PA(*pte); // PTE 有效：取下一级页表地址
    } else {
      if(!alloc || (pagetable = (pde_t*)kalloc()) == 0)
        return 0;           // 不允许分配，或内存不足 → 失败
      memset(pagetable, 0, PGSIZE);           // 清零新分配的页表页
      *pte = PA2PTE(pagetable) | PTE_V;       // 写入 PTE（只设 V 位，不设 R/W/X）
    }
  }
  return &pagetable[PX(0, va)];  // 返回 L0 级 PTE 的指针
}

逐行解析：

第一次循环（level=2）：
  pte = &pagetable[PX(2, va)]  ← L2 页表中，va 对应的 PTE 地址
  if has PTE_V → pagetable = 下一级 L1 页表的物理地址
  else if alloc → kalloc() 分配 L1 页表页，memset清零，写入 PTE（只设V位）
  else → 返回 0（不存在且不创建）

第二次循环（level=1）：
  pte = &pagetable[PX(1, va)]  ← L1 页表中，va 对应的 PTE 地址
  同上处理，得到 L0 页表的物理地址

循环结束（level=0，不进入循环体）：
  return &pagetable[PX(0, va)]  ← L0 页表中，va 对应的 PTE 地址（叶节点）

为什么中间级 PTE 只设 PTE_V，不设 R/W/X？

这是 RISC-V 规范的要求：

  • 叶节点 PTE（R/W/X 至少一位为 1）：直接映射到物理页
  • 中间节点 PTE（R=W=X=0）：指向下一级页表

如果中间节点设置了 R/W/X，硬件会把它当作叶节点处理，地址翻译就错了。

walk() 调用模式：

// 查找（不创建）：
pte_t *pte = walk(pagetable, va, 0);
if(pte == 0 || !(*pte & PTE_V)) {
    // 地址未映射
}

// 查找或创建：
pte_t *pte = walk(pagetable, va, 1);
if(pte == 0) {
    // 内存不足，无法创建中间页表
}

2.3 walkaddr()——查找用户地址的物理地址

// 在用户页表中，将虚拟地址 va 翻译为物理地址
// 失败返回 0
uint64
walkaddr(pagetable_t pagetable, uint64 va)
{
  pte_t *pte;
  uint64 pa;

  if(va >= MAXVA)
    return 0;

  pte = walk(pagetable, va, 0);    // 查找（不创建）
  if(pte == 0)
    return 0;
  if((*pte & PTE_V) == 0)          // PTE 无效（未映射）
    return 0;
  if((*pte & PTE_U) == 0)          // 没有用户访问权限
    return 0;
  pa = PTE2PA(*pte);
  return pa;
}

注意：walkaddr 只用于用户地址，因此会检查 PTE_U 标志。内核不需要 walkaddr 来访问内核地址——内核地址空间使用直接映射，虚拟地址 = 物理地址。

2.4 mappages()——建立虚拟→物理的映射

// 在页表 pagetable 中，为从 va 开始、大小为 size 的虚拟地址范围
// 建立到从 pa 开始的物理地址的映射，权限为 perm
// va 和 size 可以不是页对齐的
// 成功返回 0，walk() 分配失败返回 -1
int
mappages(pagetable_t pagetable, uint64 va, uint64 size, uint64 pa, int perm)
{
  uint64 a, last;
  pte_t *pte;

  a = PGROUNDDOWN(va);               // 起始地址向下对齐
  last = PGROUNDDOWN(va + size - 1); // 末尾地址向下对齐

  for(;;){
    if((pte = walk(pagetable, a, 1)) == 0)
      return -1;
    if(*pte & PTE_V)
      panic("remap");                // 重复映射同一地址是内核 bug
    *pte = PA2PTE(pa) | perm | PTE_V; // 写入 PTE：PPN + 权限 + Valid
    if(a == last)
      break;
    a += PGSIZE;
    pa += PGSIZE;
  }
  return 0;
}

执行流程示例：

假设要映射 va=0x80000000，size=0x2000（2页），pa=0x80000000，perm=PTE_R|PTE_X：

a    = PGROUNDDOWN(0x80000000) = 0x80000000
last = PGROUNDDOWN(0x80001FFF) = 0x80001000

循环 1：
  walk(pagetable, 0x80000000, 1) → 获取/创建 L0 PTE，写入：
  *pte = PA2PTE(0x80000000) | PTE_R | PTE_X | PTE_V
  a += PGSIZE → 0x80001000

循环 2：
  walk(pagetable, 0x80001000, 1) → 获取/创建 L0 PTE，写入：
  *pte = PA2PTE(0x80001000) | PTE_R | PTE_X | PTE_V
  a == last，break

panic("remap") 的含义：在正常的内核操作中，同一个虚拟地址不应该被映射两次。如果代码试图重新映射一个已有效的 PTE，说明有 bug。

2.5 uvmunmap()——解除映射

// 解除 pagetable 中从 va 开始的 npages 个页的映射
// va 必须页对齐，映射必须存在
// 如果 do_free 为 1，同时释放对应的物理页
void
uvmunmap(pagetable_t pagetable, uint64 va, uint64 npages, int do_free)
{
  uint64 a;
  pte_t *pte;

  if((va % PGSIZE) != 0)
    panic("uvmunmap: not aligned");

  for(a = va; a < va + npages*PGSIZE; a += PGSIZE){
    if((pte = walk(pagetable, a, 0)) == 0)
      panic("uvmunmap: walk");
    if((*pte & PTE_V) == 0)
      panic("uvmunmap: not mapped");
    if(PTE_FLAGS(*pte) == PTE_V)
      panic("uvmunmap: not a leaf");  // 只有 V 位=中间节点，不是叶节点
    if(do_free){
      uint64 pa = PTE2PA(*pte);
      kfree((void*)pa);               // 释放物理页
    }
    *pte = 0;                         // 清零 PTE（包括 V 位），使映射失效
  }
}

do_free 参数的两种用法：

  • do_free=1：解除映射 并 释放物理内存（进程终止时）
  • do_free=0：只解除映射，物理内存归还他处（如 exec 切换页表时）

第二部分：内核地址空间

2.6 kvminit()——创建内核页表

void
kvminit()
{
  kernel_pagetable = (pagetable_t) kalloc();  // 分配根页表（L2 页表）
  memset(kernel_pagetable, 0, PGSIZE);         // 清零（所有 PTE 初始无效）

  // UART0（串口寄存器，direct-map）
  kvmmap(UART0, UART0, PGSIZE, PTE_R | PTE_W);

  // VIRTIO0（磁盘 MMIO 接口）
  kvmmap(VIRTIO0, VIRTIO0, PGSIZE, PTE_R | PTE_W);

  // CLINT（核心本地中断控制器，时钟中断）
  kvmmap(CLINT, CLINT, 0x10000, PTE_R | PTE_W);

  // PLIC（平台级中断控制器）
  kvmmap(PLIC, PLIC, 0x400000, PTE_R | PTE_W);

  // 内核代码段：KERNBASE → etext（可读可执行，不可写）
  kvmmap(KERNBASE, KERNBASE, (uint64)etext-KERNBASE, PTE_R | PTE_X);

  // 内核数据段 + 剩余物理 RAM：etext → PHYSTOP（可读可写，不可执行）
  kvmmap((uint64)etext, (uint64)etext, PHYSTOP-(uint64)etext, PTE_R | PTE_W);

  // TRAMPOLINE：映射到最高虚拟地址（可读可执行）
  kvmmap(TRAMPOLINE, (uint64)trampoline, PGSIZE, PTE_R | PTE_X);
}

每次 kvmmap 调用的效果：

kvmmap(UART0=0x10000000, 0x10000000, 4096, PTE_R|PTE_W)
  → 虚拟地址 0x10000000 → 物理地址 0x10000000
  → 内核可以通过虚拟地址 0x10000000 直接访问 UART 寄存器

kvmmap(TRAMPOLINE=MAXVA-PGSIZE, trampoline物理地址, PGSIZE, PTE_R|PTE_X)
  → 虚拟地址 MAXVA-PGSIZE → 物理地址 trampoline 代码所在物理页
  → 注意：这不是直接映射！虚拟地址 ≠ 物理地址

为什么内核代码段不可写（没有 PTE_W）？

防止内核代码被意外或恶意修改。如果内核有 bug 导致写入了代码段，硬件会立即触发 page fault，而不是静默损坏代码。

为什么内核数据段不可执行（没有 PTE_X）？

NX（No-Execute）保护：防止数据被当作代码执行。即使攻击者向数据段注入了恶意代码，也无法执行（触发 page fault）。

2.7 kvminithart()——为当前 CPU 启用内核页表

void
kvminithart()
{
  w_satp(MAKE_SATP(kernel_pagetable));  // 将 satp 指向内核根页表
  sfence_vma();                          // 刷新 TLB
}

这个函数由每个 CPU 核心调用（见 main.c）。在此之前，CPU 没有启用分页（satp 为 0）——地址直接当物理地址使用。调用后，所有内存访问都经过页表翻译。

sfence_vma() 是 RISC-V 的内存屏障指令，确保对 satp 的写操作对所有后续内存访问可见，同时清空 TLB 缓存（旧的地址翻译缓存）。

2.8 kvmmap() 和 kvmpa()

// kvminit 期间使用的辅助函数，将任意失败转为 panic
void
kvmmap(uint64 va, uint64 pa, uint64 sz, int perm)
{
  if(mappages(kernel_pagetable, va, sz, pa, perm) != 0)
    panic("kvmmap");
}

// 将内核虚拟地址翻译为物理地址（走软件页表查询）
// 仅用于内核栈地址（不是直接映射区域）
uint64
kvmpa(uint64 va)
{
  uint64 off = va % PGSIZE;
  pte_t *pte;
  uint64 pa;
  
  pte = walk(kernel_pagetable, va, 0);
  if(pte == 0)
    panic("kvmpa");
  if((*pte & PTE_V) == 0)
    panic("kvmpa");
  pa = PTE2PA(*pte);
  return pa + off;  // 加上页内偏移，还原完整物理地址
}

kvmpa 的使用场景：内核栈的虚拟地址（KSTACK(p)）不在直接映射区域，必须通过软件走页表查询对应的物理地址。需要物理地址的场景是 virtio 磁盘驱动（DMA 操作需要物理地址）。

第三部分：用户地址空间管理

2.9 uvmcreate()——创建空用户页表

// 创建并返回一个空的用户页表（只分配根页表页，不建立任何映射）
// 内存不足时返回 0
pagetable_t
uvmcreate()
{
  pagetable_t pagetable;
  pagetable = (pagetable_t) kalloc();
  if(pagetable == 0)
    return 0;
  memset(pagetable, 0, PGSIZE);  // 所有 PTE 初始为 0（无效）
  return pagetable;
}

uvmcreate() 只分配根页表（L2）本身，不建立任何地址映射。返回的页表是”空的”——任何虚拟地址访问都会触发 page fault。

之后 exec() 会调用 mappages() 来逐步建立实际的地址映射。

2.10 uvminit()——加载第一个用户进程

// 将 initcode 加载到页表的虚拟地址 0（只用于第一个进程）
// sz 必须小于一页
void
uvminit(pagetable_t pagetable, uchar *src, uint sz)
{
  char *mem;

  if(sz >= PGSIZE)
    panic("inituvm: more than a page");
  mem = kalloc();                                    // 分配一个物理页
  memset(mem, 0, PGSIZE);                            // 清零
  mappages(pagetable, 0, PGSIZE, (uint64)mem,
           PTE_W|PTE_R|PTE_X|PTE_U);                 // 映射到虚拟地址 0
  memmove(mem, src, sz);                             // 复制代码
}

这个函数只用于 userinit()——启动第一个用户进程（运行 /init）的特殊路径。普通的程序加载通过 exec() + ELF 解析完成，不经过这个函数。

PTE_U 标志很关键：没有它，用户态 CPU 访问这个页会触发 page fault（即使映射存在）。

2.11 uvmalloc()——扩展用户进程内存（sbrk 的底层实现）

// 为用户进程分配更多内存，从 oldsz 增长到 newsz
// 同时分配物理页并建立映射
// 成功返回 newsz，失败返回 0
uint64
uvmalloc(pagetable_t pagetable, uint64 oldsz, uint64 newsz)
{
  char *mem;
  uint64 a;

  if(newsz < oldsz)
    return oldsz;          // 不需要缩小

  oldsz = PGROUNDUP(oldsz);  // 从 oldsz 的下一个页边界开始
  for(a = oldsz; a < newsz; a += PGSIZE){
    mem = kalloc();
    if(mem == 0){
      uvmdealloc(pagetable, a, oldsz);  // 分配失败：回滚已分配的页
      return 0;
    }
    memset(mem, 0, PGSIZE);  // 用户内存必须初始化为 0（安全要求！）
    if(mappages(pagetable, a, PGSIZE, (uint64)mem,
                PTE_W|PTE_X|PTE_R|PTE_U) != 0){
      kfree(mem);
      uvmdealloc(pagetable, a, oldsz);
      return 0;
    }
  }
  return newsz;
}

为什么用户内存必须清零（memset(mem, 0, PGSIZE)）？

安全考虑：新分配的物理页可能之前被其他进程使用过，包含敏感数据（密码、密钥等）。如果不清零，新进程可能读到它不该看到的数据——这是信息泄露漏洞。内核填充 0x05 只用于内核调试目的，用户空间分配必须清零。

失败时的回滚：如果第 k 页分配失败，必须调用 uvmdealloc(pagetable, a, oldsz) 将前 k-1 页已分配的内存释放，避免内存泄漏。

2.12 uvmdealloc()——收缩用户进程内存

// 将进程大小从 oldsz 缩小到 newsz
// 释放被解除映射的物理页
uint64
uvmdealloc(pagetable_t pagetable, uint64 oldsz, uint64 newsz)
{
  if(newsz >= oldsz)
    return oldsz;

  if(PGROUNDUP(newsz) < PGROUNDUP(oldsz)){
    int npages = (PGROUNDUP(oldsz) - PGROUNDUP(newsz)) / PGSIZE;
    uvmunmap(pagetable, PGROUNDUP(newsz), npages, 1);  // do_free=1，释放物理页
  }

  return newsz;
}

调用 uvmunmap 时 do_free=1，因此物理页会被 kfree() 归还给空闲链表。

2.13 freewalk()——递归释放页表结构

// 递归释放页表页本身（不释放叶节点映射的物理页，那必须事先已完成）
void
freewalk(pagetable_t pagetable)
{
  for(int i = 0; i < 512; i++){        // 遍历 512 个 PTE
    pte_t pte = pagetable[i];
    if((pte & PTE_V) && (pte & (PTE_R|PTE_W|PTE_X)) == 0){
      // 中间节点 PTE：递归释放下一级页表
      uint64 child = PTE2PA(pte);
      freewalk((pagetable_t)child);
      pagetable[i] = 0;
    } else if(pte & PTE_V){
      panic("freewalk: leaf");  // 叶节点还存在 → uvmfree 应先调用 uvmunmap
    }
  }
  kfree((void*)pagetable);    // 最后释放当前页表页本身
}

调用前提：调用 freewalk 之前，所有叶节点映射必须已被解除（通过 uvmunmap）。freewalk 只负责释放页表结构本身（中间节点和根节点），不负责释放用户数据页。

如果调用时还有叶节点存在，panic("freewalk: leaf") 会触发——这是一种防错机制，防止内存泄漏。

递归结构：

freewalk(L2 页表):
  对每个有效的中间 PTE：
    freewalk(L1 页表)
      对每个有效的中间 PTE：
        freewalk(L0 页表)
          kfree(L0 页表)
        清零 L1 中的 PTE
    kfree(L1 页表)
  清零 L2 中的 PTE
  kfree(L2 页表)

2.14 uvmfree()——释放整个用户地址空间

// 释放用户进程的所有地址映射和页表结构
void
uvmfree(pagetable_t pagetable, uint64 sz)
{
  if(sz > 0)
    uvmunmap(pagetable, 0, PGROUNDUP(sz)/PGSIZE, 1);  // ① 释放所有用户数据页
  freewalk(pagetable);                                  // ② 释放页表结构
}

两步操作的顺序：

  1. 先 uvmunmap（叶节点：释放用户数据的物理页）
  2. 再 freewalk（树结构：释放页表页本身）

不能颠倒顺序，否则步骤 1 无法遍历页表（页表已被释放）。

2.15 uvmcopy()——复制父进程地址空间（fork 使用）

// 将父进程页表 old 的所有映射和物理内存复制到子进程页表 new
// 同时复制页表结构和物理内容
// 成功返回 0，失败返回 -1（并回滚已复制的内存）
int
uvmcopy(pagetable_t old, pagetable_t new, uint64 sz)
{
  pte_t *pte;
  uint64 pa, i;
  uint flags;
  char *mem;

  for(i = 0; i < sz; i += PGSIZE){
    if((pte = walk(old, i, 0)) == 0)
      panic("uvmcopy: pte should exist");
    if((*pte & PTE_V) == 0)
      panic("uvmcopy: page not present");
    pa = PTE2PA(*pte);                // 父进程的物理页地址
    flags = PTE_FLAGS(*pte);          // 继承同样的权限标志
    if((mem = kalloc()) == 0)         // 为子进程分配新物理页
      goto err;
    memmove(mem, (char*)pa, PGSIZE);  // 复制物理页内容
    if(mappages(new, i, PGSIZE, (uint64)mem, flags) != 0){
      kfree(mem);
      goto err;
    }
  }
  return 0;

 err:
  uvmunmap(new, 0, i / PGSIZE, 1);  // 回滚：释放已复制的部分
  return -1;
}

uvmcopy 实现的是写时复制（Copy-on-Write，CoW）的简化版——xv6 直接复制所有页的物理内容。这比 Linux 的 CoW 效率低（多消耗物理内存），但实现简单。MIT 6.S081 的 COW lab 就是要求学生为 xv6 实现真正的 CoW。

为什么用 goto err？ 这是 C 语言中用于错误清理的经典模式，相当于 C++ 的异常处理。当内存分配失败时，需要释放已经分配的所有内存，goto err 跳到统一的清理代码。

2.16 uvmclear()——清除 PTE_U 标志（栈保护页）

// 清除某个页的用户访问权限（PTE_U 标志）
// exec 用于设置用户栈的保护页
void
uvmclear(pagetable_t pagetable, uint64 va)
{
  pte_t *pte;
  pte = walk(pagetable, va, 0);
  if(pte == 0)
    panic("uvmclear");
  *pte &= ~PTE_U;  // 清除 U 位
}

在 exec() 中，用户栈下方有一个”保护页”：映射存在，但清除了 PTE_U。当用户程序栈溢出访问这个页时：

  • 页表中有映射（PTE_V=1）→ 硬件找到了 PTE
  • 但 PTE_U=0 → 用户态访问被拒绝 → page fault

这样可以检测并报告栈溢出，而不是默默损坏其他数据。

第四部分：内核↔用户数据拷贝

系统调用经常需要在内核和用户空间之间传递数据（例如，read() 将数据从内核缓冲区复制到用户缓冲区）。这不能直接用内存赋值，因为：

  1. 内核和用户进程使用不同的页表（不同的虚拟地址空间）
  2. 用户指针可能无效或恶意（需要验证）

2.17 copyout()——内核 → 用户

// 从内核地址 src 复制 len 字节到用户页表 pagetable 的虚拟地址 dstva
// 成功返回 0，失败返回 -1
int
copyout(pagetable_t pagetable, uint64 dstva, char *src, uint64 len)
{
  uint64 n, va0, pa0;

  while(len > 0){
    va0 = PGROUNDDOWN(dstva);            // 目标地址所在页的起始虚拟地址
    pa0 = walkaddr(pagetable, va0);      // 翻译为物理地址（同时验证合法性）
    if(pa0 == 0)
      return -1;                         // 用户地址无效
    n = PGSIZE - (dstva - va0);          // 当前页还剩多少字节
    if(n > len)
      n = len;
    memmove((void*)(pa0 + (dstva - va0)), src, n);  // 复制到物理地址

    len -= n;
    src += n;
    dstva = va0 + PGSIZE;               // 移到下一页
  }
  return 0;
}

分页处理的必要性：

假设用户缓冲区跨越了两个页（例如，缓冲区的后半部分在下一页）：

用户虚拟地址空间：
┌─────────────────────┬─────────────────────┐
│    第 N 页           │    第 N+1 页         │
│  [----缓冲区前半----→│←---缓冲区后半------] │
└─────────────────────┴─────────────────────┘
   物理地址 pa0                物理地址 pa1

这两半在物理内存中可能完全不连续。copyout 每次处理一页：先处理从 dstva 到页末，再处理整个下一页，依此类推。

为什么不直接用虚拟地址复制？

内核和用户使用不同的页表。在内核模式下，CPU 使用内核页表（satp 指向 kernel_pagetable），用户的虚拟地址只在用户进程的页表中有效映射。内核必须先用 walkaddr 翻译到物理地址，才能真正访问用户内存。

2.18 copyin()——用户 → 内核

// 从用户页表的虚拟地址 srcva 复制 len 字节到内核地址 dst
int
copyin(pagetable_t pagetable, char *dst, uint64 srcva, uint64 len)
{
  uint64 n, va0, pa0;

  while(len > 0){
    va0 = PGROUNDDOWN(srcva);
    pa0 = walkaddr(pagetable, va0);
    if(pa0 == 0)
      return -1;
    n = PGSIZE - (srcva - va0);
    if(n > len)
      n = len;
    memmove(dst, (void*)(pa0 + (srcva - va0)), n);

    len -= n;
    dst += n;
    srcva = va0 + PGSIZE;
  }
  return 0;
}

逻辑与 copyout 对称，但方向相反：从用户空间（物理地址）复制到内核空间（内核直接访问）。

2.19 copyinstr()——从用户空间复制字符串

// 从用户虚拟地址 srcva 复制一个 NUL 结尾的字符串到内核地址 dst
// 最多复制 max 字节，找到 '\0' 时停止
// 成功（找到 '\0'）返回 0，未找到 '\0' 返回 -1
int
copyinstr(pagetable_t pagetable, char *dst, uint64 srcva, uint64 max)
{
  uint64 n, va0, pa0;
  int got_null = 0;

  while(got_null == 0 && max > 0){
    va0 = PGROUNDDOWN(srcva);
    pa0 = walkaddr(pagetable, va0);
    if(pa0 == 0)
      return -1;
    n = PGSIZE - (srcva - va0);
    if(n > max)
      n = max;

    char *p = (char*)(pa0 + (srcva - va0));
    while(n > 0){
      if(*p == '\0'){
        *dst = '\0';
        got_null = 1;
        break;
      } else {
        *dst = *p;
      }
      --n;
      --max;
      p++;
      dst++;
    }

    srcva = va0 + PGSIZE;
  }
  return got_null ? 0 : -1;  // 返回 0 仅当找到了 NUL 终止符
}

使用场景：系统调用 exec(path, argv) 需要从用户空间读取文件路径（字符串）。路径长度未知，必须逐字节扫描直到遇到 '\0'。max 参数防止内核被迫读取无限长的字符串（DoS 保护）。

三、深入理解：地址翻译的完整流程

3.1 一次用户态内存访问的全过程

假设用户程序执行 int x = arr[100]，arr 是虚拟地址 0x1000：

CPU 执行 "load 地址 0x1001B0"（假设 sizeof(int)=4，arr[100] 的偏移=400=0x190）

硬件查 TLB：
  TLB 中有 0x1000→物理页的缓存？
    是 → 直接使用，极快（< 1 ns）
    否 → 硬件页表遍历（Page Table Walk）：

虚拟地址 0x0000000000001190 的分解：
  VPN[2] = PX(2, 0x1190) = (0x1190 >> 30) & 0x1FF = 0
  VPN[1] = PX(1, 0x1190) = (0x1190 >> 21) & 0x1FF = 0
  VPN[0] = PX(0, 0x1190) = (0x1190 >> 12) & 0x1FF = 1
  offset =                   0x1190 & 0xFFF         = 0x190

硬件查 satp 中的根页表物理地址（假设为 0x87F6F000）：

步骤1：L2 页表（物理地址 0x87F6F000）的 PTE[0]
  = 0x87F6F000[0] = 某个有效 PTE，指向 L1 页表（假设 0x87F87000）

步骤2：L1 页表（物理地址 0x87F87000）的 PTE[0]
  = 0x87F87000[0] = 某个有效 PTE，指向 L0 页表（假设 0x87F96000）

步骤3：L0 页表（物理地址 0x87F96000）的 PTE[1]
  = 0x87F96000[8] （每个 PTE 8 字节，PTE[1] 在偏移 8 处）
  = 某个有效 PTE：PPN=0x87F70，flags=PTE_R|PTE_W|PTE_U|PTE_V

物理地址 = (0x87F70 << 12) + 0x190 = 0x87F70190

CPU 从物理地址 0x87F70190 读取 4 字节（int 的值）
TLB 缓存 0x1000→0x87F70000 的映射（下次访问同一页更快）

3.2 内核地址空间的 TLB 刷新时机

TLB 必须刷新（sfence_vma）的两种情况：

① 写入 satp（切换页表）：
   每次从用户态进入内核（trap）会切换到内核页表
   每次从内核返回用户态会切换到用户页表
   → 但 xv6 实际并不在 trap 时切换 satp！
   （xv6 的内核 trap 处理在内核页表下执行，trampoline 负责切换）

② 修改了页表内容：
   mappages() 新增映射 → 不需要刷新（新条目不在 TLB 中）
   uvmunmap() 删除映射 → 必须刷新！（TLB 可能仍缓存旧映射）
   uvmcopy() 后不需要刷新（子进程有全新的页表）

xv6 的实际做法：xv6 在 kvminithart() 中刷新一次 TLB，之后没有显式的 TLB 刷新——这是因为 xv6 的 trap 路径（trampoline.S）会在切换 satp 后执行 sfence.vma。

四、宏观理解：页表在系统中的位置

4.1 页表与进程的关系

每个进程都有一个独立的用户页表，内核有一个全局的内核页表：

内核（共享）
  kernel_pagetable（全局）
  → 内核代码、数据、MMIO、TRAMPOLINE
  → 64 个内核栈（每进程一个）

进程 0         进程 1         进程 2
p->pagetable   p->pagetable   p->pagetable
→ 用户代码    → 用户代码    → 用户代码
→ 用户数据    → 用户数据    → 用户数据
→ 用户栈      → 用户栈      → 用户栈
→ TRAPFRAME   → TRAPFRAME   → TRAPFRAME
→ TRAMPOLINE  → TRAMPOLINE  → TRAMPOLINE
  （所有用户页表中的 TRAMPOLINE 都映射到同一物理页）

进程切换时的页表切换：当调度器切换到进程 P 时，trampoline.S 中会执行 csrw satp, t1，将 satp 切换为 P 的用户页表。这样 P 就只能访问自己的地址空间，实现了进程隔离。

用户程序 sbrk(n)
  └→ sys_sbrk()
    └→ growproc(n)
      └→ uvmalloc(p->pagetable, oldsz, newsz)   ← 扩展
        ├→ kalloc()                               ← 分配物理页
        └→ mappages(p->pagetable, va, sz, pa, perm)

      │  ├→ kalloc()                                ← 分配子进程物理页
      │  ├→ memmove()                               ← 复制物理页内容
      │  └→ mappages(new, i, PGSIZE, mem, flags)
      └→ ...

用户程序 exit()
  └→ sys_exit()
    └→ exit()
      └→ freeproc()
        └→ proc_freepagetable(p->pagetable, sz)
          ├→ uvmunmap(TRAMPOLINE, 1 page, 0)        ← 不释放物理页（共享）

{
  printf("--- vmwalk va=%p ---\n", va);
  printf("VPN[2]=%d VPN[1]=%d VPN[0]=%d offset=%d\n",
         PX(2,va), PX(1,va), PX(0,va), va & (PGSIZE-1));

               (void*)(PTE2PA(*pte) | (va & (PGSIZE-1))));
      }
    } else {
      printf(" (INVALID)\n");
      break;
    }
    pagetable = (pagetable_t)PTE2PA(*pte);
  }
}

六、思考题

  1. walk() 的循环是 for(int level = 2; level > 0; level--)，注意条件是 level > 0，循环体内不处理 level=0。最后一行 return &pagetable[PX(0, va)] 才处理 L0。为什么这样设计，而不是把循环改成 level >= 0 并在循环体内返回？

    因为 L2 和 L1 的处理逻辑完全相同（找到下一级页表），而 L0 的处理不同（返回叶节点 PTE 的指针，不继续深入）。将 L0 特殊处理，使循环逻辑简洁统一。

  2. mappages() 中有 panic("remap")，但 xv6 某些地方确实需要修改已有的映射（例如内核栈初始化），这会不会触发 panic？

    不会。mappages 只在建立新映射时调用，修改已有映射应该先 uvmunmap 再 mappages，或者直接通过 walk() 拿到 PTE 指针修改。kvmmap 在 kvminit 初始化阶段调用，每个地址range只映射一次，不会触发 remap。

  3. 用户进程调用 free() 释放堆内存，实际上会调用到内核的哪个函数？

    用户的 free() 是 umalloc.c 实现的用户态分配器，它只管理用户进程的虚拟地址空间，不立即调用系统调用。只有当 free() 决定将大块内存还给内核时，才会调用 sbrk() → sys_sbrk() → growproc() → uvmdealloc() → uvmunmap() (do_free=1) → kfree()。

  4. 内核对用户内存的访问必须通过 copyin/copyout，为什么不能直接用用户传来的指针？

    因为用户传来的是用户虚拟地址，在内核页表下这个地址要么未映射（触发 panic），要么映射到完全不同的物理地址（内核的直接映射区域）。copyin/copyout 通过 walkaddr() 在用户页表中翻译地址，确保访问到用户进程真正的数据。此外，直接使用用户指针是安全漏洞（TOCTOU、越权访问），walkaddr 验证地址是否有效且具有 U 权限。

  5. TRAMPOLINE 页在用户页表中没有 PTE_U 标志，那切换到用户态后，用户程序有可能访问 TRAMPOLINE 地址吗？

    不能。用户态 CPU 访问没有 PTE_U 的页会触发 Page Fault（store/load/instruction page fault），进入内核的 trap 处理程序。trap 处理程序会检查原因并终止进程。这是一个重要的保护：trampoline 代码（ecall 的处理程序）必须在特权模式下运行，用户绝对不能直接调用它。

  6. freewalk() 为什么不处理叶节点的物理内存释放，这是否会造成内存泄漏？

    freewalk() 的前置条件是：所有叶节点（用户数据页）必须已经被 uvmunmap(..., do_free=1) 释放。uvmfree() 保证先调用 uvmunmap 再调用 freewalk，因此不会泄漏。如果在叶节点未清空时调用 freewalk，它会 panic("freewalk: leaf")——这是主动防错，而不是无声泄漏。

七、本节小结

概念 要点
Sv39 虚拟地址 39位 = VPN2 + VPN1 + VPN0 + offset(12)
PTE 结构 PPN(44位) + 标志位(10位)；中间节点 R/W/X=0，叶节点至少一个为 1
walk() 遍历三级页表，返回 L0 PTE 的指针，alloc≠0 时创建中间级页表
mappages() 建立 va→pa 映射，逐页调用 walk() 写入 PTE
内核地址空间 大部分直接映射（va=pa），TRAMPOLINE 例外映射到最高地址
用户地址空间 从 0 开始，顶部是 TRAPFRAME 和 TRAMPOLINE（无 PTE_U）
kvminit() 建立内核页表：MMIO 设备、内核代码（R/X）、内核数据（R/W）、TRAMPOLINE
uvmalloc() 扩展用户空间：kalloc() + memset(0) + mappages()
uvmcopy() fork 的内存复制：逐页 kalloc + memmove + mappages
uvmfree() 进程退出：uvmunmap(释放数据页) + freewalk(释放页表页)
copyout/copyin 内核↔用户数据拷贝：walkaddr 翻译地址，逐页 memmove
TLB 刷新 sfence_vma()；写 satp 后必须刷新
