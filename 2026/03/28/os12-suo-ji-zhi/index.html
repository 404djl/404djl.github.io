第 12 节：锁机制

学习目标：理解并发编程中竞态条件的本质，掌握 xv6 的两种锁——自旋锁（spinlock）和睡眠锁（sleeplock）的实现原理与适用场景；深入分析关中断与锁的关系；理解死锁的成因与避免策略；综合运用锁的分析方法阅读 xv6 各子系统的并发控制。

预计用时：3-4 小时

前置要求：完成第 8 节（进程调度与上下文切换），理解 sleep()/wakeup()、sched()、yield()；完成第 4 节（物理内存管理），了解 kalloc()/kfree()；了解多核（SMP）的基本概念

一、理论：为什么需要锁？

1.1 竞态条件（Race Condition）

xv6 运行在多核（SMP）硬件上，QEMU 默认模拟 4 个 CPU。多个 CPU 同时运行内核代码，可能并发访问同一块共享数据结构，就会产生竞态条件。

以 kalloc() 中的空闲链表为例，假设没有任何保护（去掉锁）：

时间线：

CPU 0                                   CPU 1
─────────────────────────────────────────────────────

r = kmem.freelist           →  [r 和 r1 都指向同一个链表头节点！]
                                r1 = kmem.freelist

kmem.freelist = r->next     →  kmem.freelist = r1->next
                               [两个 CPU 都觉得自己拿到了该节点，实际同一块内存]
return r;                       return r1;   ← 同一块物理内存被分配了两次！

这就是典型的竞态条件：两个 CPU 同时读取了链表头，然后各自把头节点移走——同一块内存被分配了两次，任何对这两块”内存”的写入都会互相覆盖，导致数据损坏甚至内核崩溃。

1.2 临界区（Critical Section）

临界区是指访问共享数据的那段代码序列，必须保证任意时刻只有一个执行上下文（CPU）在其中运行。锁的作用就是把临界区变成一个原子操作：

acquire(lock)          ← 进入临界区（其他 CPU 在此等待）
  // 读写共享数据    ← 临界区
release(lock)          ← 离开临界区（等待的 CPU 可以进入）

正确的原则是：每当访问多个并发执行流都会触碰的数据时，都必须持有锁。

1.3 不变量（Invariant）

理解锁还要理解不变量的概念。数据结构在并发访问之间维持的一致性条件称为不变量。例如 freelist 的不变量是：”链表头 kmem.freelist 指向第一个空闲页，通过 next 指针可以遍历所有空闲页，且每个空闲页只出现一次。”

  • 持有锁时：允许暂时破坏不变量（如修改链表头）
  • 释放锁前：必须恢复不变量（操作完成，链表重新一致）

这解释了为什么临界区必须整体持有锁——释放锁之前，其他 CPU 看不到中间状态。

1.4 两种锁的对比

xv6 提供两种锁，选择哪种取决于临界区的长短：

特性 自旋锁（spinlock） 睡眠锁（sleeplock）
等待方式 忙等待（循环检测，消耗 CPU） 阻塞睡眠（让出 CPU，待被唤醒）
适用场景 短临界区（几条指令，μs 级） 长临界区（如磁盘 I/O，ms 级）
持有期间 不能 sleep（会死锁） 可以 sleep
持有期间 必须 关闭中断 可以响应中断
实现基础 RISC-V amoswap 原子指令 自旋锁 + sleep/wakeup
典型用户 kmem.lock、p->lock、bcache.lock 每个 inode 上的 ip->lock

二、源码精读：kernel/spinlock.h——数据结构

// kernel/spinlock.h

struct spinlock {
  uint locked;       // 0 = 未持有；1 = 已被某 CPU 持有

  // 调试信息（不影响正确性）
  char *name;        // 锁的名字，用于 panic 时打印
  struct cpu *cpu;   // 当前持有该锁的 CPU（持有时有效）
};

字段分析：

  • locked：核心字段，0 表示空闲，1 表示被持有。
    • 对它的读-改-写必须是原子的，xv6 用 amoswap（原子交换）指令实现。
  • name、cpu：仅用于 holding() 的断言检查和崩溃调试。

struct cpu 中与锁相关的字段（来自 kernel/proc.h）：

struct cpu {
  struct proc *proc;   // 当前运行在此 CPU 上的进程（或 NULL）
  struct context context;  // 调度器的上下文
  int noff;            // push_off() 的嵌套深度（关中断计数）
  int intena;          // 最外层 push_off() 调用前中断是否开启
};

noff 和 intena 是实现安全关/开中断（push_off/pop_off）的关键，下面详述。

三、源码精读：kernel/spinlock.c——自旋锁实现

3.1 initlock()——初始化

void
initlock(struct spinlock *lk, char *name)
{
  lk->name = name;
  lk->locked = 0;   // 初始未持有
  lk->cpu = 0;      // 无 CPU 持有
}

在使用任何锁之前必须调用 initlock() 初始化。xv6 在各子系统初始化（kinit()、binit()、iinit() 等）时完成所有锁的初始化。

3.2 acquire()——获取锁

void
acquire(struct spinlock *lk)
{
  // ① 关中断（原因见 3.4 节）
  push_off();

  // ② 检测重复 acquire（死锁检测）
  if(holding(lk))
    panic("acquire");  // 同一 CPU 不能对同一把锁 acquire 两次（不可重入）

  // ③ 原子自旋：尝试将 locked 从 0 改为 1
  //
  // __sync_lock_test_and_set(&lk->locked, 1) 在 RISC-V 上编译为：
  //   a5 = 1
  //   amoswap.w.aq a5, a5, (lk->locked 的地址)
  //       → 原子地交换：a5 ← *addr, *addr ← a5
  //       → 返回交换前的旧值
  // 如果旧值为 0（锁空闲）→ 成功，退出循环
  // 如果旧值为 1（锁被持有）→ 失败，继续循环
  while(__sync_lock_test_and_set(&lk->locked, 1) != 0)
    ;   // 自旋忙等待

  // ④ 内存屏障：防止编译器/处理器将临界区的内存访问提前到这一行之前
  // 在 RISC-V 上生成 fence 指令
  __sync_synchronize();

  // ⑤ 记录调试信息
  lk->cpu = mycpu();
}

amoswap.w.aq 的 .aq（acquire）语义：

RISC-V 内存模型（RVWMO）中，.aq（acquire ordering）后缀确保这条指令之后的所有内存访问不能在处理器内部被提前到这条指令之前执行。这是正确实现锁的硬件保障，防止 CPU 乱序执行”提前”看到临界区内部的数据。

__sync_synchronize() 的作用：

这是 GCC 内建函数，生成一条完整的内存屏障（fence rw, rw）。它比 .aq/.rl 更强，双向禁止编译器和 CPU 对内存访问进行重排序。acquire() 在自旋成功后插入屏障，release() 则在清零前插入屏障——两者共同保证临界区的读写完全限制在 acquire 到 release 之间。

3.3 release()——释放锁

void
release(struct spinlock *lk)
{
  // ① 检测：必须持有才能释放（防止逻辑错误）
  if(!holding(lk))
    panic("release");

  // ② 清除调试信息（在 locked = 0 之前做，保持一致性）
  lk->cpu = 0;

  // ③ 内存屏障：确保临界区所有写操作对其他 CPU 可见后，再释放锁
  __sync_synchronize();

  // ④ 原子释放：将 locked 置 0
  // 编译为 amoswap.w.rl zero, zero, (addr)
  // .rl（release ordering）：这条指令之前的访问不能延迟到这条指令之后
  __sync_lock_release(&lk->locked);

  // ⑤ 恢复中断
  pop_off();
}

release() 的操作顺序非常重要：

必须先 __sync_synchronize() + __sync_lock_release() 释放锁，再 pop_off() 恢复中断。如果顺序颠倒（先开中断再释放锁），就可能在锁仍持有时响应中断，中断处理程序如果需要同一把锁就会自旋但永远无法获得（持有者在等中断返回），形成单 CPU 死锁。

3.4 holding()——检查锁持有者

int
holding(struct spinlock *lk)
{
  int r;
  // 检查：locked == 1 并且 持有者是当前 CPU
  r = (lk->locked && lk->cpu == mycpu());
  return r;
}

holding() 在 acquire() 和 release() 中用于断言检查，防止：

  • 同一 CPU 对同一把锁 acquire 两次（不可重入 → panic）
  • 没持有锁却调用 release（逻辑错误 → panic）

注意：调用 holding() 时中断必须已关闭（acquire() 内已由 push_off() 保证），否则另一个 CPU 可能在我们读 lk->cpu 的瞬间释放锁，导致读到错误的值。

3.5 push_off() / pop_off()——嵌套关中断

这是 xv6 中一个精心设计的小机制，解决锁与中断的交互问题：

void
push_off(void)
{
  int old = intr_get();   // 读取当前中断状态（是否开启）

  intr_off();             // 关闭中断
  if(mycpu()->noff == 0)  // 第一次关中断（最外层）
    mycpu()->intena = old; // 记住关中断前的状态（是否原本已开启）
  mycpu()->noff += 1;     // 关中断嵌套计数加 1
}

void
pop_off(void)
{
  struct cpu *c = mycpu();
  if(intr_get())           // 调用 pop_off 时中断应该是关的
    panic("pop_off - interruptible");
  if(c->noff < 1)          // 多余的 pop_off → 内部逻辑错误
    panic("pop_off");
  c->noff -= 1;            // 嵌套计数减 1
  if(c->noff == 0 && c->intena)  // 最后一层 pop，且原本中断是开的
    intr_on();             // 恢复开中断
}

为什么需要嵌套计数？

考虑以下代码：

acquire(&lock_A);          // push_off: noff=1, intena=1（原本开中断）
  acquire(&lock_B);        // push_off: noff=2（中断继续关）
  release(&lock_B);        // pop_off:  noff=1（中断仍然关，因为还持有 lock_A）
release(&lock_A);          // pop_off:  noff=0, intena=1 → 恢复开中断

如果用简单的 intr_off()/intr_on() 代替，release(&lock_B) 时就会过早开中断——此时还持有 lock_A，这是不安全的。push_off/pop_off 通过引用计数保证：只有当最后一把锁被释放时，才真正恢复中断。

为什么 acquire() 必须先关中断？

这是防止单 CPU 死锁的关键：

场景：CPU 0 持有 lock，此时响应一个中断
→ 中断处理程序也想 acquire(lock)
→ acquire 里自旋，永远等不到 lock 被释放
→ 死锁！（持有者在中断返回后才能 release，但中断处理程序在 acquire 里死等）

在 acquire() 的第一步关中断后，整个 持锁 → 操作 → 释锁 的过程中不会响应中断，消除了上述危险。

四、源码精读：kernel/sleeplock.c——睡眠锁实现

4.1 struct sleeplock 的设计

// kernel/sleeplock.h

struct sleeplock {
  uint locked;          // 睡眠锁本身的持有标志（0/1）
  struct spinlock lk;   // 保护 locked 和 pid 字段的自旋锁（元锁）

  // 调试信息
  char *name;           // 锁的名字
  int pid;              // 当前持有者的 PID
};

睡眠锁的核心思想：用一把自旋锁保护睡眠锁的状态字段。这里有两层锁：

  • 外层 sleeplock：被 inode 等对象持有，临界区较长（可能包含磁盘 I/O）
  • 内层 spinlock（lk）：仅用于保护 locked 和 pid 字段本身的读写（临界区极短），因此用自旋锁足够

4.2 acquiresleep()——获取睡眠锁

void
acquiresleep(struct sleeplock *lk)
{
  acquire(&lk->lk);           // ① 获取元锁（自旋锁），保护 lk->locked 的读写
  while (lk->locked) {        // ② 如果睡眠锁已被持有，循环等待
    sleep(lk, &lk->lk);       //    sleep(chan=lk, lk=&lk->lk)
    //  → 原子地：释放元锁 + 将当前进程状态设为 SLEEPING + 调用 sched()
    //  → 被 wakeup(lk) 唤醒后，重新获取元锁，继续检查 while 条件
  }
  lk->locked = 1;             // ③ 成功获取锁
  lk->pid = myproc()->pid;    // ④ 记录持有者
  release(&lk->lk);           // ⑤ 释放元锁
}

sleep(lk, &lk->lk) 的原子性：

sleep() 的调用看起来像是”先释放元锁，再睡眠”，实际上存在微妙之处——如果真的先释放再睡眠，就可能在释放元锁和睡眠的间隙被 wakeup() 唤醒信号错过（lost wakeup 问题）。

proc.c 中的 sleep() 实现通过同时持有 p->lock（进程锁）来解决这个问题：

// kernel/proc.c 中 sleep() 的关键逻辑（简化）
void sleep(void *chan, struct spinlock *lk) {
  struct proc *p = myproc();
  
  // 同时持有 p->lock 和 lk，然后释放 lk
  // wakeup() 需要 acquire(p->lock) 才能修改 p->state
  // 所以在我们完成 p->state = SLEEPING 之前，wakeup 不会漏掉我们
  acquire(&p->lock);
  release(lk);

  p->chan = chan;
  p->state = SLEEPING;  // 此时已持有 p->lock，wakeup 一定能看到
  sched();              // 切换到调度器

  p->chan = 0;
  release(&p->lock);
  acquire(lk);          // 醒来后重新获取元锁，回到 acquiresleep 的 while 循环
}

4.3 releasesleep()——释放睡眠锁

void
releasesleep(struct sleeplock *lk)
{
  acquire(&lk->lk);     // ① 获取元锁
  lk->locked = 0;       // ② 释放睡眠锁
  lk->pid = 0;          // ③ 清除持有者信息
  wakeup(lk);           // ④ 唤醒所有在 chan=lk 上等待的进程
  release(&lk->lk);     // ⑤ 释放元锁
}

wakeup(lk) 遍历进程表，将所有 p->chan == lk 的 SLEEPING 进程状态改为 RUNNABLE。这些进程在 sleep() 里等待，被唤醒后会重新 acquire 元锁，继续 acquiresleep() 中的 while (lk->locked) 检查——因此即使多个进程同时等待同一个睡眠锁，也只有一个能真正获得（其余会重新睡眠）。

4.4 自旋锁 vs 睡眠锁：持锁期间能否 sleep？

这是最重要的规则之一：

**持有自旋锁时绝对不能调用 sleep()**！

原因：sleep() 会调用 sched() 切换到调度器，进程让出 CPU 并进入睡眠状态。但它持有的自旋锁没有被释放——其他需要这把锁的进程/CPU 会一直自旋，而持有者睡着了，形成死锁。

sched() 中有专门的断言检查：

// kernel/proc.c
void sched(void) {
  // ...
  // 除了 p->lock，不允许持有任何其他自旋锁
  if(p->nlock != 1)
    panic("sched locks");
  // ...
}

p->nlock 记录当前进程持有的锁数量（通过 acquire/release 维护）。进入 sched() 时，必须只持有 p->lock 一把锁，否则 panic。这精确地保证了”睡眠时不持有自旋锁”的规则。

五、死锁：原因与避免

5.1 单 CPU 死锁（中断导致）

如 3.4 节分析：持有锁时若响应中断，中断处理程序再次获取同一把锁，就会死锁。

解决方案：acquire() 关中断，release() 恢复中断。

5.2 多 CPU 死锁（锁顺序不当）

经典场景——两个 CPU 以相反顺序获取两把锁：

CPU 0                    CPU 1
─────────────────────────────────────
acquire(&lock_A)         acquire(&lock_B)
acquire(&lock_B)  ←→    acquire(&lock_A)
   [等待 lock_B]            [等待 lock_A]
       ↑                       ↑
       └──────── 死锁 ──────────┘

两个 CPU 各持有一把锁，分别等待对方持有的锁，永远无法推进。

xv6 的解决方案：全局锁顺序协议

xv6 规定了所有锁的全局获取顺序，任何代码获取多把锁时必须按此顺序：

文件系统锁顺序（由粗到细）：

bcache.lock → inode.lock → ip->lock（sleeplock）→ log.lock

进程相关锁顺序：

p->lock（父进程）→ p->lock（子进程）

kmem.lock 独立使用（不与文件系统锁嵌套）

只要所有代码都遵守同一顺序（不存在”A 先然后 B”和”B 先然后 A”的情况），就不会形成死锁环。

5.3 sleep() 与锁的交互：避免 Lost Wakeup

sleep(chan, lk) 的接口设计要求调用者**持有 lk 进入 sleep()**，这是为了避免 lost wakeup：

// 错误写法（有 lost wakeup 风险）：
release(&lk);           // ← 这一时刻如果 wakeup() 发生，会被错过！
sleep(chan, NULL);

// 正确写法：
// 持有 lk 调用 sleep，sleep 内部会原子地释放 lk 并睡眠
sleep(chan, &lk);

sleep() 在持有 p->lock 的前提下释放 lk，使得 wakeup() 无法在”我们决定睡眠但还没真正睡着”的窗口内发生——这正是 acquiresleep() 中”while 循环 + sleep”模式能正确工作的基础。

六、锁在 xv6 各子系统中的应用

6.1 物理内存管理：kmem.lock

// kernel/kalloc.c
struct {
  struct spinlock lock;
  struct run *freelist;
} kmem;
  • 保护对象：freelist 链表（空闲物理页链表）
  • 临界区：kalloc() 中的链表头摘取，kfree() 中的链表头插入
  • 选择自旋锁原因：操作极短（几条指令），无需 sleep

6.2 进程表：p->lock（per-process）

每个 struct proc 有一把自旋锁，保护该进程 state、chan、killed、pid 等字段的读写。它在 xv6 中用途极广：

操作 为什么需要 p->lock
读/写 p->state 防止调度器和进程同时修改状态
sleep() / wakeup() 原子地改变状态和 chan，避免 lost wakeup
exit() / wait() 父子进程协作终止，防止 ZOMBIE 状态被漏掉
kill() 设置 p->killed，同时若进程在睡眠则唤醒它

6.3 块缓存：bcache.lock

// kernel/bio.c
struct {
  struct spinlock lock;
  struct buf buf[NBUF];
  struct buf head;   // LRU 链表头
} bcache;
  • 保护对象：缓冲区链表（head 双向链表）和各缓冲区的 refcnt
  • 选择自旋锁原因：查找和移动链表操作是短临界区；但每个 buf 自身的磁盘 I/O 操作由 buf.lock（sleeplock）保护

两层锁的设计：

bcache.lock（自旋锁）
 └─ 保护：查找缓冲区 + refcnt 增减 + LRU 链表调整（短操作）

buf.lock（sleeplock）
 └─ 保护：该缓冲区正在进行的磁盘读写（可能需要等待 I/O 完成，长操作）
 └─ 持有 buf.lock 时 → 可以 sleep（等磁盘）
 └─ 持有 buf.lock 时 → 不持有 bcache.lock（避免死锁）

6.4 文件系统 inode：ip->lock（sleeplock）

每个内存 inode（struct inode）有一把 sleeplock，保护 inode 的数据字段（type、size、addrs[] 等）和对应数据块的读写：

// kernel/file.h
struct inode {
  uint dev;          // 设备号
  uint inum;         // inode 编号
  int ref;           // 内存引用计数
  struct sleeplock lock;  // 保护以下字段
  int valid;         // 是否已从磁盘读入
  // ... type, nlink, size, addrs[]
};
  • 为什么用 sleeplock：文件读写（readi/writei）会调用 bread()，bread() 可能等待磁盘 I/O，必须 sleep。持有自旋锁时 sleep 是非法的，所以 inode 必须用 sleeplock。
  • ilock()/iunlock() 调用时机：只有在需要读/写 inode 的内容时才 ilock（持有时间尽量短）；只需要引用 inode（如修改 ref 计数）时用 icache.lock 自旋锁即可。

6.5 日志层：log.lock

// kernel/log.c
struct log {
  struct spinlock lock;
  // ...
  int outstanding;  // 当前未提交的事务数
  int committing;   // 是否正在提交
};
  • begin_op() / end_op() 用 log.lock 保护事务状态
  • 当 end_op() 发现可以提交时，调用 commit()；commit() 涉及大量磁盘写入，但此时已不持有 log.lock（避免长时间占锁）

6.6 管道：pi->lock

// kernel/pipe.c
struct pipe {
  struct spinlock lock;
  char data[PIPESIZE];  // 环形缓冲区
  uint nread, nwrite;   // 读写位置
  int readopen, writeopen;
};

pipewrite() 和 piperead() 用 pi->lock 保护缓冲区，并通过 sleep()/wakeup() 实现生产者-消费者同步——是个典型的”持有自旋锁调用 sleep”的场景（sleep() 会自动释放 pi->lock）。

七、综合图示：lock 的调用关系全景

用户进程调用 write(fd, buf, n)
        │
        ▼
sys_write() → filewrite()
        │
        ├─ [type==FD_INODE] → ilock(ip) ← 获取 sleeplock
        │       │ （允许 sleep，如等待磁盘）
        │       ▼
        │   writei() → bmap() → balloc()
        │       │            └── acquire(&bcache.lock)  ← 自旋锁
        │       │            └── release(&bcache.lock)
        │       ▼
        │   log_write(b) → acquire(&log.lock)           ← 自旋锁
        │                  release(&log.lock)
        │       ▼
        │   （磁盘 I/O：在 buf.lock sleeplock 下进行）
        │
        └─ iunlock(ip) ← 释放 sleeplock

持锁期间规则：
  sleeplock 内可以调用 sleep（如等待磁盘完成）
  spinlock  内不能调用 sleep（否则 panic）
  spinlock  内中断已关（由 push_off/pop_off 保证）

实验 1：观察竞态条件（去锁实验）

目标：直观感受没有锁保护时多核系统会发生什么。

}

char *

实验 2：追踪 push_off/pop_off 的嵌套层次

步骤：在 push_off() 中加入调试打印：

void
push_off(void)
{
  int old = intr_get();
  intr_off();
  if(mycpu()->noff == 0) {
    mycpu()->intena = old;
    printf("CPU %d: first push_off, intena=%d\n", cpuid(), old);
  }
  mycpu()->noff += 1;
  printf("CPU %d: push_off noff=%d\n", cpuid(), mycpu()->noff);
}

void
pop_off(void)
{
  struct cpu *c = mycpu();
  // ...（原有检查）
  c->noff -= 1;
  printf("CPU %d: pop_off noff=%d\n", cpuid(), c->noff);
  if(c->noff == 0 && c->intena) {
    printf("CPU %d: restoring interrupts\n", cpuid());
    intr_on();
  }
}

九、本节小结

概念 要点
竞态条件 多 CPU 并发访问共享数据，结果依赖执行顺序
临界区 必须原子执行的代码段，acquire/release 括住
自旋锁 忙等待；获取时关中断；不能持锁 sleep；适用短操作
睡眠锁 阻塞等待；可以持锁 sleep；适用长操作（如磁盘 I/O）
push_off / pop_off 嵌套关中断计数，确保最后一把锁释放时才恢复中断
amoswap RISC-V 原子交换指令，自旋锁的硬件基础
内存屏障 __sync_synchronize() / .aq / .rl，防止乱序破坏临界区语义
死锁避免 ① 关中断防单 CPU 死锁；② 全局锁顺序防多 CPU 死锁
Lost wakeup sleep(chan, lk) 设计：持有 lk 进入，原子地释放并睡眠

锁的黄金法则总结：

  1. 每个共享数据结构配一把锁，读写共享数据时必须持锁
  2. 持有自旋锁不能 sleep（会死锁），长临界区改用 sleeplock
  3. 多把锁按全局顺序获取（避免死锁环）
  4. acquire() 先关中断（避免中断处理程序重入同一把锁）
  5. 锁的粒度影响性能：粒度过大（全局锁）→ 并发度低；粒度过细 → 复杂度高、死锁风险大
