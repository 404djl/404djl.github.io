第 13 节：磁盘驱动与块缓存

学习目标：理解文件系统最底层的两个抽象层——VirtIO 磁盘驱动和块缓冲区缓存（block buffer cache）；掌握 VirtIO 协议的描述符环机制；深入分析 bio.c 中 LRU 缓存的设计；理解两层锁（bcache.lock + buf.lock）的协作关系。

预计用时：3-4 小时

前置要求：完成第 12 节（锁机制），理解自旋锁与睡眠锁的区别；完成第 11 节（Trap 与中断处理），了解外设中断的处理路径；理解 sleep()/wakeup() 同步机制

一、理论：文件系统的分层架构

xv6 文件系统是一个经典的七层抽象：

第 7 层  文件描述符（file descriptor）      ← sys_read/sys_write 的入口
第 6 层  路径名（pathname）                 ← namei()，"/a/b/c" → inode
第 5 层  目录（directory）                  ← dirlookup(), dirlink()
第 4 层  Inode（inode）                    ← ialloc(), iget(), readi(), writei()
第 3 层  日志（logging）                    ← begin_op(), end_op(), log_write()
第 2 层  块缓存（buffer cache）             ← bread(), bwrite(), brelse()   ← 本节重点
第 1 层  磁盘驱动（disk driver）            ← virtio_disk_rw()               ← 本节重点
          ↕ 物理磁盘（VirtIO Block Device）

本节关注最底两层，它们的职责分别是：

层次 职责 核心文件
磁盘驱动 通过 VirtIO MMIO 接口向 QEMU 虚拟磁盘发送读写命令，等待中断完成 kernel/virtio_disk.c、kernel/virtio.h
块缓存 在内存中缓存磁盘块，减少磁盘访问；保证同一块在内存中只有一份拷贝；用 LRU 策略淘汰旧缓存 kernel/bio.c、kernel/buf.h

1.1 块设备 vs 字符设备

特性 块设备（block device） 字符设备（char device）
访问粒度 固定大小的块（xv6 中 BSIZE = 1024 字节） 单个字符
可寻址 按块号随机访问 顺序访问
缓冲 系统自动缓冲（bcache） 通常不缓冲
典型硬件 磁盘、SSD、U 盘 UART、键盘、鼠标

xv6 的磁盘是块设备：所有 I/O 以 1024 字节（1 KB）的块为单位进行。上层文件系统通过块号（blockno）寻址，从不直接操作字节偏移量。

1.2 VirtIO 协议简介

QEMU 使用 VirtIO（Virtual I/O）标准让虚拟机与宿主机高效通信。xv6 使用的是 Legacy VirtIO MMIO 接口：

  • MMIO（Memory-Mapped I/O）：设备寄存器映射到固定物理地址（VIRTIO0 = 0x10001000），驱动通过普通内存读写操作控制设备
  • Virtqueue（虚拟队列）：驱动与设备之间的共享内存通信机制，xv6 使用其中的 Queue 0（blkq）

VirtQueue 由三个区域组成：

物理内存中（disk.pages，两个连续物理页）：

页 0 (4096 字节)：
  ┌────────────────────────────────────────────────┐
  │  Descriptor Table（描述符表）                    │
  │  8 项 × sizeof(VRingDesc) = 8 × 16 = 128 字节  │
  │  从 disk.pages 起始                             │
  ├────────────────────────────────────────────────┤
  │  Available Ring（可用环）                        │
  │  2 × uint16 头 + NUM × uint16 条目              │
  │  从 desc 表之后 0x40 偏移处                      │
  └────────────────────────────────────────────────┘

页 1 (4096 字节)：
  ┌────────────────────────────────────────────────┐
  │  Used Ring（已用环）                             │
  │  UsedArea 结构：flags(2) + id(2) + elems[NUM]  │
  └────────────────────────────────────────────────┘

三个角色：

  • 描述符表（Descriptor Table）：每个描述符描述一段内存（地址 + 长度 + 标志位 + 下一个描述符索引），多个描述符串成链表描述一次 I/O 请求
  • 可用环（Available Ring）：驱动写入，告诉设备”我准备好了这些描述符链，请处理”
  • 已用环（Used Ring）：设备写入，告诉驱动”我已完成这些描述符链对应的 I/O”

二、源码精读：kernel/virtio.h——VirtIO 数据结构

2.1 MMIO 寄存器偏移量

// kernel/virtio.h（节选）

// VirtIO MMIO 寄存器（基地址 VIRTIO0 = 0x10001000）
#define VIRTIO_MMIO_MAGIC_VALUE     0x000  // 魔数，必须为 0x74726976（"virt"）
#define VIRTIO_MMIO_VERSION         0x004  // 版本号，Legacy = 1
#define VIRTIO_MMIO_DEVICE_ID       0x008  // 设备类型：1=网卡, 2=块设备
#define VIRTIO_MMIO_VENDOR_ID       0x00c  // 厂商 ID，QEMU = 0x554d4551（"QEMU"）

// 特性协商寄存器
#define VIRTIO_MMIO_DEVICE_FEATURES 0x010  // 设备支持的特性（只读）
#define VIRTIO_MMIO_DRIVER_FEATURES 0x020  // 驱动选择的特性（只写）

// 队列配置寄存器
#define VIRTIO_MMIO_QUEUE_SEL       0x030  // 选择队列号（write）
#define VIRTIO_MMIO_QUEUE_NUM_MAX   0x034  // 队列最大大小（read）
#define VIRTIO_MMIO_QUEUE_NUM       0x038  // 设置队列大小（write）
#define VIRTIO_MMIO_QUEUE_PFN       0x040  // 队列物理页帧号（read/write）

// 中断寄存器
#define VIRTIO_MMIO_INTERRUPT_STATUS 0x060 // 中断原因（read）
#define VIRTIO_MMIO_INTERRUPT_ACK    0x064 // 确认中断（write）

// 设备状态寄存器
#define VIRTIO_MMIO_STATUS          0x070  // 驱动-设备握手状态（read/write）

状态寄存器的标志位按顺序累积写入，实现驱动-设备握手协议：

ACKNOWLEDGE(1) → DRIVER(2) → FEATURES_OK(8) → DRIVER_OK(4)

2.2 描述符结构：struct VRingDesc

struct VRingDesc {
  uint64 addr;   // 内存缓冲区的物理地址
  uint32 len;    // 缓冲区长度（字节）
  uint16 flags;  // 标志：VRING_DESC_F_NEXT(1) = 链式；VRING_DESC_F_WRITE(2) = 设备写
  uint16 next;   // 下一个描述符的索引（flags & NEXT 时有效）
};

#define VRING_DESC_F_NEXT  1  // 该描述符后面还有更多（链式）
#define VRING_DESC_F_WRITE 2  // 这段内存由设备写入（否则由设备读取）

一次磁盘读请求的三描述符链：

描述符 idx[0]：请求头（驱动→设备，只读）
  addr = &buf0（含 type/reserved/sector）
  len  = sizeof(struct virtio_blk_outhdr) = 16 字节
  flags = NEXT（还有下一个）

描述符 idx[1]：数据缓冲区（读操作时由设备写入）
  addr = b->data（1024 字节的块数据）
  len  = BSIZE = 1024 字节
  flags = WRITE | NEXT（设备写；还有下一个）

描述符 idx[2]：状态字节（由设备写入）
  addr = &disk.info[idx[0]].status
  len  = 1 字节
  flags = WRITE（设备写 0=OK，1=ERR，2=UNSUP）

三、源码精读：kernel/virtio_disk.c——磁盘驱动

3.1 disk 全局结构——驱动的核心状态

static struct disk {
  // VirtQueue 共享内存区：两个连续物理页（必须页对齐）
  char pages[2*PGSIZE];
  struct VRingDesc *desc;   // 描述符表，指向 pages 起始
  uint16 *avail;            // 可用环，紧跟描述符表后
  struct UsedArea *used;    // 已用环，在第二个页

  // 驱动侧簿记
  char free[NUM];           // free[i] = 1 表示 desc[i] 空闲（NUM = 8）
  uint16 used_idx;          // 驱动已处理到 used->elems 的哪个位置

  // 飞行中（in-flight）I/O 的信息（按描述符链首索引）
  struct {
    struct buf *b;    // 对应的缓冲区
    char status;      // 设备完成后写入的状态字节
  } info[NUM];

  struct spinlock vdisk_lock;   // 保护整个 disk 结构的访问
} __attribute__ ((aligned (PGSIZE))) disk;

为什么 disk.pages 不用 kalloc？

VirtQueue 要求描述符表、可用环、已用环分布在两个连续的、页对齐的物理页上。kalloc() 每次只分配一页（4096 字节）且不保证连续。因此 disk.pages 声明为全局静态变量，编译器保证其在 BSS 段中，__attribute__((aligned(PGSIZE))) 强制页对齐，两个连续页天然满足要求。

3.2 virtio_disk_init()——初始化与握手

void virtio_disk_init(void)
{
  uint32 status = 0;
  initlock(&disk.vdisk_lock, "virtio_disk");

  // ① 验证设备标识（防止误识别其他 MMIO 设备）
  if(*R(VIRTIO_MMIO_MAGIC_VALUE) != 0x74726976 ||   // "virt"
     *R(VIRTIO_MMIO_VERSION)     != 1            ||   // Legacy 版本
     *R(VIRTIO_MMIO_DEVICE_ID)   != 2            ||   // 块设备
     *R(VIRTIO_MMIO_VENDOR_ID)   != 0x554d4551)       // "QEMU"
    panic("could not find virtio disk");

  // ② 握手状态机：按 VirtIO 协议顺序写状态位
  status |= VIRTIO_CONFIG_S_ACKNOWLEDGE;   // "我知道你存在"
  *R(VIRTIO_MMIO_STATUS) = status;

  status |= VIRTIO_CONFIG_S_DRIVER;        // "我有驱动来处理你"
  *R(VIRTIO_MMIO_STATUS) = status;

  // ③ 特性协商：从设备特性集中剔除 xv6 不支持的特性
  uint64 features = *R(VIRTIO_MMIO_DEVICE_FEATURES);
  features &= ~(1 << VIRTIO_BLK_F_RO);        // 不使用只读模式
  features &= ~(1 << VIRTIO_BLK_F_SCSI);      // 不使用 SCSI 命令
  features &= ~(1 << VIRTIO_BLK_F_CONFIG_WCE);// 不使用回写缓存配置
  features &= ~(1 << VIRTIO_BLK_F_MQ);        // 不使用多队列
  features &= ~(1 << VIRTIO_F_ANY_LAYOUT);
  features &= ~(1 << VIRTIO_RING_F_EVENT_IDX);
  features &= ~(1 << VIRTIO_RING_F_INDIRECT_DESC);
  *R(VIRTIO_MMIO_DRIVER_FEATURES) = features;

  status |= VIRTIO_CONFIG_S_FEATURES_OK;       // "特性协商完成"
  *R(VIRTIO_MMIO_STATUS) = status;
  status |= VIRTIO_CONFIG_S_DRIVER_OK;         // "驱动完全就绪"
  *R(VIRTIO_MMIO_STATUS) = status;

  // ④ 配置 VirtQueue 0
  *R(VIRTIO_MMIO_GUEST_PAGE_SIZE) = PGSIZE;   // 告知设备页大小
  *R(VIRTIO_MMIO_QUEUE_SEL)  = 0;            // 选择队列 0
  *R(VIRTIO_MMIO_QUEUE_NUM)  = NUM;          // 队列大小 = 8
  memset(disk.pages, 0, sizeof(disk.pages));
  *R(VIRTIO_MMIO_QUEUE_PFN) = ((uint64)disk.pages) >> PGSHIFT;  // 告知物理页帧号

  // ⑤ 初始化描述符、可用环、已用环的指针
  disk.desc  = (struct VRingDesc *) disk.pages;
  disk.avail = (uint16*)((char*)disk.desc + NUM * sizeof(struct VRingDesc));
  disk.used  = (struct UsedArea *) (disk.pages + PGSIZE);

  // ⑥ 标记所有描述符为空闲
  for(int i = 0; i < NUM; i++) disk.free[i] = 1;
}

VirtIO 握手状态机是协议规定的正式初始化流程，驱动必须按顺序写入 STATUS 寄存器，设备根据当前状态决定响应方式。如果任意步骤失败，设备会在 STATUS 中设置 FAILED 位，驱动需要重置设备。

3.3 virtio_disk_rw()——提交 I/O 请求并等待完成

void virtio_disk_rw(struct buf *b, int write)
{
  uint64 sector = b->blockno * (BSIZE / 512);
  // BSIZE=1024，512 字节是磁盘扇区大小
  // 1 个块 = 2 个扇区

  acquire(&disk.vdisk_lock);

  // ① 分配 3 个描述符（如果没有空闲则 sleep 等待）
  int idx[3];
  while(1) {
    if(alloc3_desc(idx) == 0) break;   // 成功分配
    sleep(&disk.free[0], &disk.vdisk_lock);  // 等待有描述符释放
  }

  // ② 填写请求头描述符（idx[0]）：type/reserved/sector
  struct virtio_blk_outhdr {
    uint32 type;      // VIRTIO_BLK_T_IN(0)=读, VIRTIO_BLK_T_OUT(1)=写
    uint32 reserved;  // 必须为 0
    uint64 sector;    // 起始扇区号
  } buf0;

  buf0.type   = write ? VIRTIO_BLK_T_OUT : VIRTIO_BLK_T_IN;
  buf0.reserved = 0;
  buf0.sector = sector;

  // buf0 在内核栈上（非直接映射），需要 kvmpa() 转换为物理地址
  disk.desc[idx[0]].addr  = (uint64) kvmpa((uint64) &buf0);
  disk.desc[idx[0]].len   = sizeof(buf0);
  disk.desc[idx[0]].flags = VRING_DESC_F_NEXT;   // 驱动→设备，有下一个
  disk.desc[idx[0]].next  = idx[1];

  // ③ 填写数据描述符（idx[1]）：b->data 缓冲区
  disk.desc[idx[1]].addr  = (uint64) b->data;
  disk.desc[idx[1]].len   = BSIZE;
  disk.desc[idx[1]].flags = (write ? 0 : VRING_DESC_F_WRITE) | VRING_DESC_F_NEXT;
  // 读操作：WRITE 标志（设备写入 b->data）
  // 写操作：无 WRITE 标志（设备从 b->data 读取）
  disk.desc[idx[1]].next  = idx[2];

  // ④ 填写状态描述符（idx[2]）：设备写回状态字节
  disk.info[idx[0]].status = 0xff;   // 预填非零值，完成后设备会覆盖为 0
  disk.desc[idx[2]].addr  = (uint64) &disk.info[idx[0]].status;
  disk.desc[idx[2]].len   = 1;
  disk.desc[idx[2]].flags = VRING_DESC_F_WRITE;   // 设备写状态
  disk.desc[idx[2]].next  = 0;

  // ⑤ 记录 buf 指针（中断处理时使用）
  b->disk = 1;
  disk.info[idx[0]].b = b;

  // ⑥ 通知设备：将描述符链首写入可用环
  disk.avail[2 + (disk.avail[1] % NUM)] = idx[0];
  __sync_synchronize();            // 内存屏障：确保描述符写完再更新 avail[1]
  disk.avail[1] = disk.avail[1] + 1;  // avail[1] = 驱动端可用环生产者指针

  *R(VIRTIO_MMIO_QUEUE_NOTIFY) = 0;   // 写 QUEUE_NOTIFY 寄存器触发设备处理

  // ⑦ 等待中断唤醒（b->disk 变为 0 表示 I/O 完成）
  while(b->disk == 1) {
    sleep(b, &disk.vdisk_lock);   // 释放 vdisk_lock，睡眠等待
  }

  // ⑧ 清理
  disk.info[idx[0]].b = 0;
  free_chain(idx[0]);   // 释放描述符链，wakeup(&disk.free[0])

  release(&disk.vdisk_lock);
}

关键设计：b->disk 标志位

b->disk = 1 是 I/O 进行中的标记。virtio_disk_intr() 完成时会将 b->disk = 0 并 wakeup(b)，virtio_disk_rw() 在 while(b->disk == 1) 上自旋检测（配合 sleep）。

**为什么需要 __sync_synchronize()**：

在通知设备（写 QUEUE_NOTIFY）之前，必须确保所有描述符的写入对设备（QEMU）可见。内存屏障阻止处理器/编译器将通知写操作重排序到描述符填充之前，这是驱动正确性的关键。

3.4 virtio_disk_intr()——中断处理

void virtio_disk_intr()
{
  acquire(&disk.vdisk_lock);

  // 遍历已用环中所有新完成的条目
  // disk.used->id：设备端已用环生产者指针
  // disk.used_idx：驱动端已用环消费者指针
  while((disk.used_idx % NUM) != (disk.used->id % NUM)){
    int id = disk.used->elems[disk.used_idx].id;
    // id = 完成的描述符链的首描述符索引

    if(disk.info[id].status != 0)
      panic("virtio_disk_intr status");  // 状态非 0 表示 I/O 错误

    disk.info[id].b->disk = 0;    // 标记 I/O 完成
    wakeup(disk.info[id].b);      // 唤醒在 virtio_disk_rw() 中睡眠的进程

    disk.used_idx = (disk.used_idx + 1) % NUM;
  }

  // 确认中断（写 INTERRUPT_ACK 清除中断状态）
  *R(VIRTIO_MMIO_INTERRUPT_ACK) = *R(VIRTIO_MMIO_INTERRUPT_STATUS) & 0x3;

  release(&disk.vdisk_lock);
}

中断处理函数由 devintr() 调用（见第 11 节），在识别到 VIRTIO0_IRQ 后：

devintr()
  ├── plic_claim() → irq = VIRTIO0_IRQ(1)
  ├── virtio_disk_intr()
  │       ├── 检查 used ring 新条目
  │       ├── disk.info[id].b->disk = 0
  │       └── wakeup(b)  →  唤醒 virtio_disk_rw() 中 sleep(b, ...) 的进程
  └── plic_complete(irq)

四、源码精读：kernel/buf.h——缓冲区数据结构

// kernel/buf.h

struct buf {
  int valid;            // 1 = 此缓冲区的数据已从磁盘读入
  int disk;             // 1 = 磁盘 I/O 进行中（buf "属于" 设备）
  uint dev;             // 设备号
  uint blockno;         // 块号（决定缓冲区代表哪个磁盘块）
  struct sleeplock lock; // 保护此缓冲区内容的睡眠锁
  uint refcnt;          // 引用计数：有多少进程正在使用此缓冲区
  struct buf *prev;     // LRU 链表前驱
  struct buf *next;     // LRU 链表后继
  uchar data[BSIZE];    // 块数据（BSIZE = 1024 字节）
};

字段语义详解：

  • valid：0 表示未从磁盘读取（新分配的缓冲区，data[] 内容无效）；1 表示已同步
  • disk：1 表示 I/O 进行中，此时 data[] 内容属于设备，驱动正在写入；0 表示 CPU 可自由读写
  • lock（sleeplock）：调用者通过 bget() 获得的缓冲区已被上锁，必须通过 brelse() 释放。持有 buf.lock 期间可以 sleep（如等待磁盘 I/O）
  • refcnt：由 bcache.lock（自旋锁）保护；refcnt > 0 的缓冲区不能被 LRU 淘汰

NBUF 的值：

// kernel/param.h
#define MAXOPBLOCKS  10           // 单个文件系统操作最多写 10 个块
#define NBUF         (MAXOPBLOCKS*3)  // = 30 个缓冲区

30 个缓冲区看起来很少，但足够 xv6 的工作负载：日志层保证单个事务最多写 10 块，30 个缓冲区能同时支持 3 个并发事务在飞行中。

五、源码精读：kernel/bio.c——块缓存

5.1 bcache 全局结构

// kernel/bio.c

struct {
  struct spinlock lock;   // 保护以下所有字段
  struct buf buf[NBUF];   // 固定大小的缓冲区池（30 个）

  // 双向循环链表，按访问时间排序
  // head.next = 最近访问的（Most Recently Used）
  // head.prev = 最久未访问的（Least Recently Used）
  struct buf head;
} bcache;

两层锁设计（第 12 节已铺垫）：

bcache.lock（自旋锁）：
  保护链表结构（head、prev/next 指针）和 refcnt 的修改
  临界区：bget() 中的链表查找与淘汰、brelse() 中的链表移动

buf.lock（sleeplock，每个 buf 一把）：
  保护 buf 的内容（data[valid, disk 等字段）
  临界区：从磁盘读入或写出数据（可能需要 sleep 等待 I/O）
  注意：持有 buf.lock 时不持有 bcache.lock（避免死锁）

5.2 binit()——初始化缓冲区双向循环链表

void binit(void)
{
  struct buf *b;
  initlock(&bcache.lock, "bcache");

  // 构造双向循环链表：head ↔ buf[0] ↔ buf[1] ↔ ... ↔ buf[NBUF-1] ↔ head
  bcache.head.prev = &bcache.head;
  bcache.head.next = &bcache.head;

  for(b = bcache.buf; b < bcache.buf + NBUF; b++) {
    // 将 b 插入 head 之后（变为链表最前端）
    b->next = bcache.head.next;
    b->prev = &bcache.head;
    initsleeplock(&b->lock, "buffer");
    bcache.head.next->prev = b;
    bcache.head.next = b;
  }
}

初始化后的链表结构：

head ↔ buf[29] ↔ buf[28] ↔ ... ↔ buf[0] ↔ head（循环）
  ↑                                              ↑
最近使用端（head.next）               最久未使用端（head.prev）

初始时所有缓冲区都未被使用（refcnt=0，valid=0），LRU 顺序无意义，因此插入顺序即为初始链表顺序。

5.3 bget()——核心：查找或分配缓冲区

bget() 是块缓存最核心的函数，其他所有函数（bread、bwrite、brelse）都围绕它工作：

static struct buf*
bget(uint dev, uint blockno)
{
  struct buf *b;
  acquire(&bcache.lock);

  // ① 第一遍扫描：检查是否已缓存
  for(b = bcache.head.next; b != &bcache.head; b = b->next) {
    if(b->dev == dev && b->blockno == blockno) {
      b->refcnt++;               // 增加引用计数
      release(&bcache.lock);     // 释放全局锁
      acquiresleep(&b->lock);    // 获取 buf 的睡眠锁（可能等待其他进程用完）
      return b;                  // 缓存命中，返回已锁定的 buf
    }
  }

  // ② 第二遍扫描（从 LRU 端开始）：找一个 refcnt=0 的缓冲区淘汰
  for(b = bcache.head.prev; b != &bcache.head; b = b->prev) {
    if(b->refcnt == 0) {
      b->dev     = dev;
      b->blockno = blockno;
      b->valid   = 0;    // 新分配，数据无效，bread() 需要从磁盘读
      b->refcnt  = 1;
      release(&bcache.lock);
      acquiresleep(&b->lock);
      return b;          // 缓存未命中，返回已初始化的 buf（数据待读取）
    }
  }

  panic("bget: no buffers");
  // 所有 NBUF 个缓冲区都有 refcnt > 0 → 系统无法继续
}

两遍扫描的方向：

  • 第一遍从 head.next（最近）到 head.prev（最久）：查找时按新到旧遍历，找到即返回
  • 第二遍从 head.prev（最久）到 head.next（最近）：淘汰时选最久未用的（LRU 策略），从尾部向头部找第一个 refcnt == 0 的

refcnt == 0 是淘汰的前提：只有没有进程在使用的缓冲区才可以被淘汰重用。如果某个块的缓冲区正在被使用（refcnt > 0），另一个进程哪怕已经将其从缓存中”驱逐”并等不到它，也必须等待（acquiresleep）。

bget() 返回时的状态：调用者得到的 buf 已持有 buf->lock（sleeplock），可以安全读写 data[]。valid 字段告诉调用者数据是否已从磁盘同步。

5.4 bread()——读取磁盘块

struct buf*
bread(uint dev, uint blockno)
{
  struct buf *b;
  b = bget(dev, blockno);     // 获取（或分配）缓冲区，已持有 b->lock
  if(!b->valid) {
    virtio_disk_rw(b, 0);     // valid=0 表示数据未读，触发磁盘读操作
    b->valid = 1;             // 读完后标记有效
  }
  return b;    // 返回含有最新磁盘数据的、已锁定的 buf
}

bread() 极其简洁。缓存命中时（b->valid = 1），完全不涉及磁盘 I/O，直接返回内存中的缓冲区。缓存未命中时，virtio_disk_rw(b, 0) 会在 vdisk_lock 下睡眠等待磁盘完成（见第 3.3 节）。

5.5 bwrite()——将缓冲区写回磁盘

void bwrite(struct buf *b)
{
  if(!holdingsleep(&b->lock))
    panic("bwrite");          // 必须持有 buf 的睡眠锁才能写
  virtio_disk_rw(b, 1);      // 写磁盘，等待完成
}

注意：bwrite() 直接将缓冲区写到磁盘，绕过了日志层。实际上上层（log 层）使用 log_write() 代替直接 bwrite()，以实现崩溃一致性（第 14 节会详述）。只有日志提交时才真正调用 bwrite()。

5.6 brelse()——释放缓冲区，更新 LRU

void brelse(struct buf *b)
{
  if(!holdingsleep(&b->lock))
    panic("brelse");

  releasesleep(&b->lock);   // ① 释放 buf 的睡眠锁

  acquire(&bcache.lock);    // ② 获取全局锁（修改 LRU 链表）
  b->refcnt--;
  if (b->refcnt == 0) {
    // 没有其他进程在用此 buf → 将其移到链表最前端（MRU 端）
    b->next->prev = b->prev;
    b->prev->next = b->next;
    b->next = bcache.head.next;
    b->prev = &bcache.head;
    bcache.head.next->prev = b;
    bcache.head.next = b;
  }
  release(&bcache.lock);
}

brelse() 的 LRU 维护逻辑：每次释放一个缓冲区时，将其移到链表最前端（最近使用）。这样 LRU 端（head.prev）始终是最久未被 brelse() 过的缓冲区，是淘汰的首选目标。

brelse() 的锁顺序：先释放 buf.lock（sleeplock），再获取 bcache.lock（spinlock）。这与 bget() 中先获取 bcache.lock、再获取 buf.lock 的顺序相符，避免死锁（见第 12 节锁顺序原则）。

5.7 bpin() 和 bunpin()——为日志设计的固定机制

void bpin(struct buf *b) {
  acquire(&bcache.lock);
  b->refcnt++;
  release(&bcache.lock);
}

void bunpin(struct buf *b) {
  acquire(&bcache.lock);
  b->refcnt--;
  release(&bcache.lock);
}

日志层（log.c）使用这两个函数防止缓冲区在事务提交前被淘汰：

  • log_write(b) 调用时，日志层会 bpin(b)：增加 refcnt，使 refcnt 永远 > 0，bget() 的 LRU 淘汰路径绝不会选中此缓冲区
  • 事务提交后（数据写入磁盘日志位置），才调用 bunpin(b) 解除固定

这避免了”日志还没提交，缓冲区已经被别人修改并淘汰”的崩溃一致性问题。

六、数据流全景：bread() 的完整调用链

以 bread(1, 32)（读取设备 1 的第 32 号块）为例：

bread(dev=1, blockno=32)
  │
  ├── bget(1, 32)
  │     ├── acquire(&bcache.lock)
  │     │
  │     ├── [情况A：缓存命中]
  │     │     找到 b->dev==1 && b->blockno==32 的 buf
  │     │     b->refcnt++
  │     │     release(&bcache.lock)
  │     │     acquiresleep(&b->lock)  ← 可能等待其他进程先用完
  │     │     return b（valid=1）
  │     │
  │     └── [情况B：缓存未命中]
  │           从 head.prev 找 refcnt==0 的 buf（LRU 淘汰）
  │           b->dev=1, b->blockno=32, b->valid=0, b->refcnt=1
  │           release(&bcache.lock)
  │           acquiresleep(&b->lock)
  │           return b（valid=0）
  │
  ├── [情况A：valid=1] → 直接返回，无磁盘 I/O
  │
  └── [情况B：valid=0]
        virtio_disk_rw(b, 0)
          ├── acquire(&disk.vdisk_lock)
          ├── alloc3_desc(idx)（或 sleep 等描述符）
          ├── 填写 3 个描述符（请求头 + 数据区 + 状态）
          ├── 更新 avail ring，写 QUEUE_NOTIFY 通知 QEMU
          ├── while(b->disk == 1) sleep(b, &disk.vdisk_lock)
          │           ↑         等待中断
          │     ← virtio_disk_intr() 被调用
          │           b->disk = 0;  wakeup(b)
          │                             ↓
          └── release(&disk.vdisk_lock)
        b->valid = 1
        return b（data[] 已包含磁盘数据，持有 b->lock）

七、缓冲区生命周期图

未使用状态（refcnt=0, valid=0/1）
         ↓ bget() 未命中，LRU 淘汰并重分配
已分配但未读（refcnt=1, valid=0, 持有 buf.lock）
         ↓ bread() 触发 virtio_disk_rw()
已就绪（refcnt=1, valid=1, 持有 buf.lock）
         ↓ 调用者读写 data[]
         ↓ bwrite()（可选，写回磁盘）
         ↓ brelse()
已释放（refcnt=0, valid=1，移到 LRU 链表头）
         ↓ 下次被再次 bget() 命中
再次命中（refcnt++, 不清 valid，直接返回缓存数据）

八、为什么使用全局单锁（bcache.lock）？

xv6 的块缓存使用一把全局自旋锁保护整个链表，这是一个简单但性能受限的设计：

优点（适合 xv6 的教学目标）：

  • 实现极简，容易理解和验证正确性
  • 避免了复杂的锁分片（sharding）逻辑

性能瓶颈：

  • 高并发场景下（多个 CPU 同时调用 bread），bcache.lock 竞争激烈
  • 查找时需要持锁遍历链表（O(NBUF)），期间其他 CPU 必须等待

MIT 6.S081 的 “lock” Lab 就是要求学生将 bcache 从单锁改为哈希桶（hash bucket）分组，每个桶一把锁，大幅减少锁竞争，这是真实操作系统中常见的锁细化技术。

实验 1：统计缓存命中率

在 bget() 中添加计数器，观察文件系统的缓存效果：

// kernel/bio.c 顶部添加全局计数器
uint64 bcache_hits = 0;
uint64 bcache_misses = 0;

// 在 bget() 第一遍扫描找到缓存时
if(b->dev == dev && b->blockno == blockno) {
  bcache_hits++;    // 缓存命中
  b->refcnt++;
  // ...
}

// 在第二遍扫描（未命中路径）
if(b->refcnt == 0) {
  bcache_misses++;  // 缓存未命中
  // ...
}

添加一个系统调用（或在 brelse() 中定期 printf）打印命中率：

printf("bcache: hits=%d, misses=%d, rate=%d%%\n",
       bcache_hits, bcache_misses,
       bcache_hits * 100 / (bcache_hits + bcache_misses + 1));

运行 cat README、ls、usertests 等命令，观察不同工作负载的缓存命中率。

预期现象：

  • 第一次 cat README：命中率低（冷启动，大量缓存未命中）
  • 第二次 cat README：命中率接近 100%（块已缓存）
  • usertests：命中率中等（工作集超过 30 个缓冲区时发生淘汰）

实验 2：画出 bcache 的双向循环链表结构

在 binit() 完成后，添加打印函数输出初始链表：

// kernel/bio.c，在 binit() 末尾添加
void print_bcache(void) {
  struct buf *b;
  printf("bcache list (MRU → LRU):\n");
  int i = 0;
  for(b = bcache.head.next; b != &bcache.head; b = b->next) {
    printf("  [%d] dev=%d blk=%d refcnt=%d valid=%d\n",
           i++, b->dev, b->blockno, b->refcnt, b->valid);
  }
}

在系统初始化后和执行一些文件操作后分别调用 print_bcache()，观察 LRU 顺序如何随操作变化。

  • 如何设计才能避免这种 panic？（提示：参考 sleep 等待可用缓冲区）

十、本节小结

概念 要点
VirtIO MMIO 通过读写固定物理地址控制 QEMU 虚拟磁盘；VIRTIO0 = 0x10001000
三描述符链 请求头（读/写类型 + 扇区号）+ 数据区 + 状态字节；描述符链通知设备做 I/O
可用环 / 已用环 驱动写可用环通知设备；设备写已用环通知驱动完成；__sync_synchronize() 保证顺序
virtio_disk_rw 持 vdisk_lock 睡眠等待中断；b->disk 是 I/O 进行的标志
struct buf 缓冲区 = 数据（data[1024]）+ 元数据（valid, disk, dev, blockno, refcnt）+ 锁
bcache 30 个固定缓冲区；双向循环链表 LRU；全局 bcache.lock（自旋锁）+ 每 buf 的 sleeplock
bget() 两遍扫描：命中直接返回（refcnt++）；未命中从 LRU 端淘汰（refcnt=0 才可淘汰）
bread() = bget() + 视情况调用 virtio_disk_rw() 读磁盘
brelse() 释放 buf.lock + 将 buf 移到 LRU 链表 MRU 端
bpin/bunpin 通过增减 refcnt 固定缓冲区，防止日志块被 LRU 淘汰
两层锁协作 bcache.lock 保护链表结构（短操作）；buf.lock（sleeplock）保护块数据（长操作，可睡眠）
