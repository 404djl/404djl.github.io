第 10 节：系统调用实现

学习目标：掌握系统调用从用户态发起到内核执行并返回的完整路径；理解系统调用号分发机制；深入理解内核如何安全地访问用户空间数据；并动手为 xv6 添加一个新的系统调用。

预计用时：3-4 小时

前置要求：完成第 9 节（Trap 机制），了解 ecall 触发 trap、trapframe 保存用户寄存器的过程

一、理论：系统调用的核心约定

1.1 RISC-V 系统调用 ABI

用户程序通过 ecall 指令进入内核。在执行 ecall 之前，必须按照约定将参数放入正确的寄存器——这就是系统调用的 ABI（Application Binary Interface）。

xv6 遵循 RISC-V 标准系统调用约定：

寄存器 用途 方向
a7 系统调用号（System Call Number） 用户 → 内核
a0 第 1 个参数 / 返回值 双向
a1 第 2 个参数 用户 → 内核
a2 第 3 个参数 用户 → 内核
a3 第 4 个参数 用户 → 内核
a4 第 5 个参数 用户 → 内核
a5 第 6 个参数 用户 → 内核

xv6 系统调用最多支持 6 个参数（a0-a5），返回值写回 a0。

用户程序调用 write(1, "hello", 5) 的寄存器状态：

  a7 = 16    （SYS_write 的调用号）
  a0 = 1     （第 1 参数：fd）
  a1 = 0x...  （第 2 参数：buf 的用户虚拟地址）
  a2 = 5     （第 3 参数：count）
  ecall      （触发 trap，进入内核）

内核执行 sys_write() 完成后：
  a0 = 5     （返回值：实际写入字节数）
  sret       （回到用户态）

1.2 系统调用的完整路径

用户程序
  │ 调用 write(1, buf, n)（C 函数调用）
  ▼
user/usys.S 中的 write stub
  │ li a7, SYS_write（= 16）
  │ ecall
  ▼
硬件 trap（第 9 节详述）
  │ → trampoline.S/uservec：保存寄存器，切换页表
  │ → kernel/trap.c/usertrap()：识别为 ecall（scause=8）
  ▼
kernel/syscall.c/syscall()
  │ num = trapframe->a7（= 16）
  │ syscalls[16]() = sys_write()
  ▼
kernel/sysfile.c/sys_write()
  │ argint(0, &fd)        → fd = trapframe->a0 = 1
  │ argaddr(1, &addr)     → addr = trapframe->a1（buf 的用户地址）
  │ argint(2, &n)         → n = trapframe->a2 = n
  │ filewrite(...)        → 实际写入
  │ return 写入字节数
  ▼
kernel/syscall.c/syscall()（续）
  │ trapframe->a0 = 返回值（写入字节数）
  ▼
回到 usertrap() → usertrapret() → trampoline.S/userret → sret
  ▼
用户程序，write() 返回，a0 = 写入字节数

1.3 为什么不能直接读用户指针？

用户程序传入的指针（如 write 的 buf）是用户虚拟地址。内核运行时使用内核页表，用户虚拟地址在内核页表中通常没有映射。如果内核直接解引用用户指针，会发生：

  • 页错误（最好情况）：触发内核 panic
  • 安全漏洞（最差情况）：精心构造的用户地址恰好在内核直接映射区有意义，读到内核私有数据（信息泄露），或写入内核关键数据（权限提升）

因此，内核必须通过专用函数（copyin / copyout / copyinstr）来访问用户空间数据，这些函数会：

  1. 通过用户进程的页表（p->pagetable）翻译虚拟地址
  2. 校验地址合法性（地址在进程的 sz 范围内）
  3. 然后再访问对应的物理内存

二、源码精读：kernel/syscall.h——系统调用号

// kernel/syscall.h（22 行）
#define SYS_fork    1
#define SYS_exit    2
#define SYS_wait    3
#define SYS_pipe    4
#define SYS_read    5
#define SYS_kill    6
#define SYS_exec    7
#define SYS_fstat   8
#define SYS_chdir   9
#define SYS_dup    10
#define SYS_getpid 11
#define SYS_sbrk   12
#define SYS_sleep  13
#define SYS_uptime 14
#define SYS_open   15
#define SYS_write  16
#define SYS_mknod  17
#define SYS_unlink 18
#define SYS_link   19
#define SYS_mkdir  20
#define SYS_close  21

系统调用号是用户程序和内核之间的接口契约——只要调用号不变，用户程序不需要重新编译就能在新内核上运行。这也是为什么 Linux 从不更改已有的系统调用号（即使某些设计决策后来看来很糟糕）。

xv6 只有 21 个系统调用（Linux 有 350+）。这些调用号由三个地方使用：

  1. **kernel/syscall.h**：定义数字常量
  2. user/usys.pl → **user/usys.S**：用户态 stub 中 li a7, SYS_xxx
  3. **kernel/syscall.c**：分发表 syscalls[num]

三者必须保持一致。

三、源码精读：user/usys.pl 与 user/usys.S

3.1 Perl 脚本自动生成

user/usys.S 不是手写的，而是由 user/usys.pl 在编译时自动生成：

# user/usys.pl（节选）
sub entry {
    my $name = shift;
    print ".global $name\n";   # 导出符号（使其他文件可链接到此函数）
    print "${name}:\n";
    print " li a7, SYS_${name}\n";  # 将调用号加载到 a7
    print " ecall\n";               # 触发系统调用 trap
    print " ret\n";                 # trap 返回后，a0 = 返回值，用 ret 返回调用者
}

entry("fork");
entry("exit");
entry("wait");
# ... 21 个系统调用

生成的 user/usys.S（以 write 为例）：

.global write
write:
 li a7, SYS_write    # a7 = 16
 ecall               # 触发 trap → uservec → usertrap() → syscall()
 ret                 # sret 返回用户态后，a0 已被内核设置为返回值，ret 把控制权交回调用者

为什么用 ret 而不是 lr（或任何跳转）？

ret = jalr x0, ra, 0，跳转到 ra（调用者的返回地址）。调用 write(...) 的 C 代码通过 jal ra, write 进入 stub，ra 保存了 C 代码中 write() 调用的下一条指令地址。ecall 触发 trap，内核完成处理，sret 回到 ret 这条指令，然后 ret 跳回 C 调用处——整个 stub 就像一个透明的桥梁。

3.2 user/user.h——用户态声明

// user/user.h（节选）
// 这些声明告诉编译器函数的签名，实际实现在 usys.S 中
int fork(void);
int exit(int) __attribute__((noreturn));  // 标记为 noreturn，优化代码生成
int wait(int*);
int write(int, const void*, int);
int read(int, void*, int);
// ...

用户程序 #include "user/user.h" 后得到函数签名，链接时链接器将函数调用解析到 usys.S 中对应的 stub。

四、源码精读：kernel/syscall.c——分发与参数提取

4.1 syscall()——调用号分发

// kernel/syscall.c 末尾

// 函数指针数组：以调用号为下标，存放对应的处理函数
static uint64 (*syscalls[])(void) = {
[SYS_fork]    sys_fork,    // [1] = sys_fork
[SYS_exit]    sys_exit,    // [2] = sys_exit
[SYS_wait]    sys_wait,    // [3] = sys_wait
[SYS_pipe]    sys_pipe,    // [4] = sys_pipe
[SYS_read]    sys_read,    // [5] = sys_read
[SYS_kill]    sys_kill,    // [6] = sys_kill
[SYS_exec]    sys_exec,    // [7] = sys_exec
[SYS_fstat]   sys_fstat,   // [8] = sys_fstat
[SYS_chdir]   sys_chdir,   // [9] = sys_chdir
[SYS_dup]     sys_dup,     // [10] = sys_dup
[SYS_getpid]  sys_getpid,  // [11] = sys_getpid
[SYS_sbrk]    sys_sbrk,    // [12] = sys_sbrk
[SYS_sleep]   sys_sleep,   // [13] = sys_sleep
[SYS_uptime]  sys_uptime,  // [14] = sys_uptime
[SYS_open]    sys_open,    // [15] = sys_open
[SYS_write]   sys_write,   // [16] = sys_write
[SYS_mknod]   sys_mknod,   // [17] = sys_mknod
[SYS_unlink]  sys_unlink,  // [18] = sys_unlink
[SYS_link]    sys_link,    // [19] = sys_link
[SYS_mkdir]   sys_mkdir,   // [20] = sys_mkdir
[SYS_close]   sys_close,   // [21] = sys_close
};

void
syscall(void)
{
  int num;
  struct proc *p = myproc();

  // ① 从 trapframe->a7 读取系统调用号
  num = p->trapframe->a7;

  // ② 范围检查 + 非空检查，然后调用对应处理函数
  if(num > 0 && num < NELEM(syscalls) && syscalls[num]) {
    // ③ 调用处理函数，将返回值写回 trapframe->a0
    // sret 后 a0 被恢复为这个值，用户程序读到系统调用的返回值
    p->trapframe->a0 = syscalls[num]();
  } else {
    printf("%d %s: unknown sys call %d\n",
            p->pid, p->name, num);
    p->trapframe->a0 = -1;  // 未知调用号，返回 -1
  }
}

**C99 指定初始化器 [SYS_fork] sys_fork**：

这是 C99 的”指定初始化器”（designated initializer）语法：[下标] = 值（等号可以省略）。[SYS_fork] = [1]，意味着数组第 1 个元素是 sys_fork。这样写的好处是：即使 SYS_xxx 的数值顺序变化，分发表仍然正确——不会因为调用号重排导致分发到错误的函数。

**NELEM(syscalls)**：

// kernel/defs.h 或类似地方
#define NELEM(x) (sizeof(x)/sizeof((x)[0]))

计算数组元素数量。NELEM(syscalls) = 22（下标 0-21），检查 num < 22 防止数组越界。

为什么所有处理函数签名都是 uint64 sys_xxx(void)？

所有系统调用处理函数都不接受参数（void），返回 uint64。参数不通过 C 函数调用传递，而是通过 argint()/argaddr()/argstr() 从 trapframe 中提取。这样所有处理函数有统一的函数指针类型，可以放入同一个数组。

4.2 argraw()——直接读 trapframe 寄存器

// 从 trapframe 中取出第 n 个参数寄存器的原始值
static uint64
argraw(int n)
{
  struct proc *p = myproc();
  switch (n) {
  case 0: return p->trapframe->a0;  // 第 0 个参数 = a0
  case 1: return p->trapframe->a1;
  case 2: return p->trapframe->a2;
  case 3: return p->trapframe->a3;
  case 4: return p->trapframe->a4;
  case 5: return p->trapframe->a5;  // 第 5 个参数 = a5（最多 6 个）
  }
  panic("argraw");
  return -1;
}

trapframe 在 uservec 时已经保存了用户进入 ecall 时所有寄存器的值，包括 a0-a5。argraw(n) 直接从 trapframe 读取，不需要复制，性能极高。

4.3 argint()、argaddr()——安全提取整数和地址

// 取第 n 个参数，解释为 32 位整数
int
argint(int n, int *ip)
{
  *ip = argraw(n);   // 直接从 trapframe 读，截断为 int（低 32 位）
  return 0;
}

// 取第 n 个参数，解释为指针（64 位地址）
// 注意注释：不校验合法性，因为 copyin/copyout 会做
int
argaddr(int n, uint64 *ip)
{
  *ip = argraw(n);
  return 0;
}

argaddr() 不检验地址合法性！仅仅是把寄存器值存入 *ip。真正的安全检验发生在 copyin/copyout 中——每次根据用户页表翻译时都会验证地址在 p->sz 范围内。

设计原则：延迟检验（lazy validation）。并非所有传入的地址都会被访问，提前检验可能会有误检（如对齐限制），不如等到实际访问时让 copyin 统一处理。

4.4 argstr()——提取字符串参数

// 取第 n 个参数作为字符串，从用户空间拷贝到内核缓冲区 buf
// max：缓冲区最大字节数（含 NUL）
// 返回：字符串长度（不含 NUL），或 -1（错误）
int
argstr(int n, char *buf, int max)
{
  uint64 addr;
  if(argaddr(n, &addr) < 0)   // 先取参数（字符串的用户虚拟地址）
    return -1;
  return fetchstr(addr, buf, max);  // 再从用户空间拷贝字符串内容
}

4.5 fetchstr()——从用户地址空间拷贝字符串

// 从当前进程的用户地址 addr 处拷贝 NUL 终止字符串到内核 buf
// 最多拷贝 max 字节
int
fetchstr(uint64 addr, char *buf, int max)
{
  struct proc *p = myproc();
  // copyinstr：通过用户页表翻译 addr，逐字节拷贝直到 NUL 或 max
  // 如果 addr 非法（超出 p->sz 或未映射），返回 -EFAULT
  int err = copyinstr(p->pagetable, buf, addr, max);
  if(err < 0)
    return err;
  return strlen(buf);
}

4.6 fetchaddr()——从用户地址空间读取一个 64 位值

// 从当前进程的用户地址 addr 处读取一个 uint64
int
fetchaddr(uint64 addr, uint64 *ip)
{
  struct proc *p = myproc();
  // 安全检查：地址范围必须在进程的地址空间内（0 ~ p->sz）
  if(addr >= p->sz || addr+sizeof(uint64) > p->sz)
    return -1;
  // 通过用户页表拷贝数据到内核变量 *ip
  if(copyin(p->pagetable, (char *)ip, addr, sizeof(*ip)) != 0)
    return -1;
  return 0;
}

fetchaddr 比 argaddr 多了范围检查：fetchaddr 用于读取用户指向的内存中的值（如 wait(int *status) 中的 status 指针所指的 int），属于”二级指针解引用”——需要保证指针本身指向合法范围。argaddr 只是取系统调用的参数寄存器值，范围检验留给实际访问时的 copyin。

五、源码精读：kernel/sysproc.c——进程相关系统调用

5.1 sys_exit()

uint64
sys_exit(void)
{
  int n;
  if(argint(0, &n) < 0)   // 取退出码（第 0 个参数 = a0）
    return -1;
  exit(n);                  // 调用 proc.c 中的 exit()，不返回
  return 0;  // not reached（编译器需要这一行，但实际执行不到）
}

exit() 是 __attribute__((noreturn)) 的，调用后进程进入 ZOMBIE 状态并切换到调度器，永不返回到 sys_exit()。return 0 只是为了满足编译器的语法要求。

5.2 sys_getpid()

uint64
sys_getpid(void)
{
  return myproc()->pid;   // 直接返回当前进程的 PID，无需任何参数
}

最简单的系统调用——0 个参数，1 行代码。展示了系统调用实现的最简形式：取当前进程信息并返回。

5.3 sys_fork()

uint64
sys_fork(void)
{
  return fork();   // 直接调用 proc.c 中的 fork()
}

fork() 返回子进程 PID（父进程）或 0（子进程）。注意：sys_fork() 返回的值被 syscall() 写入 trapframe->a0——但子进程的 trapframe->a0 已经在 fork() 内部被设置为 0（第 7 节详述），不会被这个返回值覆盖（子进程不经过 syscall() 返回路径）。

5.4 sys_wait()

uint64
sys_wait(void)
{
  uint64 p;
  if(argaddr(0, &p) < 0)   // 取参数：int* 指针（用户空间地址）
    return -1;
  return wait(p);            // proc.c 中的 wait()
}

wait(int *status) 的 status 参数是一个用户空间指针。argaddr 把这个地址取出来，传给 wait()，wait() 内部通过 copyout() 将子进程退出码写到这个用户地址。

5.5 sys_sbrk()——堆内存扩缩

uint64
sys_sbrk(void)
{
  int addr;
  int n;

  if(argint(0, &n) < 0)    // n > 0：扩展堆；n < 0：收缩堆
    return -1;
  addr = myproc()->sz;      // 当前堆顶（进程地址空间大小）
  if(growproc(n) < 0)       // 调用 proc.c 中的 growproc() 修改地址空间
    return -1;
  return addr;               // 返回扩展/收缩之前的堆顶地址（malloc 用于计算新内存的地址）
}

growproc(n) 的实现：

// kernel/proc.c
int
growproc(int n)
{
  uint sz;
  struct proc *p = myproc();
  sz = p->sz;
  if(n > 0){
    // 申请更多内存：uvmalloc 分配物理页并在页表中建立映射
    if((sz = uvmalloc(p->pagetable, sz, sz + n)) == 0)
      return -1;
  } else if(n < 0){
    // 释放内存：uvmdealloc 取消映射并释放物理页
    sz = uvmdealloc(p->pagetable, sz, sz + n);
  }
  p->sz = sz;   // 更新进程地址空间大小
  return 0;
}

sbrk(n) 是 Unix 最原始的堆分配接口，C 的 malloc()/free() 在用户空间管理这块内存（将大块 sbrk 申请的内存切成小块分配给用户）。现代系统更常用 mmap()，xv6 只实现了 sbrk。

5.6 sys_sleep()——基于 ticks 的定时睡眠

uint64
sys_sleep(void)
{
  int n;
  uint ticks0;

  if(argint(0, &n) < 0)   // n = 要睡眠的 tick 数
    return -1;
  
  acquire(&tickslock);
  ticks0 = ticks;         // 记录开始时的 tick 计数
  
  while(ticks - ticks0 < n) {   // 循环等待直到满 n 个 tick
    if(myproc()->killed) {       // 被 kill 信号打断
      release(&tickslock);
      return -1;
    }
    sleep(&ticks, &tickslock);  // 在 ticks 变量上睡眠
    // clockintr() 每次时钟中断会 wakeup(&ticks)，唤醒所有等待的进程
    // 被唤醒后继续循环检查是否满足条件
  }
  
  release(&tickslock);
  return 0;
}

sleep 为什么需要循环？（虚假唤醒）

sleep(&ticks, &tickslock) 在 ticks 上等待。clockintr() 每次时钟中断都调用 wakeup(&ticks)，唤醒所有在 ticks 上睡眠的进程。但每个进程要等待的时间不同——有的要等 1 tick，有的要等 100 tick。被唤醒时必须重新检查条件（ticks - ticks0 < n），如果还没达到目标时间就继续睡眠。

这就是 sleep/wakeup 的经典使用模式：睡眠必须在循环中（while，而非 if），因为 wakeup 是广播（所有等待者都唤醒），而不是精准通知。

5.7 sys_uptime()

uint64
sys_uptime(void)
{
  uint xticks;
  acquire(&tickslock);
  xticks = ticks;         // 读取全局 ticks 计数器
  release(&tickslock);
  return xticks;
}

返回系统启动以来的时钟 tick 数。注意必须持有 tickslock 才能读取 ticks（clockintr() 在持有 tickslock 时写入 ticks），否则可能读到被并发修改到一半的值。

六、参数安全性：为什么不能信任用户指针

6.1 三类参数与对应处理方式

参数类型 提取方式 安全保证
整数值（fd、mode、flags 等） argint() 直接从 trapframe 读，值本身安全
地址（将被读写的缓冲区） argaddr() + copyin/copyout copyin/copyout 通过用户页表翻译，自动验证
字符串（路径名、程序名等） argstr() + fetchstr() copyinstr 有长度上限，防止内核栈溢出
指针指向的值（wait(int*) 的退出码） fetchaddr() 额外做 addr < p->sz 范围检查

6.2 TOCTOU（Time-Of-Check-Time-Of-Use）问题

内核调用 fetchstr() 或 copyin() 时，将用户内存复制到内核缓冲区。之后内核使用的是内核缓冲区中的副本，而不是用户内存本身。

如果内核使用用户指针直接访问，会有 TOCTOU 问题：

内核检查路径名合法后，用户程序修改路径名（多线程场景）
内核再次访问时，路径名已经变了
→ 安全漏洞（如 symlink attack）

通过复制，内核获得一份不变的副本：用户如何修改用户内存都不影响内核已经复制过来的数据。

6.3 copyin vs copyout vs copyinstr

// kernel/vm.c（声明在 defs.h）

// 将用户空间 srcva 处的 len 字节复制到内核 dst
// 通过用户页表 pagetable 翻译 srcva
int copyin(pagetable_t pagetable, char *dst, uint64 srcva, uint64 len);

// 将内核 src 处的 len 字节复制到用户空间 dstva
// 通过用户页表 pagetable 翻译 dstva
int copyout(pagetable_t pagetable, uint64 dstva, char *src, uint64 len);

// 将用户空间 srcva 处的 NUL 终止字符串复制到内核 dst
// 最多复制 max 字节，返回复制的字节数（含 NUL），或 -1
int copyinstr(pagetable_t pagetable, char *dst, uint64 srcva, uint64 max);

三者本质上都通过 walkaddr() 查用户页表得到物理地址，然后 memmove() 复写。copyinstr 额外处理 NUL 终止和长度限制。

int main(void) {

实验 5：追踪 sys_sleep() 的 tick 等待

修改 sys_sleep() 添加调试打印：

uint64
sys_sleep(void)
{
  int n;
  uint ticks0;
  if(argint(0, &n) < 0) return -1;
  acquire(&tickslock);
  ticks0 = ticks;
  printf("[sleep] pid=%d 开始等待 %d ticks（当前 ticks=%d）\n",
         myproc()->pid, n, ticks0);
  while(ticks - ticks0 < n){
    if(myproc()->killed){ release(&tickslock); return -1; }
    printf("[sleep] pid=%d 等待中（ticks=%d, 还差 %d）\n",
           myproc()->pid, ticks, n - (ticks - ticks0));
    sleep(&ticks, &tickslock);
  }
  printf("[sleep] pid=%d 等待完成（当前 ticks=%d）\n", myproc()->pid, ticks);
  release(&tickslock);
  return 0;
}

  • ticks 的增量如何驱动 while 循环向前推进

  2. 如果添加 #define SYS_hello 100，NELEM(syscalls) 变成多少？

八、思考题

  1. syscall() 中的分发是通过函数指针数组实现的，而不是 switch-case。这两种实现方式在性能和可维护性上有什么差异？Linux 内核使用哪种方式？

    函数指针数组：O(1) 时间复杂度，添加新系统调用只需在对应位置写入函数指针，无需修改分发逻辑。缺点：调用号必须是连续的小整数。switch-case：编译器可能生成跳转表（实质与指针数组相同）或条件分支链，可读性好，但调用号稀疏时跳转表会浪费内存。Linux 内核使用指针表（sys_call_table[]），通过汇编 SYSCALL_DEFINE 宏注册，与 xv6 本质相同。

  2. argaddr() 没有检验地址合法性，但 fetchaddr() 有（检查 addr < p->sz）。为什么有的要检验，有的不要？哪种更安全？

    argaddr() 取的是”将被传给 copyin/copyout 的地址”——这个地址的合法性由 copyin/copyout 在实际访问时验证（walk() 发现地址无效会返回 NULL）。fetchaddr() 取的是”指针指向的内存中的一个指针”（用户程序传了一个指向指针的指针），这个”内层指针”需要额外检验，因为它是”元数据”，表示一段用户内存的起始——如果它本身超出 p->sz，则访问前就应该报错。两种设计各有道理，本质上都依赖 copyin 作为最后防线；fetchaddr 只是提前做了一次快速范围检验，可以更早返回 -1。

  3. sys_sbrk(n) 在 n=0 时返回当前堆顶而不改变堆大小。这有什么实际用途？

    sbrk(0) 是查询当前堆顶地址的标准方式，常用于：(1) malloc 实现内部查询当前分配位置；(2) 调试工具查询进程地址空间大小；(3) 在 sbrk(n) 之前调用 sbrk(0) 获取基准地址，用于计算相对偏移。在 xv6 中，myproc()->sz 即是堆顶，sbrk(0) 返回 p->sz 但不调用 growproc()（因为 n == 0 时 growproc 直接返回 0，p->sz 不变）。

  4. sys_sleep() 用 while(ticks - ticks0 < n) 而非 if(...)。把 while 改成 if 会有什么问题？

    改成 if 后，进程只会睡眠一次。wakeup(&ticks) 是每 tick 对所有等待者广播唤醒，包括还没到目标时间的进程。用 if 的话，某个等待 100 tick 的进程被第 1 个 tick 唤醒后，if 条件不满足，但代码不会再次 sleep——进程会直接继续执行后续代码（相当于 sleep(100) 只睡了 1 tick 就返回了）。while 确保每次醒来都重新检查是否达到目标 tick 数，不满足则继续睡眠，正确实现了”至少睡满 n 个 tick”的语义。

  5. 为什么 usys.S 的每个 stub 用 ret 而不是 j _start（跳回 _start 重新初始化）？RISC-V 的 ret 指令实际上是什么汇编？

    ret 是伪指令，等价于 jalr x0, x1, 0（即 jalr zero, ra, 0）——跳转到 ra 寄存器中的地址，不保存返回地址（写到 x0 丢弃）。调用者通过 jal ra, write（或 call write）进入 stub，ra 中存的是调用者的下一条指令地址。ecall 返回后，sret 将控制权交回 stub 中 ecall 的下一条指令（即 ret），ret 再跳回调用者——这是标准的 C 函数调用/返回机制。用 j _start 根本是错误的：会重启整个程序而不是让调用者的函数返回。

  6. xv6 的系统调用没有错误码系统（如 Linux 的 errno）。write() 出错时直接返回 -1，调用者无法知道具体错误原因。如果要为 xv6 实现 errno，需要改动哪些地方？

    Linux 的 errno 存储在线程私有存储（TLS） 中（每个线程一个，防止多线程竞争）。xv6 没有线程，但可以类似地：(1) 在 struct proc 中添加 int errno 字段；(2) 内核 sys_xxx() 函数在出错时除了返回负数，还通过 myproc()->errno = ENOENT 等设置错误码；(3) 用户态 stub（usys.S）检查 a0 < 0，若是则将 proc->errno 复制到用户可见的全局变量 errno（通过另一个简单系统调用或共享内存）；(4) ulib.c 中的包装函数负责设置/清除用户态 errno。实际上 musl libc 通过 mmap/clone 等机制实现 TLS，使 errno 对每个线程独立——在 xv6 这个简化版本中使用进程局部的 errno 就够了。

九、本节小结

概念 要点
系统调用 ABI a7 = 调用号，a0-a5 = 参数，返回值写回 a0
usys.pl 生成 usys.S 每个 stub：li a7, SYS_xxx + ecall + ret
syscall() 分发 从 trapframe->a7 读调用号，通过函数指针数组 syscalls[num]() 分发
返回值写回 syscalls[num]() 的返回值写入 trapframe->a0，sret 后用户程序读到 a0
argraw(n) 从 trapframe->a0-a5 直接读第 n 个参数
argint / argaddr 提取整数/地址参数，argaddr 不做范围检验（留给 copyin/copyout）
argstr / fetchstr 提取字符串，通过 copyinstr 安全复制（防 NUL 溢出）
fetchaddr 取用户指针指向的值，需额外检验 addr < p->sz
不能直接解引用用户指针 内核使用内核页表，用户虚拟地址无效；需通过 copyin/copyout 经用户页表翻译
sys_sleep() 的 while 循环 wakeup 是广播，必须循环检查条件，防止虚假唤醒导致提前返回
sys_sbrk() 调用 growproc(n) 扩缩堆，返回扩缩前的堆顶地址
