第 14 节：日志层与崩溃恢复

学习目标：理解文件系统崩溃一致性（crash consistency）问题的本质；掌握 Write-Ahead Logging（WAL）的核心思想；深入分析 xv6 日志层的全部代码（log.c，235 行）；理解 begin_op/end_op 事务机制、log_write 的日志吸收优化，以及崩溃恢复的完整流程。

预计用时：3-4 小时

前置要求：完成第 13 节（磁盘驱动与块缓存），理解 bread/bwrite/brelse/bpin/bunpin；完成第 12 节（锁机制），理解 sleep/wakeup 与自旋锁的关系；了解磁盘布局（fs.h 中的 struct superblock）

一、理论：崩溃一致性问题

1.1 为什么需要日志？

文件系统经常需要原子地更新多个磁盘块。典型示例：创建一个新文件需要：

① 在 inode 区分配一个新 inode（写 inode 块）
② 在父目录中添加一条条目（写目录数据块）
③ 更新 inode 引用计数（nlink）

这三步写磁盘操作不是原子的——如果在步骤 ① 和 ② 之间系统断电，磁盘上就会出现一个”存在但没有目录条目”的 inode，文件系统元数据不一致，下次挂载时 fsck（文件系统检查工具）需要扫描整个磁盘来修复。

这类问题统称为崩溃一致性问题（crash consistency）：多步写操作的中间状态不应在崩溃重启后持久化。

1.2 Write-Ahead Logging（WAL）

xv6 使用 Write-Ahead Logging 解决此问题，核心规则只有两条：

  1. 先写日志，再写数据：在实际数据写到磁盘之前，先把”打算写什么”记录到日志
  2. 提交后才安装：只有日志头（header block）成功写到磁盘后，才将日志数据”安装”到实际位置

由于日志头的写入是单块操作，磁盘控制器保证单扇区写是原子的（即使中途断电，要么写完要么没写），因此日志头的写入构成了原子提交点。

崩溃恢复逻辑极其简单：

重启时检查日志头 lh.n：
  lh.n == 0  → 上次未提交（崩溃在提交前）→ 丢弃日志，什么都不做
  lh.n  > 0  → 上次已提交（崩溃在安装时）→ 重新安装（redo），然后清零

WAL 的幂等性（idempotent）：无论 install_trans() 执行了多少次，最终结果相同——所以重启后重做已提交的日志是安全的。

1.3 xv6 日志的磁盘布局

xv6 的磁盘分区（由 mkfs.c 和 fs.h 定义）：

磁盘块编号  区域
─────────────────────────────────────────────────────────
0           boot block（引导块，不由 xv6 使用）
1           super block（超级块：文件系统元信息）
2           log header block（日志头块）          ← 日志区起始
3..31       log data blocks（30 个日志数据块）    ← LOGSIZE = 30
32..57      inode blocks（inode 区）
58          bitmap block（空闲块位图）
59..999     data blocks（数据区）
─────────────────────────────────────────────────────────

参数（kernel/param.h）：
  MAXOPBLOCKS = 10    单个 FS 系统调用最多写 10 个块
  LOGSIZE     = 30    日志区数据块数（= MAXOPBLOCKS × 3）
  NBUF        = 30    块缓存缓冲区个数

日志区的内容：

块 2（日志头块）：struct logheader { int n; int block[LOGSIZE]; }
  n         = 已提交的日志块数（0 表示无未完成事务）
  block[0]  = 被修改的第 0 个块的实际目标块号
  block[1]  = 被修改的第 1 个块的实际目标块号
  ...

块 3（日志数据块 0）：block[0] 对应块的修改内容
块 4（日志数据块 1）：block[1] 对应块的修改内容
  ...

二、数据结构：struct log 和 struct logheader

// kernel/log.c

// 日志头：同时存在于磁盘（块 2）和内存（log.lh）
struct logheader {
  int n;                 // 当前日志中的块数（内存中动态追踪；磁盘上是原子提交点）
  int block[LOGSIZE];    // 各日志槽对应的实际目标块号
};

struct log {
  struct spinlock lock;  // 保护以下所有字段

  int start;             // 日志区第一个日志块的块号（= sb.logstart = 2）
  int size;              // 日志区大小（块数，= sb.nlog = 30）
  int dev;               // 设备号

  int outstanding;       // 当前正在执行中的 FS 系统调用数（每个 begin_op +1，end_op -1）
  int committing;        // 是否正在提交（commit() 执行期间为 1）

  struct logheader lh;   // 内存中的日志头（与磁盘日志头同步）
};

struct log log;          // 全局日志对象（只有一个）

log.lh.n 的双重含义：

  • 内存中：当前事务期间通过 log_write() 记录的块数（动态增长）
  • 磁盘上：已提交并等待安装的块数（提交时写入，安装完成后清零）

这是 WAL 设计的精妙之处：n > 0 是崩溃恢复的唯一触发条件。

三、源码精读：日志的生命周期

3.1 initlog()——启动时初始化与崩溃恢复

void initlog(int dev, struct superblock *sb)
{
  if (sizeof(struct logheader) >= BSIZE)
    panic("initlog: too big logheader");
  // logheader 必须装进一个块（1024 字节）：
  // sizeof(logheader) = 4 + 30×4 = 124 字节，远小于 1024，安全

  initlock(&log.lock, "log");
  log.start = sb->logstart;   // 日志区起始块号（= 2）
  log.size  = sb->nlog;       // 日志区总块数（= 30）
  log.dev   = dev;

  recover_from_log();   // ← 关键：检查上次是否有未完成事务
}

initlog() 在 main() → fsinit() → iinit() 中被调用，是文件系统初始化的第一步。

3.2 recover_from_log()——崩溃恢复

static void recover_from_log(void)
{
  read_head();       // 从磁盘读取日志头到 log.lh
  install_trans();   // 若 log.lh.n > 0，将日志数据安装到实际位置（redo）
  log.lh.n = 0;
  write_head();      // 将 n=0 写回磁盘，清除日志（表示恢复完成）
}

**read_head()**：

static void read_head(void)
{
  struct buf *buf = bread(log.dev, log.start);   // 读日志头块（块号 2）
  struct logheader *lh = (struct logheader *)(buf->data);
  log.lh.n = lh->n;
  for (int i = 0; i < log.lh.n; i++)
    log.lh.block[i] = lh->block[i];
  brelse(buf);
}

**install_trans()**——将日志数据拷贝到实际磁盘位置：

static void install_trans(void)
{
  for (int tail = 0; tail < log.lh.n; tail++) {
    struct buf *lbuf = bread(log.dev, log.start + tail + 1);
    // 读日志数据块（log.start+1 = 块3，log.start+2 = 块4，...）

    struct buf *dbuf = bread(log.dev, log.lh.block[tail]);
    // 读目标块（实际应该写入的位置）

    memmove(dbuf->data, lbuf->data, BSIZE);  // 从日志块复制到目标块
    bwrite(dbuf);    // 将目标块写到磁盘（安装）
    bunpin(dbuf);    // 解除 bpin（允许被 LRU 淘汰）
    brelse(lbuf);
    brelse(dbuf);
  }
}

崩溃恢复时序分析：

场景 A：崩溃在 write_head() 之前（提交前）
  磁盘日志头 lh.n == 0 → read_head() 后 log.lh.n = 0
  install_trans() 什么都不做（循环 0 次）
  write_head() 写 n=0（无变化）
  结论：本次未提交的写操作全部丢弃，文件系统回到上次提交状态 ✓

场景 B：崩溃在 write_head() 之后、install_trans() 完成之前（提交后安装中）
  磁盘日志头 lh.n > 0 → read_head() 后 log.lh.n > 0
  install_trans() 重做所有已提交的写操作（幂等）
  write_head() 写 n=0 清除日志
  结论：已提交的操作全部完成，文件系统达到一致状态 ✓

场景 C：正常关机（完整提交 + 安装后清零）
  磁盘日志头 lh.n == 0 → 同场景 A，什么都不做 ✓

3.3 begin_op()——事务开始

void begin_op(void)
{
  acquire(&log.lock);
  while(1) {
    if(log.committing) {
      // 正在提交中，必须等待提交完成再开始新操作
      // （避免新操作的写入混入正在提交的事务）
      sleep(&log, &log.lock);

    } else if(log.lh.n + (log.outstanding + 1) * MAXOPBLOCKS > LOGSIZE) {
      // 日志空间不足：当前已用 log.lh.n 个槽，
      // 加上"已有 outstanding 个操作"+"新操作"各自最多 MAXOPBLOCKS 个块
      // 超过了 LOGSIZE(=30) → 等待当前事务提交后腾出空间
      sleep(&log, &log.lock);

    } else {
      // 可以开始新操作
      log.outstanding += 1;
      release(&log.lock);
      break;
    }
  }
}

begin_op() 的空间预留逻辑：

(log.lh.n) + (log.outstanding + 1) × MAXOPBLOCKS > LOGSIZE
     ↑                  ↑
已用槽位      "新操作开始后，已有操作+新操作的最坏用量"

这是一种悲观预留：假设每个进行中的系统调用都会用满 MAXOPBLOCKS 个日志槽，提前预留，防止日志溢出。实际上大多数操作用不了那么多槽，但这保证了安全性。

log.committing 标志的作用：

提交期间（commit() 执行时），log.committing = 1。此时新的 begin_op() 必须等待，原因是提交本身是一个多步操作（写日志 → 写头 → 安装 → 清零），如果提交中途有新操作混入，新操作的写操作会与提交的日志数据交织，破坏崩溃一致性。

3.4 end_op()——事务结束，可能触发提交

void end_op(void)
{
  int do_commit = 0;

  acquire(&log.lock);
  log.outstanding -= 1;

  if(log.committing)
    panic("log.committing");   // 持有 log.lock 期间不可能处于提交状态

  if(log.outstanding == 0) {
    // 最后一个活跃操作结束 → 我来负责提交
    do_commit = 1;
    log.committing = 1;
  } else {
    // 还有其他操作进行中，不提交；但 outstanding 减小了，
    // 可能让等待日志空间的 begin_op() 满足条件了，唤醒它们
    wakeup(&log);
  }
  release(&log.lock);

  if(do_commit) {
    // 在不持任何锁的情况下提交
    // （commit() 中会调用 bread/bwrite，可能 sleep，不能持锁 sleep）
    commit();
    acquire(&log.lock);
    log.committing = 0;
    wakeup(&log);     // 唤醒因 committing=1 或空间不足而等待的 begin_op()
    release(&log.lock);
  }
}

“最后一个操作提交”的设计：

xv6 的日志实现了一种组提交（group commit）：多个并发的文件系统系统调用共享同一个事务，直到最后一个调用 end_op() 时才统一提交。这减少了磁盘写操作的次数（多个操作的日志一次性写入），提高了吞吐量。

时间线示例（3 个并发操作）：

        begin_op→ ... end_op
       /                   \
begin_op→ ...  end_op       \
      \              \       \
       begin_op→ ...  end_op  → commit()（最后一个触发）

3.5 log_write()——记录修改意图（替代 bwrite）

void log_write(struct buf *b)
{
  int i;

  if (log.lh.n >= LOGSIZE || log.lh.n >= log.size - 1)
    panic("too big a transaction");
  if (log.outstanding < 1)
    panic("log_write outside of trans");  // 必须在 begin_op/end_op 之间调用

  acquire(&log.lock);

  // 日志吸收（log absorption）：检查该块是否已在本次事务的日志里
  for (i = 0; i < log.lh.n; i++) {
    if (log.lh.block[i] == b->blockno)
      break;    // 已有记录，复用该槽（不额外占用新槽位）
  }
  log.lh.block[i] = b->blockno;  // 记录目标块号

  if (i == log.lh.n) {
    // 新块（之前没有记录过）
    bpin(b);        // 固定缓冲区，防止被 LRU 淘汰（事务提交前必须保留在内存）
    log.lh.n++;     // 日志使用量加一
  }
  // 注意：如果是吸收（i < log.lh.n），不增加 lh.n，也不重复 bpin

  release(&log.lock);
}

日志吸收（Log Absorption）是一个重要优化：

如果同一个块在一个事务中被多次修改（例如频繁更新的 inode 块），log_write() 只记录一个日志槽，提交时只写一次日志和一次安装，而非多次。这大幅减少磁盘写入量。

示例：cat file 期间，inode 的 atime 被更新 3 次

无吸收：日志槽 [inode_block, inode_block, inode_block]  → 3 个槽位
有吸收：日志槽 [inode_block]                            → 1 个槽位（只记最终状态）

bpin(b) 的必要性（第 13 节铺垫）：

log_write() 只是”记录意图”，不立即写磁盘。修改后的数据还在 b->data[] 缓冲区里。如果在 commit() 之前这个缓冲区被 LRU 淘汰并分配给其他块，日志就会丢失这次修改。bpin(b) 使 b->refcnt > 0，bget() 的 LRU 淘汰路径永不触碰它，直到 install_trans() 中 bunpin(dbuf) 解除固定。

3.6 commit()——四步提交

static void commit()
{
  if (log.lh.n > 0) {
    write_log();     // 步骤 1：将缓存中修改过的块写到日志区
    write_head();    // 步骤 2：将日志头写到磁盘 ← 原子提交点
    install_trans(); // 步骤 3：将日志数据安装到实际磁盘位置
    log.lh.n = 0;
    write_head();    // 步骤 4：写 n=0 到日志头，表示事务完成（清除日志）
  }
}

write_log()——步骤 1：缓存→日志区：

static void write_log(void)
{
  for (int tail = 0; tail < log.lh.n; tail++) {
    struct buf *to   = bread(log.dev, log.start + tail + 1);
    // 日志数据区的第 tail 个槽（块 3, 4, 5, ...）

    struct buf *from = bread(log.dev, log.lh.block[tail]);
    // 被修改块的缓冲区（已在内存中，bpin 固定，直接 bread 命中缓存）

    memmove(to->data, from->data, BSIZE);  // 从修改后的块拷贝到日志槽
    bwrite(to);    // 将日志槽写到磁盘
    brelse(from);
    brelse(to);
  }
}

write_head()——步骤 2：原子提交点：

static void write_head(void)
{
  struct buf *buf = bread(log.dev, log.start);   // 日志头块（块 2）
  struct logheader *hb = (struct logheader *)(buf->data);
  hb->n = log.lh.n;
  for (int i = 0; i < log.lh.n; i++)
    hb->block[i] = log.lh.block[i];
  bwrite(buf);   // ← 真正的提交点：这一块写成功，事务永久提交
  brelse(buf);
}

崩溃点分析：

提交的 4 个步骤与崩溃恢复：

[步骤 1] write_log()
  崩溃位置：日志数据区已写部分块，日志头 n 仍为 0（上次清零的状态）
  恢复行为：read_head() 得到 n=0 → install_trans() 空操作 → 丢弃 ✓

[步骤 2] write_head()（原子提交点）
  此步骤是单块写，磁盘保证原子性
  崩溃在写入完成前 → n=0，同上 ✓
  崩溃在写入完成后 → n>0，进入步骤 3-4 的恢复

[步骤 3] install_trans()
  崩溃位置：已安装部分块到实际位置，日志头 n 仍为上次 commit 的值
  恢复行为：read_head() 得到 n>0 → install_trans() 重新安装所有块（幂等）✓

[步骤 4] write_head()（n=0，清除日志）
  崩溃在写入前 → n>0，同步骤 3 的恢复 ✓
  崩溃在写入后 → n=0，正常状态 ✓

四、完整事务流程图

以一次 write(fd, data, n) 系统调用为例，展示从用户程序到磁盘的日志全流程：

用户程序: write(fd, data, n)
         │
         ▼
sys_write() → filewrite() → writei()
         │
         ▼
begin_op()
  acquire(log.lock)
  log.outstanding++
  release(log.lock)
         │
         ▼
[writei 内部循环写数据块]
  bp = bread(dev, blockno)        ← 读目标块（可能触发磁盘读）
  memmove(bp->data, src, n)       ← 在缓冲区中修改数据
  log_write(bp)                   ← 记录"这个块要写"（加入 lh.block[]，bpin）
  brelse(bp)                      ← 释放 buf.lock（数据仍在缓冲区内存中）
         │
         ▼
end_op()
  acquire(log.lock)
  log.outstanding--
  [若 outstanding == 0，设 committing=1，do_commit=1]
  release(log.lock)
         │
         ▼ (若 do_commit)
commit()
  ┌── write_log()
  │     for each lh.block[i]:
  │       to   = bread(dev, log_slot_i)    ← 读日志数据槽
  │       from = bread(dev, lh.block[i])  ← 读修改块（命中缓存）
  │       memmove(to->data, from->data)   ← 复制到日志槽
  │       bwrite(to)                       ← 写日志数据到磁盘
  │       brelse(from); brelse(to)
  │
  ├── write_head()                         ← 原子提交点：写日志头（n > 0）
  │
  ├── install_trans()
  │     for each lh.block[i]:
  │       lbuf = bread(dev, log_slot_i)   ← 读日志数据槽
  │       dbuf = bread(dev, lh.block[i]) ← 读目标块
  │       memmove(dbuf->data, lbuf->data) ← 复制到目标块
  │       bwrite(dbuf)                    ← 写目标块到磁盘
  │       bunpin(dbuf)                    ← 解除 bpin
  │       brelse(lbuf); brelse(dbuf)
  │
  └── lh.n = 0; write_head()             ← 清除日志（n = 0）
         │
         ▼
acquire(log.lock); committing=0; wakeup(&log); release(log.lock)

数据在磁盘上的三次落地：

写操作 写入位置 目的
write_log() 中的 bwrite(to) 日志数据区（块 3-31） 备份修改内容到日志
write_head() 中的 bwrite(buf) 日志头块（块 2） 原子提交点
install_trans() 中的 bwrite(dbuf) 实际数据位置 将修改安装到正确位置

五、并发事务：group commit 详解

5.1 多个 FS 系统调用共享一个事务

时间线（3 个并发 FS 系统调用）：

操作 A: begin_op() ... log_write(b1) ... log_write(b2) ... end_op()
操作 B:     begin_op() ... log_write(b3) .............. end_op()
操作 C:         begin_op() ... log_write(b4) .......... end_op()
                                                             │
                        outstanding 减到 0 ─────────────────┘
                                committing=1，commit()
                                write_log({b1,b2,b3,b4})
                                write_head(n=4)
                                install_trans()
                                write_head(n=0)

这 4 个块在同一次提交中落盘，只产生了：

  • 4 次日志数据写（write_log）
  • 1 次日志头写（write_head，提交点）
  • 4 次安装写（install_trans）
  • 1 次日志头清零写

如果 A、B、C 各自独立提交，则需要 3 组上述操作，磁盘写次数大约是 group commit 的 3 倍。

5.2 日志空间与并发限制

// begin_op() 中的等待条件：
log.lh.n + (log.outstanding + 1) * MAXOPBLOCKS > LOGSIZE

代入实际数值（LOGSIZE=30，MAXOPBLOCKS=10）：

  • 若 outstanding=0（无并发）：允许最多 30 块，即 3 个”最大操作”在飞行
  • 若 outstanding=1：新操作需要 log.lh.n + 2×10 ≤ 30 → log.lh.n ≤ 10，已用超过 10 个槽就要等待
  • 若 outstanding=2：log.lh.n + 3×10 ≤ 30 → log.lh.n ≤ 0，根本无法再接受新操作

这个约束保证了任何时候日志不会溢出，代价是在日志接近满时新操作需要等待。

5.3 log.committing vs log.outstanding

状态变量 含义 何时为真
log.committing = 1 正在执行 commit()，禁止新事务 commit() 执行期间
log.outstanding > 0 有 FS 系统调用在 begin/end 之间 每次 begin_op 到 end_op

两者共同决定了 begin_op() 是否需要等待：只要二者之一为真，新系统调用必须 sleep。

六、磁盘布局与实际地址

用数字具体化日志的磁盘映射（参考 mkfs.c）：

log.start  = sb.logstart = 2
log.size   = sb.nlog     = LOGSIZE = 30

日志头块：  块 2
日志数据槽：块 3（第 0 槽），块 4（第 1 槽），...，块 32（第 29 槽）

示例：log.lh = {n=3, block=[45, 60, 61]}
  → 提交时：
      write_log() 将块 45 的内容写到块 3（日志槽 0）
                  将块 60 的内容写到块 4（日志槽 1）
                  将块 61 的内容写到块 5（日志槽 2）
      write_head() 写 {n=3, block=[45,60,61]} 到块 2
      install_trans() 将块 3 的内容写到块 45（安装）
                      将块 4 的内容写到块 60（安装）
                      将块 5 的内容写到块 61（安装）
      write_head() 写 {n=0} 到块 2

七、动手实验

实验 1：观察日志的四步提交过程

在 commit() 的每个步骤中加入 printf，追踪一次文件写入的日志流程：

static void commit()
{
  if (log.lh.n > 0) {
    printf("commit: step 1 - write_log (n=%d blocks)\n", log.lh.n);
    write_log();

    printf("commit: step 2 - write_head (COMMIT POINT)\n");
    write_head();

    printf("commit: step 3 - install_trans\n");
    install_trans();

    printf("commit: step 4 - clear log (n=0)\n");
    log.lh.n = 0;
    write_head();
    printf("commit: done\n");
  }
}

同时在 log_write() 中打印：

void log_write(struct buf *b)
{
  // ...（原有代码）
  if (i == log.lh.n) {
    printf("log_write: NEW block %d (slot %d)\n", b->blockno, i);
  } else {
    printf("log_write: ABSORB block %d (slot %d)\n", b->blockno, i);
  }
  // ...
}

在 xv6 中运行 echo hello > /tmp/test，观察：

  • 哪些块被 log_write() 记录？（目录块、inode 块、数据块）
  • 日志吸收发生了几次？
  • 四步提交各自触发了几次磁盘 I/O？

实验 2：理解 write_head() 是原子提交点

思考实验（无需修改代码，用纸笔分析）：

假设 write_head() 在写到磁盘的中途系统崩溃（断电），分两种情况：

情况 A：日志头块（块 2）的写入尚未完成（n 字段还是 0）：

  • 重启后 read_head() 得到 n = 0
  • install_trans() 不执行（循环 0 次）
  • write(fd, data, n) 的结果：数据丢失（但文件系统一致）

情况 B：日志头块的写入已完成（n 已更新）：

  • 重启后 read_head() 得到正确的 n 和 block[]
  • install_trans() 重新安装所有块
  • write(fd, data, n) 的结果：数据完整写入

结论：用户视角的”数据是否持久”取决于 fsync() 是否被调用（xv6 没有 fsync，所有操作完成后会自动提交）。

实验 3：模拟崩溃并验证恢复

在 install_trans() 中模拟中途崩溃（在安装第 1 个块后触发 panic）：

static void install_trans(void)
{
  static int panic_once = 1;   // 只 panic 一次
  for (int tail = 0; tail < log.lh.n; tail++) {
    // ... 原有安装代码 ...
    bwrite(dbuf);

    if(panic_once && tail == 0 && log.lh.n > 1) {
      panic_once = 0;
      panic("SIMULATED CRASH: mid-install");   // 模拟崩溃
    }
  }
}
  1. 运行 xv6，执行 echo hello > test.txt，触发 panic（安装到一半崩溃）
  2. 重启 xv6（make qemu），观察 initlog() 时的恢复输出
  3. 运行 cat test.txt，验证数据是否完整

预期结果：因为 write_head() 在 panic 前已完成（n > 0），恢复时会重新 install_trans()，cat test.txt 应该能看到 hello。

实验 4：分析 begin_op() 的等待条件

在 begin_op() 中打印等待原因：

void begin_op(void)
{
  acquire(&log.lock);
  while(1) {
    if(log.committing) {
      printf("begin_op: waiting for commit to finish\n");
      sleep(&log, &log.lock);
    } else if(log.lh.n + (log.outstanding+1)*MAXOPBLOCKS > LOGSIZE) {
      printf("begin_op: waiting for log space (lh.n=%d, outstanding=%d)\n",
             log.lh.n, log.outstanding);
      sleep(&log, &log.lock);
    } else {
      log.outstanding++;
      release(&log.lock);
      break;
    }
  }
}

运行 usertests（会产生大量并发文件操作），统计：

  • “waiting for commit” 和 “waiting for log space” 各出现多少次？
  • 哪个等待条件更频繁？

分析：usertests 有 forktest 等会创建大量进程的测试，这些进程会并发调用文件系统。观察日志空间的竞争情况，理解 group commit 的必要性。

实验 5：理解 log_write 必须在 begin_op/end_op 之间调用

临时在 log.c 顶部直接调用 log_write() 而不经过事务：

// 在某个不合适的地方（如 kinit 早期初始化中）调用 log_write
// 观察 "log_write outside of trans" 的 panic

或者直接阅读 log_write() 的断言：

if (log.outstanding < 1)
  panic("log_write outside of trans");

思考：为什么必须在事务内才能调用 log_write()？如果不做这个检查，会有什么后果？（提示：提交时 commit() 假设 lh.block[] 中的所有块都需要写，如果不在事务中，lh.n 不会正确更新，缓冲区也没有 bpin，可能被淘汰）

八、本节小结

概念 要点
崩溃一致性 多步磁盘写的中间状态不应在崩溃后持久化
WAL 规则 先写日志再写数据；日志头是原子提交点
磁盘布局 块 2=日志头；块 3-32=日志数据槽；LOGSIZE=30
begin_op outstanding++；等待 committing 或空间不足
end_op outstanding--；最后一个触发 commit()
log_write 记录”意图”（块号加入 lh.block[]）+ bpin；不立即写磁盘
日志吸收 同一块多次 log_write 只占一个槽位（写最终状态）
commit() 4 步：写日志数据 → 写日志头（提交点）→ 安装 → 清零
install_trans 幂等操作：日志→实际位置，可在崩溃后重复执行
group commit 多个并发系统调用共享一个事务，减少磁盘写次数
bpin/bunpin log_write 时固定 buf（防 LRU 淘汰）；install_trans 后解除
崩溃恢复逻辑 n==0 → 丢弃；n>0 → redo（幂等）

关键规则：

  1. 所有文件系统写操作必须在 begin_op/end_op 之间
  2. 修改缓冲区后必须调用 log_write()，而不是 bwrite()
  3. log_write() 只记录意图，commit() 才真正落盘
  4. 原子提交点是 write_head()（单块写，磁盘保证原子性）

下一节预告：第 15 节（Inode 层与目录）将在日志层之上构建文件和目录的磁盘表示，大量使用 bread()、log_write()、begin_op/end_op 来实现原子的 inode 分配、数据块读写和路径解析。
